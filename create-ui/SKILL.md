# create-ui

보여줄 데이터와 사용자가 해야 할 일을 먼저 정하고, 그에 맞는 페이지와 UI를 구현한다. 필요한 정보만 노출하며 모든 작업과 설정은 **현재 프로젝트**에만 적용한다.

## 요청과 명령 구분

명령은 스킬에 전달하는 요청의 구분이다. 별도 실행 프로그램이나 명령 파서를 만들지 않는다.

| 요청 | 수행할 작업 |
| --- | --- |
| `$create-ui <만들 웹사이트>` | 데이터 포맷과 페이지 계층을 정의하고 UI 및 필요한 서버·API·저장소를 구현한다. |
| `$create-ui migrate <전환 범위>` | [migrate 지침](reference/commands/migrate.md)을 읽고 기존 기능·데이터 계약을 보존하며 기술과 화면을 전환한다. |
| `$create-ui style` | [style 지침](reference/commands/style.md)에 따라 현재 프로젝트의 설정과 변경 가능한 항목을 짧게 보여준다. |
| `$create-ui style <변경 요청>` | [style 지침](reference/commands/style.md)에 따라 시각적 값, 개별 화면의 배치, 페이지 계층과 탐색 방식을 수정한다. |
| `$create-ui help` | [help 지침](reference/commands/help.md)에 따라 역할과 짧은 사용 예시를 안내한다. |

`help`와 변경 요청이 없는 `style`은 조회만 한다. 파일 생성·설치·서버 실행·기술 전환을 시작하지 않는다. 아직 웹 프로젝트가 없으면 현재 설정이 없음을 알리고 사용법을 안내한다. `style` 조회를 위해 별도의 미리보기 앱을 만들지 않는다.

해당 명령 문서와 현재 작업에 필요한 참고 문서만 읽는다. 데이터에 맞는 Block은 [Block 참고](reference/blocks.md), 페이지 구성은 [레이아웃](reference/layout.md), UI 선택과 아이콘은 [컴포넌트](reference/components.md), 컬러와 실제 스타일 값은 [스타일 시스템](reference/style-system.md)을 사용한다.

## 작업 범위 확인

- 요청에 필요한 현재 프로젝트의 구조, 실행 명령, 기존 UI·스타일·데이터·서버를 확인한다. 기존 변경과 규칙을 보존하며 관련 없는 파일을 정리하지 않는다.
- 새 프런트엔드와 전환 대상은 Vite·React·Tailwind CSS·shadcn/ui를 사용하고, 새 코드와 전환 대상 코드는 TypeScript로 작성한다. 좁은 `style` 요청을 프로젝트 전체의 기술 전환으로 확대하지 않는다.
- 판단 근거를 짧게 알리고 진행한다. 고정된 디자인 승인 단계를 두지 않는다. 사용 목적·데이터 계약·기존 브랜드 등 결과를 크게 바꾸는 충돌이 있으면 영향받는 부분만 질문하고 독립적인 작업은 계속한다.
- 서버를 구성하거나 전환하는 작업에서 **기존 서버가 있으면 유지할지 교체할지 질문한다.** 이 작업에서 이미 받은 선택은 다시 묻지 않는다. 답변이 없다는 이유로 교체를 결정하지 않으며, 단순 스타일 수정 때문에 서버 교체 질문을 시작하지 않는다.
- 완성된 스킬이나 프로젝트에 접근할 수 있다는 이유로 전역 설치·배포·외부 서비스 변경을 실행하지 않는다. 요청받은 프로젝트 변경과 검증의 범위를 지킨다.

## 데이터에서 페이지로

UI를 만들기 전에 다음 내용을 코드·API·기존 자료와 요청에서 정리한다. 자료가 없으면 에이전트가 먼저 필요한 데이터 포맷을 정의한다. 사용자의 완성된 데이터 명세 제출을 시작 조건으로 삼지 않는다.

1. 데이터의 종류, 필드, 관계, 표시 형식과 필요한 상태를 정한다. 기존 API와 저장 데이터의 계약은 유지한다. 데이터 모델 정의를 DB 도입이나 기존 데이터 재설계와 동일하게 취급하지 않는다.
2. 데이터 종류별 페이지 분할을 기본으로 하여 각 페이지의 데이터와 주요 행동을 정한다. 작업에 필요하지 않은 통계·설명·메뉴를 화면을 채우기 위해 추가하지 않는다.
3. 페이지의 깊이와 상하 관계를 설계한다. 불필요한 경유 페이지와 중복 계층을 줄이고, 관련 작업 사이의 이동이 짧고 이해하기 쉽게 연결한다.
4. 목록과 상세는 **별도 페이지**를 기본으로 한다. 동선 단축을 이유로 상세를 옆 패널이나 사이드 페이지로 바꾸지 않는다. 목록으로 돌아오면 검색·필터 등 작업 맥락을 유지한다.
5. 페이지가 적으면 상단 메뉴, 관리 대상과 하위 항목이 많으면 사이드바 등 알맞은 탐색 패턴을 선택한다. 메뉴 패턴을 먼저 고르고 데이터와 페이지를 억지로 맞추지 않는다.

페이지를 실제로 필요한 영역으로 나눈다. Navbar·Sidebar·페이지 제목 영역·검색 도구 모음·본문·Footer 중 존재하는 영역을 확인하고, 공통 영역과 페이지별 영역을 구분한다. 각 필요한 영역에 적합한 shadcn.io Block을 대응시킨다. 본문용 Block 하나를 고른 뒤 Navbar 등을 임의로 조합한 채 전체 페이지가 Block을 참고했다고 설명하지 않는다. 여러 페이지의 공통 Navbar는 한 번 선택하고 일관되게 재사용한다. 원본에만 있는 영역이나 기능을 새로 추가하지 않는다.

데이터 포맷과 페이지별 데이터·행동·경로의 관계를 구현에 사용할 수 있을 정도로 짧게 정리한다. 이 정리를 위해 별도 기획 문서나 승인 절차를 필수로 만들지 않는다.

## Block을 참고해 화면 구성

[shadcn.io Blocks](https://www.shadcn.io/blocks)의 현재 카탈로그와 관련 카테고리를 탐색해 데이터와 필요한 화면 영역에 맞는 후보를 찾는다. 문서의 예시나 과거 테스트에서 사용한 Block을 기본 후보 목록으로 삼지 않는다. 항목의 반복 방식, 필드의 우선순위, 비교·입력·읽기 목적, 도구 모음과 반응형 동작을 기준으로 고른다. 접근 가능한 실제 프리뷰를 열어 보고 선택하며, Block 이름이나 설명만 읽은 상태를 화면을 확인한 것으로 취급하지 않는다.

- Block은 레이아웃 참고용이다. Block 코드 구매·설치나 완전히 동일한 재현을 요구하지 않는다. UI 구현에는 [컴포넌트 기준](reference/components.md)에 따라 실제 shadcn/ui·shadcn.io 컴포넌트를 사용한다.
- 핵심 정보 관계를 유지하면서 열 수·너비·순서·간격을 조정한다. 참고한 구조와 무관한 자유로운 전면 재구성을 기본 방식으로 삼지 않는다.
- 사용하지 않는 문구·버튼·배지·장식은 제거한다. 이를 제거한 빈자리를 다른 불필요한 정보로 채우지 않는다.
- 가까운 후보가 있으면 핵심 구조를 유지해 조정한다. 사이트에 접근할 수 없거나 적합한 후보가 없으면 그 이유를 알리고 shadcn/ui 기본 컴포넌트로 진행한다.
- 실제 확인한 Block 링크와 선택 이유를 작업 결과에 짧게 남긴다. 확인하지 않은 출처를 만들거나 추측한 내용을 확인한 사실처럼 쓰지 않는다.
- 원본에서 유지할 정보 관계, 제거할 요소, 바꿀 배치와 이유를 짧게 정리한다. 구현 후 비슷한 화면 폭에서 원본 프리뷰와 결과를 비교한다. 컴포넌트 import나 빌드 성공만으로 적절한 Block 활용을 완료한 것으로 판단하지 않는다.
- 영역별로 역할·참고 Block·유지/변경 이유를 짧게 연결하고, 참고가 누락된 영역이 없는지 확인한다. 하나의 Block이 여러 영역을 이미 포함하면 같은 Block을 재사용하며, 영역마다 억지로 별도 Block을 추가하지 않는다. 접근 실패 시 대체 처리도 해당 영역별로 구분한다.

## 공통 스타일과 UI 동작

새 스타일을 적용하거나 수정할 때 [스타일 시스템](reference/style-system.md)을 읽고 [스타일 자산](assets/styles.css)을 사용한다. 자산은 **현재 프로젝트에 복사하거나 필요한 토큰을 병합**한다. 설치된 스킬의 원본 파일을 직접 수정하거나 연결해 다른 프로젝트와 설정을 공유하지 않는다. 기존 프로젝트의 변경을 원본 자산 복사로 덮어쓰지 않는다.

- 새 UI를 선택할 때 [컴포넌트 기준](reference/components.md)에 따라 **shadcn/ui와 shadcn.io UI 카탈로그를 함께 확인**한다. 기존 구현이 요구사항을 충족하면 재사용하고, 확장 UI에 적합한 shadcn.io 컴포넌트를 도입할 수 있으면 실제 소스를 사용한다. 기본 HTML에 유사한 CSS를 붙이거나 이름만 같은 컴포넌트로 대체하지 않는다. 기본 컨트롤은 실제 shadcn/ui를 사용하며 Select는 Trigger·Content·Item 조합을 따른다. 명시적인 네이티브 선택 상자 요구가 없는 한 `<select>`로 대체하지 않는다.
- 아이콘은 **Lucide**를 사용한다. React에서는 `lucide-react`의 필요한 아이콘을 이름으로 가져온다. 장식용 이모지·유니코드 화살표·다른 아이콘 패키지로 대체하지 않는다. 필요한 아이콘만 쓰며 아이콘 버튼에는 접근 가능한 이름을 제공한다.
- 중립을 기본으로 블루·그린·바이올렛·오렌지의 라이트·다크 팔레트를 제공한다. 프로젝트의 `html`에 `data-palette`를 적용하며 테마는 `.light` 또는 `.dark`로 표현한다.
- 시스템 테마를 기본으로 따르고 사용자가 라이트·다크·시스템 설정을 선택할 수 있게 한다. 앱에서 선택한 테마를 적용하고, 시스템 모드에서는 운영체제 설정 변경도 반영한다.
- **폰트는 Pretendard, 그 외 디자인 기본값은 shadcn/ui 공식 기본값이다.** 공식 컴포넌트의 클래스와 기본 테마를 그대로 출발점으로 삼는다. 글자 크기·행간·간격·높이·모서리·테두리·그림자·포커스·전환을 자체 값으로 다시 꾸미지 않는다. 앞서 기획한 14/16/24px·4px 간격·6~8px 모서리·120~180ms 같은 커스텀 값은 기본 요구사항에서 제외한다. 명시적인 `style` 변경 요청이 있을 때만 해당 값을 조정한다.
- 선택한 shadcn.io 확장 컴포넌트는 원본의 기본 구조·동작을 유지해 기존 테마에 연결한다. shadcn/ui 기본값을 따른다는 이유로 확장 UI를 직접 다시 만들거나 핵심 기능을 제거하지 않는다.
- 컴포넌트는 역할에 맞게 선택한다. 입력 필드의 값 선택은 Select를 사용하되, 전역 테마 같은 부가 설정은 공식 ModeToggle의 아이콘 Button과 DropdownMenu처럼 적절한 패턴을 사용한다. 선택지가 있다는 이유로 모든 UI를 Select로 만들지 않는다.
- 화면 문구는 [텍스트 필요성 검수](reference/layout.md#텍스트-필요성-검수)를 적용한다. 각 문구를 지웠을 때 현재 작업에 필요한 어떤 정보를 놓치거나, 무엇을 오해하거나, 어떤 행동을 수행하기 어려워지는지 구체적으로 설명할 수 있어야 한다. 근거가 없으면 삭제하고, 같은 역할의 문구가 겹치면 합친다. 유용한 정보라도 기존 제목·레이블·링크를 정확하게 고쳐 전달할 수 있으면 별도 설명은 제거한다. 입력 레이블·오류 메시지·접근 가능한 이름과 데이터 해석에 필요한 조건은 보존한다.
- 불필요한 정보는 삭제한다. 가끔 필요한 정보와 부가 기능은 상세 보기·펼치기·더보기처럼 명시적으로 여는 곳에 둔다. 이 원칙을 주 상세 페이지를 옆 패널로 바꾸는 근거로 사용하지 않는다.
- 비교하는 목록은 적당히 조밀하게, 읽기와 입력 영역은 여유 있게 배치한다. 정보량을 맞추려고 글자를 과도하게 줄이지 않는다.
- 데이터 포맷에 있는 모든 필드를 목록에 노출하지 않는다. 식별·비교·주요 행동에 필요한 필드만 우선하고 모델·이력 등의 보조 정보는 상세에 둔다. 검색의 레이블·플레이스홀더·버튼이 같은 설명을 반복하지 않게 하고, 필요한 접근 가능한 이름은 유지한다.
- 입력 폼은 명시적 저장 버튼을 기본으로 한다. 저장 중에는 중복 제출을 막고, 실패하면 입력을 보존하며 해당 폼에 상태와 다시 시도할 방법을 표시한다. 실제 결과 없이 저장 성공을 표시하지 않는다.
- 모바일에서도 핵심 작업을 유지한다. 열 배치와 제어 영역을 조정하고 긴 내용·표·입력창 때문에 화면 전체가 잘리거나 중요한 작업이 사라지지 않게 한다.
- 페이지를 채우기 위한 장식·그림자를 새로 추가하지 않는다. 공식 컴포넌트가 제공하는 기본 그림자·경계선·포커스는 임의로 제거하거나 진하게 바꾸지 않는다.
- **카드 안에 다시 카드를 넣는 중첩 카드는 기본적으로 피한다.** 내부 정보 묶음은 여백·구분선·일반 영역으로 정리한다. 실제 참고한 shadcn.io Block의 프리뷰에서 중첩 카드가 사용된 것을 확인한 경우에만 필요한 범위에서 같은 구조를 허용한다.
- 공식 컴포넌트의 기본 상태 전환을 유지하고 움직임 줄이기 설정을 따른다. 별도의 장식적인 반복 효과나 스크롤 등장 효과를 추가하지 않는다.

## 서버와 저장소

기존 서버가 없으면 Hono + Node로 구성한다. 기존 서버가 있으면 앞서 확인한 유지·교체 선택을 따른다. 유지하기로 한 서버를 단일 Node 서버 기본값에 맞추기 위해 다시 작성하지 않는다.

- 새 구성은 하나의 프로젝트에서 개발 중 Vite와 API를 함께 실행하고, 빌드 후에는 하나의 Node 서버가 웹 파일과 API를 제공하도록 한다. 기존 서버를 유지하면 해당 환경에 맞게 프런트엔드와 API를 연결한다.
- API 라우트를 먼저 처리한다. 없는 API와 없는 정적 파일은 적절한 오류로 응답하며 HTML 성공 응답으로 덮지 않는다. 클라이언트 라우팅용 `index.html` 대체 응답은 앱의 페이지를 여는 GET·HEAD 요청에 한정하여 상세 주소 직접 접근과 새로고침을 지원한다.
- 정적 파일은 빌드된 공개 파일 디렉터리에서만 제공한다. 소스·설정·DB 파일·비공개 데이터를 공개 디렉터리에 넣지 않는다.
- 필요한 조회·수정·저장 API를 실제로 연결한다. 요청 입력을 서버에서 검증하고 실패를 클라이언트가 구분할 수 있도록 응답한다. 기존 인증·권한 검사와 데이터 계약을 보존한다.
- DB는 필요한 경우에만 추가한다. 간단한 정적 데이터나 일시적 UI 상태에 DB를 자동으로 붙이지 않는다. 영속 저장이 필요하면 SQLite를 기본 후보로 삼고 요구사항에 맞지 않으면 다른 저장소를 선택한다. 재시작 후 보존해야 하는 데이터를 메모리 저장으로 대신하지 않는다.
- 의존성·버전·패키지 매니저는 현재 프로젝트와 호환되게 선택한다. 실제 사용하는 API는 해당 버전의 공식 문서로 확인하고, 필요하지 않은 저장소·인증·운영 계층을 미리 추가하지 않는다.
- 실행·빌드·시작 명령과 필요한 환경 설정을 프로젝트에 남긴다. 새 서버를 작성했다면 API 입력·실패 처리와 실제 저장 요구를 검증한다.

## 검증과 결과 보고

**테스트 파일·테스트 스위트·별도 검증 스크립트를 만들지 않는다.** 검수용 앱이나 테스트 전용 미리보기도 생성하지 않는다. 필요한 빌드와 이미 존재하는 검사는 사용할 수 있으며, 변경한 실제 앱을 브라우저에서 확인한다. 빌드 성공만으로 화면 검수를 대신하지 않는다.

- 데스크톱과 모바일에서 핵심 조회·이동·입력·저장 작업을 수행한다. 상세 주소 직접 접근과 목록으로 돌아올 때의 검색·필터 맥락도 확인한다.
- 라이트·다크, 시스템 설정 반영과 사용자 전환을 확인한다. 키보드만으로 주요 컨트롤을 사용할 수 있고 포커스와 필요한 레이블이 보이는지 확인한다.
- 긴 내용·빈 목록·로딩·오류·저장 실패에서 레이아웃과 사용법을 확인한다. 실패했을 때 입력과 필요한 데이터가 보존되는지 확인한다.
- 완료 전에 실제 화면과 주요 상태의 텍스트 전체에 [필요성 검수](reference/layout.md#텍스트-필요성-검수)를 수행한다. 일부 문구만 다듬거나 빌드가 통과한 것으로 대체하지 않는다. 검수 결과와 미검수 화면을 짧게 보고한다.
- [컴포넌트 실제 사용과 누락](reference/components.md#실제-사용과-누락-검수)을 검수한다. 선택한 shadcn.io 소스가 실제 화면에서 데이터·이벤트와 연결되어 동작하는지 추적하고, 적합한 후보를 놓친 채 직접 구현한 UI도 확인한다. 파일·import·빌드 성공만으로 사용했다고 보고하지 않는다.
- 움직임 줄이기 설정에서 전환 효과가 줄어드는지 확인한다. 장식과 설명을 제거한 결과가 사용성을 해치지 않는지 실제 화면을 보고 판단한다.
- 서버·저장소를 변경했다면 실제 API와 연결해 입력 검증·실패·필요한 영속성을 확인한다. `migrate`에서는 기존 주요 흐름과 계약을 비교한다.

결과에는 바뀐 기능·페이지·스타일, 실제 참고한 Block과 사용한 shadcn.io 컴포넌트, 실행 방법, 수행한 검증과 남은 한계를 짧게 남긴다. 브라우저나 필요한 환경을 사용할 수 없으면 수행한 좁은 검증과 확인하지 못한 항목을 구분한다. 확인하지 않은 동작을 성공으로 보고하지 않는다.
