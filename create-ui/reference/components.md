# shadcn/ui 컴포넌트와 Lucide 아이콘

화면의 컨트롤을 선택하거나 기존 UI를 바꿀 때 읽는다. 레이아웃은 [레이아웃 기준](layout.md), 색상·크기·여백은 [스타일 시스템](style-system.md)을 따른다.

## 실제 shadcn/ui를 우선 사용한다

1. 프로젝트의 `components/ui` 또는 해당 역할의 기존 컴포넌트, `components.json`, import 별칭을 확인한다.
2. 필요한 shadcn/ui 컴포넌트가 있으면 재사용한다. 없으면 현재 프로젝트의 설정과 패키지 매니저에 맞춰 공식 구현을 필요한 만큼만 추가한다.
3. 현재 shadcn 설정과 기반 라이브러리를 유지한다. 프로젝트가 사용하는 Base UI·Radix 등의 구성을 이유 없이 섞거나 전환하지 않는다.
4. 공식 컴포넌트의 기본 클래스와 디자인을 유지한다. 테두리·색상·높이·패딩·글자 크기·모서리·그림자·포커스를 별도의 자체 값으로 바꾸지 않는다. 호출하는 화면의 `className`에서도 기본 외형을 덮어쓰지 않는다. 폭·배치 같은 페이지 구성과 명시적인 `style` 변경에 필요한 부분만 조정한다.
5. 컴포넌트의 키보드 처리·포커스 복귀·포털·접근성 동작을 외형 수정 때문에 제거하지 않는다. 실제 설치한 스타일·버전의 공식 예제와 열린 상태까지 비교한다. import 이름만 같다는 이유로 기본 디자인을 따른 것으로 판단하지 않는다.

| 필요한 UI | 우선 사용할 shadcn/ui 구성 |
| --- | --- |
| 실행·저장·취소 | Button |
| 한 줄·여러 줄 입력 | Input, Textarea, 필요한 Label 또는 Field |
| 입력 필드·필터의 정해진 값 하나 고르기 | Select |
| 전역 테마처럼 사용 빈도가 낮은 표시 설정 | 공식 ModeToggle 형태의 아이콘 Button과 DropdownMenu |
| 검색 입력과 관련 부가 조작 | InputGroup 또는 기존 검색 도구 모음 구성 |
| 검색이 필요한 선택 목록 | 프로젝트에 맞는 Combobox 구성 |
| 선택·동의·완료 상태 | Checkbox, RadioGroup, Switch 중 의미에 맞는 구성 |
| 부가 행동 | DropdownMenu |
| 짧은 확인·집중 작업 | Dialog, AlertDialog |
| 같은 화면의 관련 뷰 전환 | Tabs |
| 반복 데이터 비교 | Table 또는 실제 기능에 필요한 Data Table 구성 |
| 반복 탐색 영역 | Sidebar, NavigationMenu 등 현재 페이지 구조에 맞는 구성 |

해당 컴포넌트가 있는데도 기본 HTML 컨트롤에 비슷한 CSS만 붙여 대체하지 않는다. `Select`라는 이름으로 `<select>`를 감싼 자체 컴포넌트도 대체 구현이다. HTML의 의미 있는 구조 요소나 shadcn 컴포넌트 내부의 네이티브 요소를 없애라는 뜻은 아니다.

`Card`는 정보 묶음의 실제 역할이 있을 때 사용한다. 카드 안에 다시 Card를 넣는 구조는 기본적으로 피하고, 내부 구분은 여백·구분선·일반 영역으로 처리한다. 실제 참고한 shadcn.io Block에서 중첩 카드를 확인한 경우에만 같은 정보 관계를 표현하는 데 사용할 수 있다.

## Select 구성

필드나 필터에서 고정된 값을 고르는 UI에는 실제 shadcn/ui Select를 사용한다. 운영체제 기본 선택 상자가 필요한 명시적 요구가 없는 한 네이티브 `<select>` 또는 Native Select로 바꾸지 않는다. 전역 표시 설정·탐색·실행 메뉴는 각각의 역할에 맞는 컴포넌트를 선택한다.

- 루트 `Select`가 값과 변경 처리를 담당한다.
- `SelectTrigger` 안의 `SelectValue`가 현재 선택과 플레이스홀더를 표시한다.
- `SelectContent` 안의 `SelectItem`들이 실제 선택 목록을 구성한다. 관련 항목을 묶어야 할 때만 그룹과 구분을 추가한다.
- 레이블을 Trigger에 연결하고 빈 값·비활성·오류 상태를 실제 컴포넌트의 지원 방식으로 표현한다.
- 사용하는 기반 구현의 속성을 확인한다. Base UI 예시의 `items` 같은 속성을 다른 기반의 구현에도 있다고 가정하지 않는다.

선택 전에는 Trigger만 봐서는 부족하다. 실제로 열어 항목 배경·선택 표시·포커스·오버레이 위치를 확인한다. 방향키·Enter·Escape와 포커스 복귀, 긴 항목의 처리, 모바일과 라이트·다크에서의 가독성을 살핀다. 관련 기준은 [shadcn/ui Select 공식 문서](https://ui.shadcn.com/docs/components/select)를 사용한다.

## 컨트롤의 역할을 먼저 정한다

공식 컴포넌트를 사용했다는 사실과 그 위치에 적합하다는 판단은 별개다. 현재 사용자의 주요 작업, 조작 빈도, 공간과 다른 컨트롤과의 관계를 보고 선택한다.

- 헤더의 테마 전환은 [공식 ModeToggle 예시](https://ui.shadcn.com/docs/dark-mode/vite)처럼 Lucide Sun/Moon 아이콘 Button과 DropdownMenu로 제공한다. 별도 설정 폼의 테마 필드라면 Select를 사용할 수 있다.
- 검색은 표와 함께 사용하는 도구 모음에 배치하고 InputGroup의 Search 아이콘처럼 의미 있는 단서를 사용한다. 같은 뜻의 큰 제목·레이블·플레이스홀더·버튼을 모두 반복하지 않는다. 숨긴 시각 레이블을 대신할 접근 가능한 이름은 유지한다.
- 즉시 검색인지 제출 후 검색인지는 데이터 양과 기존 동작에 맞춘다. 원본 Block의 동작을 무조건 복사하거나 입력만으로 저장하는 기능으로 확대하지 않는다.
- 상태는 텍스트·Badge 등 비교에 필요한 표현을 선택한다. 모든 값에 배지·아이콘을 붙이는 것으로 정보 우선순위를 대신하지 않는다.

## 아이콘은 Lucide로 통일한다

React에서는 `lucide-react`의 필요한 아이콘만 이름으로 가져온다. 기존 의존성과 아이콘 사용 방식을 확인하고, 일반적인 정적 아이콘을 위해 전체 아이콘 모음을 동적으로 불러오는 구조를 만들지 않는다. 사용법은 [Lucide React 공식 문서](https://lucide.dev/guide/packages/lucide-react)를 참고한다.

예를 들어 뒤로 가기는 `ArrowLeft`, 검색은 `Search`, 추가는 `Plus`처럼 의미에 맞는 Lucide 아이콘을 사용한다. 유니코드 화살표·이모지·다른 아이콘 패키지·직접 그린 대체 SVG를 아이콘 대신 사용하지 않는다.

- 크기와 선 두께를 같은 역할끼리 일관되게 적용하고, 색상은 기본적으로 `currentColor`와 주변 스타일을 따른다.
- 텍스트와 같은 의미의 장식 아이콘은 보조기술에서 중복 읽지 않게 처리한다.
- 아이콘만 있는 버튼에는 의미 있는 접근 가능한 이름을 제공한다. 모호한 행동을 아이콘만으로 표현하지 않는다.
- 아이콘이 없어도 충분히 이해되는 곳에는 아이콘을 채워 넣지 않는다.
- 검색·테마·뒤로 가기처럼 표준적인 조작에는 의미에 맞는 아이콘을 사용한다. 데이터 종류를 빠르게 구별하는 데 도움이 되는 경우에도 Lucide 아이콘을 사용할 수 있지만, 모든 행·셀에 장식으로 반복하지 않는다.
- 레지스트리에서 받은 컴포넌트가 다른 아이콘 묶음을 사용하면, 해당 아이콘 슬롯을 Lucide로 바꾸고 원래 조작 동작은 유지한다.

## 적용 후 확인

import가 실제 프로젝트의 shadcn/ui 컴포넌트와 `lucide-react`를 가리키는지 확인한다. 개발자 도구에서 색상 토큰이 맞더라도 열린 Select나 Dialog의 포털 안에서 스타일이 달라지지 않는지 실제 화면을 확인한다.

테스트 파일·테스트 스위트·별도 검증 스크립트는 생성하지 않는다. 필요한 빌드·기존 검사와 직접 조작으로 확인하고, 실행하지 않은 확인을 완료했다고 보고하지 않는다.
