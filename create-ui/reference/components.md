# shadcn/ui·shadcn.io 컴포넌트와 Lucide 아이콘

화면의 컨트롤을 선택하거나 기존 UI를 바꿀 때 읽는다. 레이아웃은 [레이아웃 기준](layout.md), 색상·크기·여백은 [스타일 시스템](style-system.md)을 따른다.

## 필요한 UI를 두 카탈로그에서 찾는다

1. 페이지별로 필요한 입력·선택·탐색·표시 기능을 정리하고, 프로젝트의 기존 컴포넌트, `components.json`, import 별칭과 기반 라이브러리를 확인한다.
2. 새 UI를 선택하거나 직접 구현하기 전에 [shadcn/ui 컴포넌트](https://ui.shadcn.com/docs/components)와 [shadcn.io UI 카탈로그](https://www.shadcn.io/ui)를 함께 확인한다. shadcn.io의 현재 분류·검색에서 필요한 기능을 찾고, 후보의 실제 데모·API·설치 방법을 확인한다. Block 목록만 보거나 익숙한 기본 컴포넌트만 살펴본 것으로 탐색을 마치지 않는다.
3. 기존 컴포넌트가 요구사항을 충족하면 재사용한다. 확장 UI가 필요하고 적합한 shadcn.io 구현을 도입할 수 있으면 그 컴포넌트를 실제로 사용한다. 편의상 직접 만들거나 기본 컴포넌트 조합으로 비슷하게 재현하지 않는다. 아래 기본 컨트롤 표를 전체 후보 목록으로 취급하지 않는다.
4. 현재 React·TypeScript·Tailwind·UI 기반과 호환되는 구현을 선택한다. 후보가 추가 기반 라이브러리를 요구하면 필요한 의존성과 영향을 확인하고 해당 컴포넌트 범위에 도입한다. 이를 이유로 기존 프로젝트 전체의 기반을 바꾸지 않는다.

shadcn.io는 shadcn/ui와 별도의 출처다. **Block은 레이아웃 참고용이고, 선택한 UI 컴포넌트는 실제 코드를 도입해 사용한다.** 확인한 페이지의 설치 명령이나 수동 설치 안내에 따라 필요한 소스와 의존성만 추가한다. 컴포넌트 이름만으로 패키지명·레지스트리 URL·설치 명령을 추측하지 않는다. 기존 파일과 같은 경로를 쓰면 내용을 비교해 사용자 수정과 이미 연결된 동작을 보존한다.

선택한 출처의 기본 구조·클래스·접근성·핵심 동작을 유지하고, 프로젝트의 실제 데이터·상태·이벤트에 연결한다. 데이터 계약·import 경로·테마 토큰 등에 필요한 조정은 허용하되 핵심 구현을 자체 코드로 대체한 뒤 원본을 사용했다고 보고하지 않는다. 기본 컨트롤은 shadcn/ui 공식 디자인을 유지하고, 확장 컴포넌트의 스타일 연결은 [스타일 기준](style-system.md)을 따른다.

프로젝트에서 이미 검토한 컴포넌트는 재사용한다. 단순 색상·문구 수정에 전체 카탈로그 탐색이나 컴포넌트 교체를 반복하지 않는다. shadcn.io 사용 개수를 채우려고 불필요한 UI·장식·효과를 추가하지 않는다.

관련 후보를 확인했지만 요구 기능·호환성에 맞지 않거나 실제 코드에 접근할 수 없으면 구체적인 이유와 대체 구성을 알린다. 계정·권한이 필요한 경우 접근하지 못한 코드의 사용을 주장하거나 확인하지 않은 설치 명령을 실행하지 않는다. 가능한 기존 컴포넌트와 shadcn/ui로 진행하고, 해당 부분을 shadcn.io 사용으로 보고하지 않는다. 확인 없이 '적합한 컴포넌트가 없다'고 결론 내리지 않는다.

| 필요한 UI | 우선 사용할 shadcn/ui 구성 |
| --- | --- |
| 실행·저장·취소 | Button |
| 한 줄·여러 줄 입력 | Input, Textarea, 필요한 Label 또는 Field |
| 입력 필드·필터의 정해진 값 하나 고르기 | Select |
| 전역 테마처럼 사용 빈도가 낮은 표시 설정 | 공식 ModeToggle 형태의 아이콘 Button과 DropdownMenu |
| 검색 입력과 관련 부가 조작 | InputGroup 또는 기존 검색 도구 모음 구성 |
| 검색이 필요한 선택 목록 | 프로젝트에 맞는 Combobox 구성 |
| 선택·동의·완료 상태 | Checkbox, RadioGroup, Switch 중 의미에 맞는 구성 |
| 부가 행동 | DropdownMenu |
| 짧은 확인·집중 작업 | Dialog, AlertDialog |
| 같은 화면의 관련 뷰 전환 | Tabs |
| 반복 데이터 비교 | Table 또는 실제 기능에 필요한 Data Table 구성 |
| 반복 탐색 영역 | Sidebar, NavigationMenu 등 현재 페이지 구조에 맞는 구성 |

적합하고 도입 가능한 shadcn/ui·shadcn.io 컴포넌트가 있는데도 기본 HTML 컨트롤에 비슷한 CSS만 붙여 대체하지 않는다. `Select`라는 이름으로 `<select>`를 감싼 자체 컴포넌트도 대체 구현이다. HTML의 의미 있는 구조 요소나 원본 컴포넌트 내부의 네이티브 요소를 없애라는 뜻은 아니다.

`Card`는 정보 묶음의 실제 역할이 있을 때 사용한다. 카드 안에 다시 Card를 넣는 구조는 기본적으로 피하고, 내부 구분은 여백·구분선·일반 영역으로 처리한다. 실제 참고한 shadcn.io Block에서 중첩 카드를 확인한 경우에만 같은 정보 관계를 표현하는 데 사용할 수 있다.

## Select 구성

필드나 필터에서 고정된 값을 고르는 UI에는 실제 shadcn/ui Select를 사용한다. 운영체제 기본 선택 상자가 필요한 명시적 요구가 없는 한 네이티브 `<select>` 또는 Native Select로 바꾸지 않는다. 전역 표시 설정·탐색·실행 메뉴는 각각의 역할에 맞는 컴포넌트를 선택한다.

- 루트 `Select`가 값과 변경 처리를 담당한다.
- `SelectTrigger` 안의 `SelectValue`가 현재 선택과 플레이스홀더를 표시한다.
- `SelectContent` 안의 `SelectItem`들이 실제 선택 목록을 구성한다. 관련 항목을 묶어야 할 때만 그룹과 구분을 추가한다.
- 레이블을 Trigger에 연결하고 빈 값·비활성·오류 상태를 실제 컴포넌트의 지원 방식으로 표현한다.
- 사용하는 기반 구현의 속성을 확인한다. Base UI 예시의 `items` 같은 속성을 다른 기반의 구현에도 있다고 가정하지 않는다.

선택 전에는 Trigger만 봐서는 부족하다. 실제로 열어 항목 배경·선택 표시·포커스·오버레이 위치를 확인한다. 방향키·Enter·Escape와 포커스 복귀, 긴 항목의 처리, 모바일과 라이트·다크에서의 가독성을 살핀다. 관련 기준은 [shadcn/ui Select 공식 문서](https://ui.shadcn.com/docs/components/select)를 사용한다.

## 컨트롤의 역할을 먼저 정한다

실제 컴포넌트를 사용했다는 사실과 그 위치에 적합하다는 판단은 별개다. 현재 사용자의 주요 작업, 조작 빈도, 공간과 다른 컨트롤과의 관계를 보고 선택한다.

- 헤더의 테마 전환은 [공식 ModeToggle 예시](https://ui.shadcn.com/docs/dark-mode/vite)처럼 Lucide Sun/Moon 아이콘 Button과 DropdownMenu로 제공한다. 별도 설정 폼의 테마 필드라면 Select를 사용할 수 있다.
- 검색은 표와 함께 사용하는 도구 모음에 배치하고 InputGroup의 Search 아이콘처럼 의미 있는 단서를 사용한다. 같은 뜻의 큰 제목·레이블·플레이스홀더·버튼을 모두 반복하지 않는다. 숨긴 시각 레이블을 대신할 접근 가능한 이름은 유지한다.
- 즉시 검색인지 제출 후 검색인지는 데이터 양과 기존 동작에 맞춘다. 원본 Block의 동작을 무조건 복사하거나 입력만으로 저장하는 기능으로 확대하지 않는다.
- 상태는 텍스트·Badge 등 비교에 필요한 표현을 선택한다. 모든 값에 배지·아이콘을 붙이는 것으로 정보 우선순위를 대신하지 않는다.

## 아이콘은 Lucide로 통일한다

React에서는 `lucide-react`의 필요한 아이콘만 이름으로 가져온다. 기존 의존성과 아이콘 사용 방식을 확인하고, 일반적인 정적 아이콘을 위해 전체 아이콘 모음을 동적으로 불러오는 구조를 만들지 않는다. 사용법은 [Lucide React 공식 문서](https://lucide.dev/guide/packages/lucide-react)를 참고한다.

예를 들어 뒤로 가기는 `ArrowLeft`, 검색은 `Search`, 추가는 `Plus`처럼 의미에 맞는 Lucide 아이콘을 사용한다. 유니코드 화살표·이모지·다른 아이콘 패키지·직접 그린 대체 SVG를 아이콘 대신 사용하지 않는다.

- 크기와 선 두께를 같은 역할끼리 일관되게 적용하고, 색상은 기본적으로 `currentColor`와 주변 스타일을 따른다.
- 텍스트와 같은 의미의 장식 아이콘은 보조기술에서 중복 읽지 않게 처리한다.
- 아이콘만 있는 버튼에는 의미 있는 접근 가능한 이름을 제공한다. 모호한 행동을 아이콘만으로 표현하지 않는다.
- 아이콘이 없어도 충분히 이해되는 곳에는 아이콘을 채워 넣지 않는다.
- 검색·테마·뒤로 가기처럼 표준적인 조작에는 의미에 맞는 아이콘을 사용한다. 데이터 종류를 빠르게 구별하는 데 도움이 되는 경우에도 Lucide 아이콘을 사용할 수 있지만, 모든 행·셀에 장식으로 반복하지 않는다.
- 레지스트리에서 받은 컴포넌트가 다른 아이콘 묶음을 사용하면, 해당 아이콘 슬롯을 Lucide로 바꾸고 원래 조작 동작은 유지한다.

## 실제 사용과 누락 검수

선택한 컴포넌트마다 **출처 페이지 → 프로젝트의 실제 구현 파일 → 호출하는 화면 → 실제 조작 결과**를 연결해 확인한다. 설치 성공·파일 존재·import·컴포넌트 이름·빌드 성공만으로 사용을 인정하지 않는다.

1. 구현 파일이 확인한 출처의 코드인지 읽고 필요한 조정과 원본 핵심 동작을 대조한다. 같은 이름의 자체 구현, 단순 HTML 래퍼, 사용하지 않는 원본 파일로 사용 근거를 대신하지 않는다.
2. import와 호출 경로를 따라 실제 사용자가 여는 페이지에서 렌더링되는지 확인한다. 사용하지 않는 import, 예제 전용 화면, 도달할 수 없는 분기는 적용으로 세지 않는다. 기본 HTML이나 다른 자체 UI로 우회되는 부분도 확인한다.
3. 데모 데이터·고정 값만 보여주는 상태가 아닌지 확인한다. 대상 프로젝트의 데이터와 상태 변경·입력·선택·저장 등 필요한 이벤트를 연결하고, 실제 앱에서 해당 기능과 키보드·포커스·오류 상태를 조작한다. 열린 오버레이, 모바일과 라이트·다크에서도 확인한다.
4. 작업 대상에서 직접 구현하거나 기본 컴포넌트로 조합한 주요 UI를 다시 살핀다. shadcn.io에 적합한 구현이 있는데 조사 누락이나 편의 때문에 사용하지 않았으면 실제 컴포넌트로 교체한다. 기존 구현이 충분하거나 호환성·접근 문제로 대체했다면 해당 후보와 구체적인 이유를 남긴다.

결과에는 선택한 shadcn.io 컴포넌트의 출처 링크·적용 파일과 화면·확인한 동작을 짧게 연결한다. 확인한 후보를 사용하지 않았다면 이유를 구분하고, 코드나 브라우저를 확인하지 못한 부분은 미검수로 남긴다. 출처 표시는 개발 결과 보고에 남기며 제품 화면에 자동으로 추가하지 않는다.

테스트 파일·테스트 스위트·별도 검증 스크립트는 생성하지 않는다. 필요한 빌드·기존 검사와 직접 조작으로 확인하고, 실행하지 않은 확인을 완료했다고 보고하지 않는다.
