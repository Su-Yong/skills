# 데이터에 맞는 Block 선택

새 화면의 레이아웃을 고르거나 기존 화면을 재구성할 때 읽는다. 색상·폰트는 [스타일 시스템](style-system.md), 페이지 관계는 [레이아웃](layout.md), 실제 UI 구현은 [컴포넌트](components.md)를 따른다.

## 먼저 확인할 데이터

Block을 검색하기 전에 데이터의 단위, 반복 방식, 필드 관계와 주요 행동을 정리한다. 단일 객체인지 목록인지, 항목끼리 비교해야 하는지, 읽기와 편집 중 무엇이 중심인지가 선택 기준이다. 데이터의 종류가 비슷하다는 이유만으로 Block을 확정하지 않는다.

목록의 각 항목을 식별하는 필드, 나란히 비교해야 하는 필드, 상세에서 확인할 보조 정보를 구분한다. 데이터 모델에 정의한 필드를 모두 목록에 노출할 필요는 없다. 여러 필드를 한 셀에 쌓아 행 높이가 커지면 항목 비교가 쉬워지는지 다시 판단한다. 작은 화면에서 필요한 합침을 넓은 화면에도 그대로 적용하지 않는다. 화면을 채우기 위한 새 데이터나 기능을 만들지 않는다.

## 본문뿐 아니라 전체 화면의 영역을 대응한다

페이지에 실제로 필요한 Navbar·Sidebar·페이지 제목·검색/작업 도구 모음·본문·Footer를 먼저 식별한다. 필요하지 않은 영역을 의무적으로 만들지 않는다. **Navbar는 본문 밖의 임의 구현 영역이 아니라 별도로 Block을 선택해야 하는 UI 영역**이다.

| 영역 | 선택 기준 | 참고 범위 |
| --- | --- | --- |
| Navbar | 브랜드, 전역 탐색, 현재 위치, 테마 등 필요한 공통 조작 | [Navbar Block 목록](https://www.shadcn.io/navbar-block)에서 역할이 맞는 후보의 실제 프리뷰 확인 |
| Sidebar | 데이터 종류와 하위 페이지의 실제 계층 | 사이드바·앱 탐색용 Block의 펼침·현재 위치·작은 화면 동작 |
| 제목과 작업 도구 모음 | 현재 페이지의 목적과 주요 행동 | 본문 Block에 포함되어 있으면 그 구성을 사용하고, 없을 때 별도 후보 검토 |
| 검색·본문 | 표시할 데이터 형식과 비교·입력·읽기 작업 | 표·목록·폼 등 데이터에 맞는 Block |
| Footer | 실제로 필요한 공통 정보와 탐색 | 필요한 경우에만 Footer 후보 검토 |

하나의 Block이 여러 영역을 이미 포함하면 중복 선택하지 않는다. 공통 Navbar·Sidebar는 한 번 선택한 구성과 동작을 여러 페이지에서 재사용한다. 표를 참고했다는 이유로 임의로 만든 헤더까지 출처가 확인된 것으로 취급하지 않는다.

작업 설명에는 실제 영역, 선택한 Block, 유지·제거·변경 이유를 짧게 대응시킨다. 적합한 후보를 확인하지 못한 영역은 대체 구성이라는 사실을 해당 영역에 명시한다. 화면의 모든 부분을 억지로 카드나 독립된 Block으로 쪼개지는 않는다.

| 데이터와 작업 | 먼저 살펴볼 배치 | 선택 시 확인할 점 |
| --- | --- | --- |
| 같은 필드를 가진 여러 항목 비교 | 검색 영역과 표 | 비교할 열이 맞는지, 긴 셀과 작은 화면을 처리할 수 있는지 |
| 제목·상태 중심의 짧은 항목 | 간결한 반복 목록 | 각 행에서 필요한 행동만 드러나는지 |
| 하나의 객체에 속한 여러 필드 | 제목과 관련 필드 묶음 | 읽는 순서와 편집 순서가 데이터 관계에 맞는지 |
| 한 객체에 소속된 다른 데이터 목록 | 별도 상세 페이지 안의 관련 목록 | 주 객체와 하위 목록의 관계가 분명한지 |
| 이미지 자체가 중요한 항목 | 이미지와 핵심 속성의 그리드 | 실제 이미지 데이터가 있는지, 카드마다 불필요한 설명이 붙지 않는지 |
| 실제 수치의 추이·분포 비교 | 요구된 비교에 맞는 차트 영역 | 표보다 차트가 판단에 도움이 되는지, 없는 지표를 만들고 있지 않은지 |

## 현재 카탈로그에서 후보 찾기

새로 Block을 선택할 때는 [shadcn.io Blocks](https://www.shadcn.io/blocks)의 현재 카탈로그에서 시작한다. 정의한 데이터와 필요한 화면 영역에 맞는 카테고리·검색 결과를 살펴 후보를 찾는다. 카탈로그 탐색이 어려우면 `site:shadcn.io/blocks`에 해당 영역과 작업을 설명하는 검색어를 조합하고, 실제 확인한 링크를 연다.

과거 테스트·다른 프로젝트·대화에서 사용한 Block만 다시 열어 보고 탐색을 마치지 않는다. 현재 탐색에서 찾은 후보가 여러 개면 데이터 관계·주요 행동·탐색 깊이·반응형 배치가 잘 맞는 것을 선택한다. 이전에 사용한 Block도 이 기준에 가장 잘 맞으면 다시 사용할 수 있으며, 다양성을 위해 억지로 다른 Block을 고를 필요는 없다.

같은 프로젝트에서 이미 검토한 공통 영역은 재사용한다. 색상만 바꾸는 요청처럼 레이아웃을 다시 고를 필요가 없는 작업에서는 Block 탐색을 반복하지 않는다.

선택 이유에는 어떤 카테고리나 검색 조건에서 후보를 찾았고, 현재 데이터와 영역에 어떤 구조가 맞는지 짧게 남긴다. 원본의 필터·배지·계정 메뉴·가입 버튼 등은 실제 서비스에 필요한 것만 남기고, 동작 구현은 공식 shadcn/ui와 Lucide를 사용한다.

## 실제 미리보기에서 선택 근거 확인

사용할 후보는 브라우저에서 실제 미리보기를 열어 확인한다. 이름·설명·스크린샷 하나만으로 조작이나 반응형 동작까지 확인했다고 판단하지 않는다. 후보 개수를 고정하거나 개수를 채우기 위해 관련 없는 Block을 추가 조사하지 않는다.

| 관찰할 부분 | 대상 화면과 비교할 내용 |
| --- | --- |
| 데이터 단위와 필드 | 한 행·카드가 표현하는 객체, 식별 정보, 비교할 열, 보조 정보의 우선순위가 맞는지 |
| 제목과 툴바 | 제목·검색·필터·주요 행동이 어느 영역에 모여 있는지, 중복 안내나 불필요한 분리 영역이 생기지 않는지 |
| 컨트롤의 의미 | 실제로 열고 조작했을 때 값을 선택하는지, 행동을 실행하는지, 표시 설정을 바꾸는지 |
| 목록의 밀도 | 필드 수·줄 수·정렬·열 너비·행 높이가 항목을 찾고 비교하는 작업에 맞는지 |
| 작은 화면 | 어떤 열과 행동이 재배치되는지, 정보 합침이 어느 화면 크기에서 필요한지 |
| 필요한 상태 | 검색 결과·빈 상태·선택 상태 등 대상 작업에 필요한 동작을 어떻게 표현하는지 |

미리보기의 메뉴는 실제로 열어 역할을 확인한다. 예를 들어 표시할 열을 켜고 끄는 설정을 검색 대상 필드 하나를 고르는 `Select`로 바꾸면 다른 기능이 된다. 모양만 비슷한 컨트롤을 선택하지 말고 [컴포넌트 기준](components.md)에 따라 의미에 맞는 실제 shadcn/ui 구성을 사용한다. 대상 화면에 필요하지 않은 기능이라면 다른 기능으로 변형해 남기는 대신 제거한다.

## 원본 구조를 대상 데이터에 대응

구현 전에 원본에서 **유지·제거·변경할 부분과 이유**를 짧게 정리한다. 작업 설명 안의 몇 줄이나 작은 표면 충분하며 별도 문서나 승인 단계를 만들지 않는다.

| 원본에서 관찰한 부분 | 대상 화면에서의 처리 | 판단 근거 |
| --- | --- | --- |
| 검색·필터와 표가 이어지는 툴바 | 필요한 검색·필터의 관계를 유지 | 같은 목록을 좁히는 작업이므로 한 흐름에서 사용 |
| 한 항목의 주 필드와 보조 필드 | 식별·비교할 필드는 목록에, 드문 정보는 상세에 배치 | 실제 사용자가 항목을 구분하고 비교하는 데 필요한 정도 |
| 대상 작업에 없는 보조 행동 | 제거 | 원본에 있다는 이유로 새 기능을 추가하지 않음 |
| 작은 화면에서 접히는 열 | 대상 데이터 길이와 핵심 필드를 보고 재배치 | 넓은 화면의 비교성과 모바일의 핵심 작업을 함께 유지 |

이 표는 대응 방법의 예시다. 관찰하지 않은 원본 구조를 실제로 확인한 내용처럼 복사하지 않는다.

핵심 정보 관계를 유지하면서 열 수·너비·순서·간격을 데이터에 맞게 조정한다. 페이지 경계와 별도 상세 페이지 원칙은 프로젝트의 데이터 설계를 따른다. 데이터가 다르다는 이유로 원본과 무관한 임의의 화면을 만들고 같은 Block을 참고했다고 설명하지 않는다.

불필요한 문구·장식·버튼은 제거한다. UI 구현은 [컴포넌트 기준](components.md)에 따라 shadcn/ui와 shadcn.io UI를 함께 살펴 실제 구현을 사용한다. Block의 레이아웃을 참고한 것과 shadcn.io 컴포넌트 코드를 사용한 것은 구분한다. 아이콘은 인지나 행동을 돕는 곳에만 Lucide로 넣는다. 이름·분류·위치 등 모든 셀에 장식 아이콘을 붙이지 않는다. 원본의 아이콘이 다른 라이브러리라면 필요한 역할만 Lucide로 옮긴다.

중첩 카드는 기본적으로 피한다. 실제로 확인한 원본 Block이 카드 안에 카드를 사용하는 경우에는 그 관계를 필요한 범위에서 유지할 수 있다. 이때 원본에서 확인한 구조와 대상 데이터의 대응을 설명할 수 있어야 한다. 다른 Block 어딘가에 있을 것이라는 추측을 허용 근거로 삼지 않는다.

레이아웃 참고는 원본 코드의 구매·설치, 동일한 데이터, 정확한 복제를 요구하지 않는다. 장식적 움직임이나 화면 고정 높이 역시 대상 작업에 맞는지 판단하고 조건 없이 가져오지 않는다.

## 후보가 없거나 접근할 수 없을 때

가까운 후보의 미리보기를 확인할 수 있으면 핵심 구조를 유지해 조정한다. 미리보기를 열 수 없고 설명만 확인했다면 **설명만 참고했으며 실제 배치·동작은 확인하지 못했다**고 구분한다. 이 경우 설명은 방향을 정하는 자료로만 사용하고, 정의한 데이터에 맞는 단순한 shadcn/ui 기본 컴포넌트 구성으로 진행한다. 원본 레이아웃을 확인했거나 충실하게 반영했다고 주장하지 않는다.

사이트에 접근할 수 없거나 적합한 후보가 없는 경우도 해당 사실을 짧게 알리고 기본 컴포넌트로 구성한다. 후보가 없다는 판단은 현재 카탈로그의 관련 카테고리나 검색 결과를 살핀 뒤에 한다. 익숙한 Block 몇 개가 맞지 않는다는 이유만으로 후보가 없다고 결론 내리지 않는다. 확인하지 않은 Block URL을 만들거나, 도구로 확인하지 않은 접근 실패를 사실처럼 표현하지 않는다.

대체 구현에서도 [컴포넌트 기준](components.md)을 지킨다. Block 미리보기 접근 실패만으로 별도의 UI 카탈로그 탐색까지 생략하지 않는다. Select 등을 기본 HTML 컨트롤로 바꾸거나, 디자인 참고를 위한 별도 테스트 앱을 만들지 않는다.

## 원본과 결과를 실제 화면에서 비교

구현 후에는 확인한 원본 미리보기와 실제 결과를 비슷한 화면 크기에서 비교한다. 데이터가 달라 생긴 의도적인 변경은 위의 대응 근거로 설명하고, 의도 없이 바뀐 정보 우선순위·툴바 역할·행 밀도·반응형 배치는 수정한다.

- 목록에서 항목을 식별하고 비교하기 쉬운지, 모든 메타데이터를 한 셀에 쌓아 불필요하게 큰 행이 되지 않았는지 확인한다.
- 검색·필터·표시 설정·주요 행동이 각각 의도한 역할로 작동하는지 실제로 조작한다. 메뉴와 팝오버는 열린 상태까지 확인한다.
- 데스크톱과 모바일에서 정보와 행동의 우선순위가 유지되는지 확인한다. 불필요한 제목·레이블·아이콘을 제거한 뒤에도 사용법을 이해할 수 있어야 한다.
- Navbar·Sidebar 등 공통 영역부터 본문까지 영역별 참고가 빠지지 않았는지 확인한다. 여러 Block을 조합해도 바깥 폭·정렬·테마·컴포넌트 기본 디자인이 일관되어야 한다.

shadcn/ui import나 빌드 성공만으로 적합한 Block을 선택하거나 그 구조를 제대로 반영했다고 판단하지 않는다. 실제 확인한 원본 링크, 유지·제거·변경의 핵심 이유, 결과 화면에서 확인한 내용과 미확인 범위를 작업 결과에 짧게 남긴다. 구현 참고 출처를 사용자 화면에 표시할 필요는 없다.

새 테스트 파일·테스트 모음·검증 스크립트나 별도 검수 앱은 만들지 않는다. 실제 작업 중인 화면에서 확인한다.
