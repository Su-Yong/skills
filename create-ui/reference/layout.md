# 페이지 계층과 레이아웃

페이지를 나누거나 메뉴·화면 배치를 바꿀 때 읽는다. 먼저 데이터 포맷을 정의하고, 그 결과에 따라 페이지를 설계한다. Block 선택은 [Block 참고](blocks.md), 실제 간격과 타이포그래피 값은 [스타일 시스템](style-system.md)을 사용한다.

## 페이지를 나누는 기준

데이터 종류별 분할을 기본으로 삼는다. 같은 종류의 데이터는 목록에서 탐색하고, 상세가 필요한 항목은 별도 상세 페이지에서 읽거나 수정한다. 단순한 체크 목록처럼 독립된 상세 내용이 없는 경우까지 불필요한 상세 페이지를 만들지 않는다.

| 페이지 역할 | 포함할 내용 | 제외하거나 별도 접근으로 둘 내용 |
| --- | --- | --- |
| 목록 | 항목 구분과 비교에 필요한 필드, 실제로 필요한 검색·필터와 주요 행동 | 모든 메타데이터, 긴 본문, 사용 빈도가 낮은 부가 행동 |
| 상세 | 해당 객체를 이해하고 작업하는 데 필요한 필드와 관련 데이터 | 다른 종류의 데이터 전체 목록, 관계없는 요약·홍보 영역 |
| 입력·편집 | 현재 작업에 필요한 필드, 명시적인 저장과 오류 안내 | 중복 설명, 입력과 무관한 통계·설정 |
| 설정 | 같은 목적의 설정 묶음과 상태 | 깊이를 늘리기 위한 중간 메뉴 |

페이지별 데이터·행동·경로를 짧게 정리한 뒤 구현한다. 별도 기획서나 단계별 승인을 만드는 것은 기본 요구사항이 아니다.

데이터 포맷은 사용할 수 있는 정보의 구조이며, 모든 필드를 목록에 표시하라는 뜻이 아니다. 목록에서 식별·비교·주요 행동에 필요한 정보와 상세에서만 필요한 정보를 나눈다. 각 항목에 여러 메타데이터 문단을 쌓아 행이 커지면 더 낮은 우선순위의 정보를 상세로 옮기거나 비교 가능한 별도 열로 정리한다.

## 깊이와 상하 관계

동선 단축은 페이지의 의미 있는 계층을 설계하는 일이다. URL 문자열의 구간 수나 클릭 횟수만 줄이려고 관련 없는 데이터를 합치지 않는다. 필요 없는 경유 페이지와 중복 메뉴를 제거하되 데이터의 소속 관계는 유지한다.

예를 들어 장비는 `/equipment` 목록에서 찾고 `/equipment/:equipmentId` 상세로 이동할 수 있다. 사용자가 목록으로 돌아오면 검색·필터 조건을 보존한다. 프로젝트와 작업처럼 소속 관계가 중요한 데이터는 그 관계를 이해할 수 있는 탐색 경로를 제공하되, 빈 중간 페이지를 거치게 하지 않는다.

- 주 상세는 별도 페이지로 유지한다. 상세 패널·드로어를 기본으로 삼아 동선 단축을 대신하지 않는다.
- 보조 설명을 여는 팝오버나 짧은 확인 다이얼로그는 주 상세 페이지와 역할을 구분한다.
- 기존 프로젝트의 경로를 바꾸면 직접 접근·새로고침·뒤로 가기와 기존 링크의 영향을 확인한다.
- 검색·필터 등의 상태는 프로젝트의 라우터와 상태 관리 방식을 이용해 보존한다. 여러 곳에 서로 다른 값을 저장하지 않는다.

## 메뉴와 전체 화면 틀

페이지가 적고 하위 관계가 단순하면 상단 메뉴를 사용한다. 관리 대상과 하위 항목이 많으면 사이드바를 검토한다. 메뉴 틀을 먼저 정하고 데이터를 맞추지 않는다.

상단에는 현재 페이지를 구분할 수 있는 제목과 실제로 필요한 주요 행동을 둔다. 페이지마다 소개 문장·통계 카드·장식 배너를 반복하지 않는다. 제목만으로 이해할 수 있으면 설명을 추가하지 않는다. 선택 상태와 오류는 색상 이외에도 접근 가능한 정보로 표현한다.

Navbar·Sidebar도 [Block 선택 기준](blocks.md)의 대상이다. 필요한 공통 탐색 영역을 먼저 식별하고 알맞은 Block을 선택한다. 본문 표만 참고하고 상단 바는 임의로 배치하지 않는다. 선택한 공통 영역은 페이지 사이에서 재사용하고, 여러 Block을 조합할 때 바깥 폭·정렬·컴포넌트 기본 디자인을 맞춘다.

검색·필터는 관련 목록과 하나의 도구 모음 흐름으로 묶는다. 원본 Block이 표와 붙어 있는 간결한 도구 모음을 사용하는데 큰 검색 구역을 따로 만드는 식으로 정보 관계를 무심코 바꾸지 않는다. 테마 같은 전역 표시 설정은 주요 데이터 작업과 시각적 비중을 구분한다.

## 정보 밀도와 가로 폭

- 여러 항목의 비교가 핵심인 표·목록은 읽기와 조작이 가능한 범위에서 조밀하게 배치한다.
- 긴 본문과 입력 폼은 내용 묶음 사이에 여유를 둔다. 같은 역할의 간격은 스타일 토큰을 일관되게 사용한다.
- 표는 필요한 열의 수와 길이를 고려하고, 본문·폼은 읽기와 입력에 적절한 폭을 선택한다. 모든 페이지에 하나의 최대 폭을 강제하지 않는다.
- 페이지의 묶음은 여백과 필요한 구분으로 표현한다. 모든 정보를 카드로 감싸거나 새 장식 그림자를 추가하지 않으며, shadcn/ui 컴포넌트의 기본 그림자·경계선은 그대로 유지한다.
- 카드 내부의 정보 묶음을 다시 카드로 감싸는 중첩 카드는 기본적으로 피한다. 내부 구분은 일반 영역·여백·구분선을 먼저 사용한다. 실제 참고한 shadcn.io Block의 프리뷰에 중첩 카드가 있는 경우에만 그 정보 관계를 유지하는 범위에서 허용한다. 원본을 확인하지 않고 관행적으로 중첩하지 않는다.
- 긴 텍스트 때문에 글자 크기를 임의로 줄이거나, 핵심 정보를 말줄임표로만 감추지 않는다. 줄바꿈 또는 필요한 상세 접근을 제공한다.

## 작은 화면

핵심 조회·이동·입력·저장 작업을 유지하면서 배치를 바꾼다. 열이 많은 표는 핵심 식별 정보와 관련 필드를 같은 항목 안에 재배치하거나 의미 있는 스크롤 영역을 사용한다. 화면 전체가 가로로 넘치거나 주요 행동이 사라지지 않게 한다.

작은 화면에서 어떤 열을 숨길지는 데이터의 우선순위로 정한다. 단순히 왼쪽부터 몇 개를 남기거나 중요하지 않은 분류를 유지한 채 핵심 위치·상태를 여러 줄로 밀어 넣지 않는다. 같은 항목으로 접을 때에도 정보 순서를 유지하고 원본 프리뷰와 비슷한 폭에서 비교한다.

상세는 작은 화면에서도 독립 페이지로 유지한다. 버튼과 입력창은 터치와 키보드로 조작할 수 있는 영역을 확보한다. 실제 데이터 길이를 보고 화면이 깨지는 지점에 맞춰 반응형 구간을 정하며, 사용자의 글자 확대를 막지 않는다.

## 상태와 확인

빈 목록·로딩·오류에서 필요한 다음 행동만 안내한다. 저장은 명시적 버튼을 기본으로 하고, 저장 중 중복 제출을 막으며 실패하면 입력을 보존한다. 주요 화면에서 긴 내용과 작은 화면, 테마 전환, 키보드 접근을 직접 확인한다.

새 테스트 파일·테스트 스위트·검증 스크립트나 별도 검수 앱은 만들지 않는다. 실제 수정한 화면에서 확인하고 확인하지 못한 범위를 결과에 남긴다.
