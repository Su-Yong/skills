# audit

현재 프로젝트가 `create-ui` 규칙에 맞는지 검사하고, 확인한 문제를 코드와 화면에서 수정한 뒤 재검증한다. **검사·수정·재확인이 기본 동작**이며 문제 목록이나 개선 제안만 남기고 끝내지 않는다. 공통 원칙과 적용 조건은 [스킬 진입점](../../SKILL.md)을 따른다.

## 호출과 검사 범위

```text
$create-ui audit
$create-ui audit text
$create-ui audit layout
$create-ui audit ui
$create-ui audit page
$create-ui audit data
```

| 요청 | 검사하고 수정할 범위 | 읽을 기준 |
| --- | --- | --- |
| `audit text` | 모든 페이지와 주요 상태의 텍스트 내용·필요성·중복·대체 가능성·노출 시점·최소 표현 | [텍스트 필요성 검수](../layout.md#텍스트-필요성-검수) |
| `audit layout`, `audit ui` | 필요한 영역별 Block의 적합성과 실제 반영, shadcn/ui·shadcn.io 컴포넌트의 실제 사용과 누락, 배치·반응형·조작 | [Block](../blocks.md), [컴포넌트](../components.md), [레이아웃](../layout.md), 관련 [스타일](../style-system.md) |
| `audit page`, `audit data` | 실제 데이터 포맷·관계에 맞는 페이지 분할, 페이지별 데이터·행동·경로, 탐색 계층과 웹 UI의 작업 흐름 | [데이터에서 페이지로](../../SKILL.md#데이터에서-페이지로), [페이지 계층과 레이아웃](../layout.md) |
| `audit` | 위 범위 모두와 스타일·테마·접근성·상태 처리·서버·저장소 등 현재 프로젝트에 적용되는 모든 스킬 규칙 | 스킬 진입점과 공통 참고 문서 전체 |

`layout`과 `ui`는 같은 검사 범위이며 어느 쪽으로 호출해도 Block과 컴포넌트를 모두 확인한다. `page`와 `data`도 같은 범위이며 페이지 구성과 데이터·작업 흐름을 함께 확인한다.

별도 화면 범위를 지정하지 않으면 현재 프로젝트의 모든 페이지가 대상이다. 특정 페이지나 경로를 지정하면 그 범위와 수정에 필요한 공통 사용처를 확인한다. 알 수 없는 검사 주제나 모호한 대상은 영향받는 범위만 질문하며, 임의로 전체 검사로 확대하지 않는다. 웹 프로젝트가 없으면 검사할 대상이 없음을 알리고 새 앱을 생성하지 않는다.

## 검사에서 수정까지

1. 현재 변경, 실행 명령, 라우트·메뉴·페이지, 공통 컴포넌트와 실제 데이터 소스를 확인한다. 대상 페이지와 주요 상태를 짧게 정리해 첫 화면이나 일부 예제만 검사하고 전체 검사로 보고하지 않는다.
2. 코드와 실제 앱을 함께 살펴 각 문제에 해당 규칙·위치·관찰 근거를 연결한다. 기존 사용자의 명시적인 선택과 허용된 예외를 보존하고, 기본값과 다르다는 이유만으로 위반이라고 판단하지 않는다.
3. 근거가 확인된 문제를 현재 프로젝트에서 직접 수정한다. 같은 문제가 공통 컴포넌트나 문구 정의에서 반복되면 공유된 원인을 고치고 모든 사용처를 확인한다. 필요한 연결 수정까지 완료하되 관련 없는 기능을 추가하거나 전면 재작성하지 않는다.
4. 기존 빌드·관련 검사와 실제 브라우저에서 수정 결과를 확인한다. 변경된 페이지와 주요 상태, 공통 수정의 영향을 받는 화면을 다시 검수하고 발견된 회귀를 고친다. 테스트 파일·검증 스크립트·별도 검수 앱을 새로 만들지 않는다.
5. 검사 범위의 각 항목을 수정 후 확인·문제 없음·미해결·미검수·적용 대상 아님으로 구분한다. 남은 문제와 확인할 수 없는 부분을 드러내고, 확인된 범위까지만 완료했다고 보고한다.

수정은 명령에 포함되어 있으므로 일반적인 문구·배치·컴포넌트·페이지 수정마다 승인을 다시 묻지 않는다. 실제 데이터나 사용 목적이 불명확해 동작의 의미를 바꿀 수 있는 부분만 질문하고, 독립적인 검사와 수정은 계속한다.

## text

- [텍스트 필요성 검수](../layout.md#텍스트-필요성-검수)를 모든 대상 페이지에 적용한다. 제목·본문·레이블·플레이스홀더·버튼·배지·보조 문구뿐 아니라 메뉴·펼침 영역·로딩·빈 상태·오류·저장 결과도 확인한다. 같은 문구를 공유하는 여러 화면의 맥락 차이도 살핀다.
- 실제 데이터·동작과 맞지 않는 표현, 불필요한 문구, 중복 안내를 수정한다. 기존 제목·레이블·링크를 정확하게 고치면 설명을 없앨 수 있는지 확인하고, 필요한 레이블·오류 피드백·해석 조건은 보존한다.
- 사용자가 제공한 본문·인용·브랜드 문구와 저장 데이터의 의미를 임의로 바꾸지 않는다. 모든 텍스트를 검사한다는 이유로 콘텐츠나 DB의 값을 일괄 삭제·변경하지 않는다. 문구 수정만으로 해결되는 문제를 페이지 재설계로 확대하지 않는다.

## layout / ui

- [Block 기준](../blocks.md)에 따라 Navbar·Sidebar·제목·도구 모음·본문 등 실제 필요한 영역을 확인한다. 선택한 Block의 실제 프리뷰와 현재 화면을 비교하고, 대응이 없거나 데이터·작업에 맞지 않으면 현재 카탈로그에서 적합한 후보를 찾아 배치를 수정한다. 공통 영역은 한 번 검토해 재사용한다.
- [컴포넌트 실제 사용과 누락 검수](../components.md#실제-사용과-누락-검수)에 따라 출처·구현 파일·호출 화면·실제 동작을 추적한다. 이름만 같은 자체 구현, 미사용 import, 기본 HTML로의 우회, 적합한 shadcn.io UI의 조사 누락을 확인하고 수정한다. Block 참고와 UI 코드 사용을 혼동하지 않는다.
- 데이터 연결·선택·입력·저장·키보드·포커스·오버레이, 데스크톱·모바일과 라이트·다크에서 실제로 동작하는지 확인한다. 불필요한 중첩 카드·장식과 원본 구조를 해치는 재정의도 관련 기준에 따라 수정한다.
- 사이트·코드 접근 실패나 호환성 문제는 실제 확인한 근거와 대체 이유를 남긴다. 확인하지 못한 원본을 사용했다고 보고하거나, 이미 충분한 컴포넌트를 사용 개수 때문에 교체하지 않는다.

## page / data

- 타입·API 응답·실제 데이터·사용처에서 데이터의 종류·필드·관계·상태와 주요 행동을 확인한다. 명세가 없으면 기존 구현의 근거로 필요한 포맷을 정리하고, 추측한 새 모델에 기존 데이터를 억지로 맞추지 않는다.
- 데이터 종류별 페이지 구분, 목록·별도 상세·입력의 역할, 정보의 우선순위, 깊이와 상하 관계를 확인한다. 관계없는 데이터의 혼합, 불필요한 경유 페이지, 중복 메뉴, 누락된 데이터·행동 연결을 수정한다. 별도 상세 내용이 없는 단순 목록에 빈 상세 페이지를 만들지 않는다.
- 사용자의 조회·검색·필터·상세·수정·저장·목록 복귀 흐름을 따라가며 단절과 불필요한 이동을 고친다. 경로를 바꾸면 메뉴·내부 링크·직접 접근·새로고침·뒤로 가기와 검색·필터 맥락을 함께 보존하고 재검증한다.
- API·저장 데이터·인증·권한 계약을 유지한다. `data`는 데이터와 페이지의 대응을 검사하는 범위이며 DB 교체·스키마 재설계·데이터 초기화를 자동으로 실행하는 명령이 아니다. 페이지 수정으로 생기는 UI에도 공통 Block·컴포넌트·텍스트 규칙을 적용한다.

## 전체 audit

데이터·페이지 흐름, Block·컴포넌트, 텍스트 순으로 확인해 앞선 구조 수정이 이후 검수에 반영되도록 한다. [스타일 체계](../style-system.md)의 기본 디자인·Pretendard·팔레트·테마, 접근성·반응형·움직임 줄이기, 빈 상태·오류·저장 실패, [서버와 저장소](../../SKILL.md#서버와-저장소)와 실행 설정도 적용 조건에 따라 검사하고 수정한다.

현재 프로젝트에 필요 없는 서버·DB·화면을 검사 항목을 채우기 위해 추가하지 않는다. 기술 스택이 다르다는 이유만으로 전체 마이그레이션을 실행하지 않는다. 기존 서버 교체가 실제로 필요하면 스킬의 서버 유지·교체 선택 규칙을 따르고 이미 받은 선택을 존중한다. 설치된 스킬·다른 프로젝트·외부 서비스는 변경하지 않는다.

## 결과 보고

검사한 범위와 페이지·상태, 발견해 수정한 문제와 파일, 재검증 결과, 남은 문제·미검수 항목을 짧게 보고한다. Block·컴포넌트 수정에는 실제 출처와 적용 근거를 연결한다. 수정할 문제가 없으면 수행한 검사 근거와 함께 알리고 불필요한 변경을 만들지 않는다.

브라우저·인증·외부 원본에 접근할 수 없으면 가능한 코드 검토와 근거 있는 수정은 계속하되 실제 화면·동작 확인은 미검수로 남긴다. 빌드 성공이나 일부 페이지 확인만으로 전체 audit 통과를 선언하지 않는다.
