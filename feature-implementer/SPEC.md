# Feature Implementer 스킬 기획서

작성일: 2026-09-07 / 개정: 4

이 문서는 Feature Implementer의 단독 실행 계약을 정의합니다. 작성 주체나 도구에 관계없이 충분히 구체적인 계획과 구현 요청을 입력받으며, 다른 스킬의 설치나 실행을 요구하지 않습니다. 예시의 경로, 명령과 검증 결과는 설명용이며 이번 작업의 실행 결과가 아닙니다.

개정 4는 사용자가 지정한 **기획 충실성, 구현 속도, 사람이 읽기 쉬운 코드**를 중심으로 정의한 실행 계약입니다. [SKILL.md](SKILL.md), [실행 프로토콜](references/execution-protocol.md)과 모델별 보정은 이 계약을 공통 기준으로 사용합니다. 파일 구조와 책임은 24절에 정리합니다.

## 1. 문서 개요

### 1.1 제품명

**Feature Implementer**

### 1.2 한 줄 정의

작성 주체와 형식에 관계없이 기획 문서를 읽고, **기획에 충실한 기능을 적극적인 서브 에이전트 병렬 작업으로 빠르게 구현하며, 사람이 읽기 쉬운 코드로 완성하는 독립적인 구현 실행 스킬**이다.

사람이 작성한 계획, 기존 설계 문서와 다른 도구가 만든 Markdown을 동일한 입력 계약으로 다룬다. 스킬 자체가 계획 접수부터 변경, 통합과 검증 결과 보고까지 책임진다.

### 1.3 핵심 가치

다음 세 가지 핵심 가치로 작업 분해, 구현, 통합과 완료 판단을 설계한다.

1. **기획 충실성 — Plan Fidelity**
   기획서가 요구하는 동작, 범위, 제약과 실제 구현이 일치해야 한다. 요구사항을 빠뜨리거나 임의로 바꾸지 않고, 각 인수 기준을 실제 코드와 동작 증거로 확인한다.

2. **구현 속도 — Fast Implementation**
   서브 에이전트를 적극적으로 활용해 병렬로 진행할 수 있는 기능 작업을 최대한 동시에 구현한다. `A → B → C`처럼 실행 순서가 있는 기능도 A의 출력과 B의 입력, B의 출력과 C의 입력 계약을 먼저 맞추고 각 구현을 병렬로 배정한다. 실제 선행 결과가 있어야 하는 통합과 실행 검증은 필요한 순서를 지킨다.

3. **사람이 읽기 쉬운 코드 — Human-Readable Code**
   비슷한 역할의 코드는 이름, 구조와 처리 흐름의 모양을 맞추고, 같은 관심사의 코드를 가까이 묶는다. 가독성은 코드 자체로 확보한다. 주석은 hacky한 우회나 tricky한 구현에서 코드만으로 드러나지 않는 이유와 제약을 설명할 때만 작성한다.

속도는 기획 충실성과 가독성을 충족하면서 전체 완료까지 걸리는 시간을 줄이는 방향으로 최적화한다. 인수 기준을 생략하거나 읽기 어려운 구현을 남겨 속도를 높였다고 평가하지 않는다.

기존의 사용자 작업 보존, 증거 기반 완료 판단과 다른 스킬에 의존하지 않는 실행은 세 가치를 뒷받침하는 필수 실행 조건으로 유지한다. 계획이 요구하는 여러 파일의 수정이나 구조 변경도 구현 범위에 포함하며, 모든 변경은 요구사항 또는 필요한 통합과 검증에 연결한다.

### 1.4 핵심 가치와 실행 계약의 연결

| 핵심 가치 | 실행에서 책임질 내용 | 연결 목표 | 주요 평가 기준 |
| --- | --- | --- | --- |
| 기획 충실성 | 요구사항과 계약 추출, 범위 유지, 구현과 인수 기준의 대조 | G-001, G-002, G-003, G-005 | S-001, S-002, S-003, S-005, S-006, QR-001, QR-004 |
| 구현 속도 | 입출력 계약 선합의, 적극적 병렬 배정, 대기와 통합 재작업 감소 | G-006 | S-008, QR-005, QR-009 |
| 사람이 읽기 쉬운 코드 | 유사한 코드 형태 통일, 관심사별 배치, 예외적인 주석 사용 | G-008 | S-010, QR-010, QR-011 |

## 2. 배경 및 문제 정의

기능 기획서를 코드로 옮기는 에이전트는 일반적인 코딩 에이전트보다 더 엄격한 제약이 필요하다.

단순히 “이 기능 구현해”라는 요청을 처리하면 다음과 같은 문제가 발생하기 쉽다.

* 계획서에 없는 동작을 에이전트가 자의적으로 결정한다.
* 기능 구현을 빌미로 주변 코드를 리팩터링한다.
* 이미 존재하는 사용자 변경을 덮어쓴다.
* 여러 에이전트가 같은 파일을 동시에 수정한다.
* 병렬로 구현할 수 있는 기능도 주 에이전트가 하나씩 처리한다.
* 실행 시 데이터 의존성을 구현 착수의 의존성으로 해석해 선행 구현 전체를 기다린다.
* 입출력 계약을 맞추지 않고 병렬화해 통합 시 서로 다른 가정을 다시 수정한다.
* 같은 역할의 코드가 제각각 작성되고 관련 코드가 흩어져 읽는 사람이 흐름을 재구성해야 한다.
* 구조를 정리하는 대신 동작을 풀어 쓴 주석을 늘려 가독성이 좋아졌다고 판단한다.
* 일부 구현이 실패했음에도 전체 작업을 성공으로 보고한다.
* 기존부터 실패하던 테스트와 새로 발생한 회귀를 구분하지 않는다.
* 충분히 구체적인 계획도 특정 스킬이나 생성기를 거쳐야만 실행할 수 있게 만든다.
* 구현 요청을 커밋, Push, PR, 배포까지의 권한으로 확대 해석한다.

Feature Implementer는 이러한 문제를 막기 위한 **계획 → 코드 실행 계층**이다.

실행 흐름은 세 가지 핵심 가치를 실제 작업과 연결한다.

**요구사항 추적 → 저장소와 소유권 확인 → 경계 계약 합의 → 최대한 병렬 구현 → 코드 형태와 관심사 정돈 → 실제 구현 통합과 검증 → 증거 기반 보고**

## 3. 목표

### 3.1 주요 목표

### G-001. 구현 준비된 계획을 실제 저장소 변경으로 전환

기획서의 요구사항을 분석하고 각 요구사항을 실제 코드, 설정, 테스트 등의 변경 대상으로 변환한다.

### G-002. 계획서와 구현 사이의 추적성 유지

각 요구사항이 다음 정보와 연결되어야 한다.

`계획 요구사항 → 수정 대상 → 구현 변경 → 검증 방법 → 최종 증거`

문서에 `R-*`, `UD-*`, `SF-*`, `AR-*`, `OI-*`, `RK-*`처럼 요구사항과 근거를 구분하는 ID가 존재한다면 원래 의미를 확인하고 그대로 활용한다.

ID와 원장이 없는 일반 Markdown도 동일하게 처리한다. 작성자나 생성 도구와 관계없이 필요한 계약이 충분히 구체적인지를 판단한다.

### G-003. 계획 범위와 계약 준수

활성 요구사항, 비목표, 제약과 인수 기준을 구현 범위의 기준으로 삼는다. 모든 구현 변경을 해당 요구사항이나 필요한 통합 및 검증에 연결한다.

필요한 파일 수와 코드 구조는 계획의 동작과 계약에 따라 결정한다. 변경량을 줄이기 위해 요구사항을 누락하거나, 계획에 없는 정리를 별도 작업으로 추가하지 않는다.

### G-004. 사용자 작업 보호

이미 존재하는 staged/unstaged 변경은 Feature Implementer 소유가 아니라 **사용자 소유 작업**으로 취급한다.

자동 reset, revert, clean, stash, 광범위 formatting 등으로 이를 제거해서는 안 된다.

### G-005. 검증 기반 완료 판단

각 요구사항을 검증 가능한 증거와 연결한다.

구현됐지만 검증할 수 없었던 항목과 실제 검증된 항목은 반드시 구분한다.

### G-006. 계약을 먼저 맞추고 병렬 구현해 완료 시간 단축

주 에이전트가 병렬로 배정할 기능 단위를 적극적으로 찾고, 허용된 협업 도구와 가용 작업자 범위에서 최대한 동시에 진행한다. 기능 사이에 의존성이 있으면 먼저 입출력과 필요한 동작 계약을 맞춰 선행 구현 전체를 기다리지 않도록 만든다.

주 에이전트는 공유 계약, 작업 배정, 병목 해소와 통합을 책임지고, 작업자와 쓰기 범위가 겹치지 않는 구현이나 검증도 수행한다. 성과는 검증과 통합 재작업까지 포함한 전체 완료 시간으로 판단한다.

분해와 조율 비용이 더 큰 작은 단일 변경, 계약만으로 분리할 수 없는 작업, 협업 도구를 사용할 수 없는 경우에는 직접 또는 필요한 부분만 순차 수행한다.

### G-007. 독립적인 실행 관리

계획의 작성자나 생성 도구에 관계없이 입력 내용을 분석하고 요구사항, 소유권, 의존성, 통합과 검증을 자체적으로 관리한다.

다른 스킬의 설치나 선행 실행을 요구하지 않는다. 호스트의 협업 도구를 사용할 수 없더라도 주 에이전트가 안전하게 수행할 수 있는 작업은 계속 진행한다.

### G-008. 코드의 모양과 관심사로 가독성 확보

같은 역할의 구현은 저장소에서 사용하는 이름, 선언 순서, 분기와 오류 처리 형태를 일관되게 따른다. 같은 이유로 바뀌는 로직과 데이터는 가까이 배치하고, 서로 다른 관심사는 구분해 읽는 사람이 코드 사이를 오가며 동작을 복원할 필요를 줄인다.

공통 모양을 맞추기 위해 서로 다른 도메인을 억지로 추상화하거나, 관련 없는 기존 코드를 정리하지 않는다. 가독성 점검은 이번에 구현·변경한 코드와 필요한 통합 범위에서 수행한다.

주석은 hacky하거나 tricky한 구현의 비자명한 이유와 제약에만 사용한다. 일반적인 흐름은 이름과 코드 구조로 드러내며, 설명 주석의 양을 품질 기준으로 사용하지 않는다.

## 4. 비목표

Feature Implementer는 다음을 기본 기능으로 하지 않는다.

### NG-001. 제품 요구사항 기획

무엇을 만들어야 하는지 결정하는 것이 목적이 아니다.

중요한 제품/API/데이터/UX 계약이 빠져 있다면 임의로 결정하지 않는다.

### NG-002. 불필요한 리팩터링

기능 구현과 관계없는 구조 개선, 코드 정리, 파일 재배치 등은 하지 않는다.

계획이 구조 변경이나 리팩터링을 명시한 경우에는 해당 작업을 구현 범위에 포함한다. 적용되는 스타일과 호환성 제약도 계획 및 저장소 지침에서 확인한다.

### NG-003. 임의의 패키지 업그레이드

현재 요구사항에 반드시 필요하지 않은 dependency 추가 또는 업데이트를 하지 않는다.

### NG-004. 자동 Git 히스토리 작업

별도의 요청이 없다면 다음을 수행하지 않는다.

* commit
* amend
* branch 생성/변경
* rebase
* merge
* push
* Pull Request 생성 또는 수정

### NG-005. 배포 및 외부 시스템 변경

별도 승인이 없는 한 deploy, publish, 외부 tracker 수정, 메시지 전송, 서비스 설정 변경 등을 하지 않는다.

현재 스킬 역시 기본 종료 지점을 **workspace 변경 + validation**으로 한정한다.

## 5. 독립적인 실행 범위

시작점은 식별된 계획과 명확한 구현 요청이다. 계획을 작성한 도구, 특정 기획 스킬의 완료 상태와 별도 코딩 원칙 스킬은 설치 조건이 아니다.

```text
계획 문서 + 구현 요청 + 기존 저장소
    ↓
계획 전체 접수와 작업 시작 상태 확인
    ↓
요구사항 → 변경 대상 → 검증 근거 연결
    ↓
기능 경계의 입출력 계약과 쓰기 소유권 확정
    ↓
가능한 기능 작업을 서브 에이전트에 병렬 배정
    ↓
읽기 쉬운 코드 구현, 실제 구현 통합과 인수 기준 검증
    ↓
요구사항별 상태를 담은 하나의 보고서
```

“이 계획을 검토해 줘”와 “이 계획대로 구현해 줘”는 서로 다른 요청이다. 전자는 편집 권한을 만들지 않으며, 후자는 계획 범위의 조사, 작업 공간 수정과 비례적인 검증을 허용한다.

계획에 남은 미정 계약은 이 스킬이 영향받는 요구사항에 연결해 처리한다. 다른 스킬을 호출해야만 미정 상태를 표현하거나 작업을 재개할 수 있는 구조로 만들지 않는다.

### 5.1 입력 형식의 독립성

문서에 안정적인 ID와 출처 기록이 있으면 보존한다. 없으면 내부 실행용 ID를 만들어 추적한다. 호환 가능한 ID를 읽는 기능은 해당 문서를 만든 스킬에 대한 의존성이 아니다.

### 5.2 완료의 독립성

완료 결과는 실제 저장소 변경과 인수 기준의 증거로 판단한다. 별도 스킬의 검토, 커밋, PR 또는 배포를 완료 조건으로 추가하지 않는다.

## 6. Invocation 설계

### 6.1 사용 조건

다음과 같은 요청에서 사용한다.

* “이 기획서대로 구현해줘.”
* “이 feature spec을 실제 코드에 반영해줘.”
* “작성된 계획대로 기능을 완성해줘.”
* “이 계획 문서를 기준으로 구현하고 검증해줘.”

### 6.2 사용하지 않는 조건

다음 요청에서는 사용하지 않는다.

* 기획만 작성
* 기획 검토
* 코드 리뷰만 수행
* 버그 원인 분석만 수행
* 구현 가능성 조사
* 아키텍처 상담

### 6.3 암시적 호출

`agents/openai.yaml`은 다음 정책을 사용한다.

```yaml
policy:
  allow_implicit_invocation: true
```

따라서 사용자가 `$feature-implementer`라는 이름을 직접 쓰지 않더라도 기획서를 실제로 구현해 달라는 요청이라면 스킬이 선택될 수 있다.

계획서를 읽어 달라는 요청만으로는 구현을 시작하지 않는다.

## 7. 입력 계약

Feature Implementer는 다음 입력을 대상으로 한다.

### 7.1 Planning Document

가장 중요한 입력이다.

반드시 전체 문서를 먼저 읽는다.

다음 정보를 추출한다.

| 항목                  | 의미               |
| ------------------- | ---------------- |
| Requirements        | 구현해야 할 동작        |
| Acceptance Criteria | 완료 판단 기준         |
| Non-goals           | 구현하면 안 되는 것      |
| Constraints         | 기술/제품/호환성 제약     |
| Unresolved Items    | 아직 결정되지 않은 내용    |
| Risks               | 구현 시 고려해야 할 위험   |
| Provenance          | 요구사항의 근거         |
| Authorization       | 현재 실행해도 되는 작업 범위 |

문서에 stable ID가 있으면 해당 ID와 의미를 보존한다.

일반 Markdown 문서라면 동일한 의미의 내부 requirement map을 생성한다.

### 7.2 Existing Repository

구현 전에 저장소를 조사하여 다음을 확인한다.

* repository instruction
* 기존 architecture
* 관련 source
* 관련 tests
* 기존 helper/component
* coding convention
* validation command
* 기존 변경사항

### 7.3 Workspace State

Git 저장소라면 관련 staged/unstaged 변경을 확인한다.

기존 변경은 사용자 소유로 간주한다.

### 7.4 Repository Evidence

기획서에 기술적 세부사항이 부족하더라도 저장소를 안전하게 조사하여 확인할 수 있는 사실이라면 사용자에게 다시 묻지 않고 저장소 증거를 활용할 수 있다.

## 8. 핵심 실행 불변조건

Feature Implementer는 실행 방식과 관계없이 다음 규칙을 항상 유지해야 한다.

### INV-001. 전체 계획서를 읽은 후 구현한다.

부분적으로 읽고 바로 코드를 변경하지 않는다.

### INV-002. 중요한 계약을 발명하지 않는다.

제품 행동, API contract, 데이터 의미 등 구현 결과를 본질적으로 바꾸는 결정이 없다면 에이전트가 임의로 정하지 않는다.

### INV-003. 막힌 부분만 차단한다.

하나의 요구사항에 결정이 부족하다고 해서 전체 구현을 중단하지 않는다.

독립적인 안전한 요구사항은 계속 구현한다.

### INV-004. 기존 사용자 변경을 보존한다.

Feature Implementer가 만들지 않은 변경을 임의로 제거하지 않는다.

### INV-005. 변경을 활성 요구사항과 실행 계약에 연결한다.

필요한 구현과 통합 변경을 모두 수행하고, 계획에 없는 동작이나 구조 정리를 임의로 추가하지 않는다. 변경 크기 자체를 인수 기준으로 대신 사용하지 않는다.

### INV-006. 메인 에이전트가 전체 작업의 소유자다.

sub-agent를 사용하더라도 전체 요구사항, integration, 검증, 완료 판단은 primary agent가 담당한다.

### INV-007. 에이전트의 성공 보고를 증거로 간주하지 않는다.

실제 workspace diff와 검증 결과를 primary agent가 확인해야 한다.

### INV-008. 미검증 상태를 성공으로 표현하지 않는다.

구현과 검증은 별개의 단계다.

### INV-009. 구현 착수와 통합 실행의 의존성을 구분한다.

경계의 입출력과 동작 계약이 확정되고 쓰기 범위가 분리되면 생산자와 소비자의 구현을 병렬로 시작한다. 실제 선행 산출물이 필요한 통합과 검증만 대기시킨다. 제품 계약을 발명해 병렬화하지 않는다.

### INV-010. 가독성을 코드 자체로 확보한다.

같은 역할의 코드 모양을 맞추고 같은 관심사를 가까이 묶는다. 일반적인 코드 설명을 위한 주석을 추가하지 않으며, hacky하거나 tricky한 구현의 이유와 제약에 한해 주석을 작성한다.

이 불변조건은 개정 4의 공통 계약이며 `SKILL.md`와 상세 Execution Protocol에 함께 적용한다.

## 9. 전체 실행 프로세스

### Phase 1. Plan Intake

계획서를 완전히 읽는다.

각 요구사항에 대해 내부적으로 다음 관계를 만든다.

```text
Requirement
 ├─ Source / Provenance
 ├─ Constraints
 ├─ Acceptance Criteria
 ├─ Dependencies
 └─ Authorization
```

결정되지 않은 사항을 발견하면 그 영향 범위를 판단한다.

예를 들어 API endpoint 하나의 에러 응답 정책만 미정이라면 해당 API 작업만 `blocked`시키고 다른 독립 작업은 진행할 수 있다.

### Phase 2. Repository Baseline

코드를 변경하기 전 baseline을 만든다.

요구사항의 구현 대상, 작업 소유권, 의존성과 검증 근거를 확인할 수 있도록 관련 코드를 조사한다. 공유 계약이나 기존 변경의 영향이 불분명하면 필요한 범위까지 확인한다.

확인 대상은 다음과 같다.

1. repository instruction 파일
2. 관련 구현 코드
3. 관련 테스트
4. 기존 abstraction
5. Git workspace 변경
6. validation command
7. 필요 시 기존 테스트 실패 상태

여기서 중요한 목적 중 하나가 **baseline failure와 새로운 regression을 구분하는 것**이다.

## 10. Requirement-to-Evidence Map

각 Requirement마다 다음 정보를 정의한다.

```text
Requirement
→ Source / provenance
→ Required behavior and acceptance criteria
→ Target file / symbol
→ Plan constraints and non-goals
→ Implementation and integration prerequisites / boundary contracts
→ Ownership conflicts / local code patterns and concern boundaries
→ Verification evidence
```

예를 들어 다음 요구사항이 있다고 가정한다.

```text
R-012
로그인 실패 시 API가 401을 반환해야 한다.
```

Requirement-to-Evidence Map은 다음과 비슷하다.

```text
R-012

Source:
  지정한 계획의 인증 실패 응답 요구사항

Required behavior:
  invalid token → 401

Existing behavior:
  invalid token → generic 500

Plan constraints:
  오류 JSON 필드와 정상 요청 동작 유지

Target:
  src/auth/handler.ts

Test:
  tests/auth/handler.test.ts

Dependencies and ownership:
  관련 인증 계약과 기존 파일 변경을 확인한 뒤 작업 소유권 배정

Do not touch:
  login UI
  token generation

Evidence:
  targeted auth test passes
```

이 단계에서는 구현 대상, 작업 의존성과 소유권, 해당 요구사항을 충족한 것으로 판단할 근거를 정한다. 위 경로와 동작은 설명용이며 실제 저장소의 근거로 채워야 한다.

## 11. 병렬 구현을 우선하는 작업 배정

주 에이전트는 요구사항을 검증 가능한 기능 단위로 나누고 동시에 진행할 수 있는 작업을 먼저 찾는다. 이미 독립적인 작업뿐 아니라 입출력 계약을 정하면 독립적으로 구현할 수 있는 생산자·소비자 작업도 포함한다.

### 11.1 Direct Execution

분해와 조율 비용이 이점보다 큰 작은 단일 변경은 primary agent가 직접 구현할 수 있다. 협업 도구를 사용할 수 없거나, 계약을 맞춰도 분리할 수 없는 쓰기 작업 역시 직접 처리할 수 있다.

기능 사이에 호출 순서가 있다는 사실만으로 직접 또는 순차 실행을 선택하지 않는다. 병렬 구현을 선택하지 않은 단위는 실제 제약이나 비용을 실행 기록에 짧게 남긴다.

### 11.2 Delegated Execution

허용된 협업 도구와 분리 가능한 구현 단위가 있고 병렬화 이점이 있으면 내부 collaboration worker를 적극적으로 사용한다.

* 이미 독립적인 기능 작업은 겹치지 않는 write scope로 동시에 배정한다.
* 의존하는 기능은 13절에 따라 경계 계약을 먼저 맞추고 생산자와 소비자의 구현을 동시에 배정한다.
* 같은 파일의 공유 선언 등 작은 선행 편집은 한 소유자가 먼저 처리하고, 나머지 기능까지 순차 실행하지 않는다.
* 작업자가 끝나거나 계약이 준비되면 착수 가능한 다음 작업을 바로 배정한다. 관계없는 작업의 종료까지 기다리는 일괄 Wave 경계를 만들지 않는다.
* 주 에이전트는 계약과 소유권을 조율하고 실제 결과를 수시로 검토·통합한다. 병목에 있는 작업을 먼저 풀어 가용 작업자가 불필요하게 대기하지 않게 한다.

복잡하거나 위험한 부분에는 독립적인 검토를 병행할 수 있다. 작업자 수 자체를 늘리기보다 구현과 검증을 포함한 완료 시간을 줄이며, 협업 비용 때문에 직접 수행하는 예외는 해당 단위에만 적용한다.

## 12. Work Unit 모델

복수 작업 또는 worker가 필요한 경우 구현 작업을 Work Unit으로 나눈다.

Work Unit은 개념적으로 다음 정보를 가진다.

```text
ID
Goal
Linked requirements
Implementation prerequisites
Integration / validation prerequisites
Boundary contracts: inputs, outputs, observable behavior, errors
Shared contract owner and agreed revision
Exclusive write scope
Read-only context
Do not touch
Existing changes to preserve
Implementation constraints
Local code patterns and concern boundaries
Acceptance criteria
Validation commands
Expected report
```

경계 계약이 없는 단일 작업에는 불필요한 계약 문서를 만들지 않는다. 경계를 공유하는 작업자에게는 동일한 합의 내용과 저장소의 코드 형태 예시를 전달해 각자 다른 API나 구현 스타일을 만들지 않도록 한다.

특히 **Exclusive write scope**가 중요하다.

병렬 worker가 동시에 다음 대상을 수정해서는 안 된다.

* 같은 파일
* 동일한 tightly coupled symbol
* 같은 migration chain
* 동일 generated artifact
* 공유 snapshot
* 같은 핵심 type contract

읽기 범위는 겹쳐도 된다.

## 13. 입출력 계약을 먼저 맞추는 병렬 오케스트레이션

### 13.1 의존성 분류

실행 중 A의 결과를 B가 사용한다는 사실과 B의 코드를 쓰기 위해 A의 구현 완료가 필요하다는 사실을 구분한다.

| 의존성 | 처리 방식 |
| --- | --- |
| 합의한 입출력과 동작만 알면 구현할 수 있음 | 경계 계약을 먼저 확정하고 생산자와 소비자를 병렬 구현한다. |
| 공통 타입이나 같은 파일의 선언이 먼저 필요함 | 한 소유자가 최소 공유 선언을 반영한 뒤 나머지 구현을 병렬로 진행한다. |
| 실제 산출물이나 관찰 결과가 있어야 다음 결정을 할 수 있음 | 필요한 산출물을 만드는 최소 작업을 선행하고, 영향받는 작업만 기다린다. |
| 같은 파일, 생성물 또는 마이그레이션 체인을 수정함 | 겹치는 쓰기 부분을 한 소유자에게 모으거나 순차 배정한다. |
| 실제 구현끼리 연결해야 확인할 수 있음 | 구현과 검증 코드 작성은 가능한 범위에서 병렬화하고, 실제 통합 검증은 관련 구현이 준비된 뒤 실행한다. |

### 13.2 최소 경계 계약

주 에이전트가 계획과 저장소의 기존 계약을 근거로 필요한 경계만 확정하고 관련 작업자에게 같은 내용을 전달한다.

계약에는 관련되는 항목만 포함한다.

* 호출 지점과 이름, 입력·출력의 자료형과 데이터 의미
* 필수·선택 값, 빈 값과 경계 조건의 처리
* 성공·실패 동작과 오류 전달 방식
* 상태 변경, 부수 효과, 순서와 호환성 제약
* 구현 파일의 쓰기 소유권, 공유 계약의 소유자와 합의본 식별
* 실제 구현을 연결했을 때 확인할 인수 기준

이미 존재하는 타입과 인터페이스를 재사용하고, 공유 선언 수정이 필요하면 한 소유자만 반영한다. 소비자 구현에 필요한 최소 계약이 갖춰지면 배정하며 전체 내부 설계를 미리 완성하느라 착수를 늦추지 않는다.

지역적인 구현 선택은 계획과 저장소 근거로 해결한다. 빠진 제품 동작이나 중요한 API·데이터 의미를 병렬화 목적으로 임의 결정하지 않는다. 필요한 사용자 결정이 없으면 해당 경계에 의존하는 부분만 차단한다.

### 13.3 A → B → C 구현 예시

다음 예시의 기능과 계약이 기획서에서 확정되어 있다고 가정한다.

```text
실제 동작: A 데이터 조회 → B 결과 가공 → C 화면 표시

짧은 계약 정렬
  A 출력 = B 입력
  B 출력 = C 입력
  오류·빈 결과 처리와 공유 타입 소유자 확정
  필요한 공유 선언 반영
        ↓
동시 구현
  Worker A: 조회 구현   ┐
  Worker B: 가공 구현   ├ 각자 다른 쓰기 범위, 같은 합의 계약
  Worker C: 화면 구현   ┘
  Primary: 계약 조율, 완료된 부분 검토와 통합
        ↓
준비된 실제 구현부터 연결
  A와 B 준비 → A+B 계약 검증
  C까지 준비 → 전체 시나리오 검증
```

B는 A의 구현 완료를 기다리지 않고 합의한 입력 형태를 기준으로 구현한다. C 역시 B의 출력 계약을 기준으로 동시에 구현할 수 있다. 일시적인 fixture나 stub은 테스트 또는 개발 격리 범위에서 필요한 경우에만 사용한다. stub 통과는 실제 경계의 통합 증거가 아니며, 최종 요구사항의 실행 경로는 실제 구현에 연결해야 한다.

### 13.4 진행 중 계약 변경과 순차 작업

작업자가 계약의 결함이나 누락을 발견하면 공유 계약을 일방적으로 바꾸지 않고 주 에이전트에게 전달한다. 주 에이전트는 영향받는 생산자와 소비자를 찾아 계약 변경을 정렬하고, 해당 부분의 구현과 검증 근거를 갱신한다. 영향받지 않는 작업은 계속 진행한다.

공유 쓰기 충돌이나 실제 선행 결과가 필요한 구간만 순차 처리한다. 관련 구현이 준비되면 주 에이전트가 실제 diff와 근거를 확인해 통합하고 검증한다. 이 조건은 후속 기능의 코드 작성 전체를 선행 구현 통합 뒤로 미루는 조건이 아니다.

## 14. 공유 작업 공간과 코드 통합

모든 worker는 별도의 독립 저장소가 아니라 **공유 workspace**에서 작업한다고 가정한다.

따라서 worker에게 반드시 다음 의미가 전달되어야 한다.

```text
다른 변경이 실행 중 나타날 수 있다.

자신에게 할당되지 않은 변경을 되돌리지 않는다.

다른 사람의 코드를 reset하거나 overwrite하지 않는다.

할당된 write scope 밖의 문제를 발견해도 임의로 고치지 않는다.
```

Primary Agent는 각 worker 결과를 받을 때 실제 workspace를 직접 검사한다.

다음 항목을 확인한다.

```text
changed path가 scope 내부인가?
다른 변경을 손상시키지 않았는가?
requirement를 실제로 충족하는가?
non-goal까지 건드리지 않았는가?
validation 결과를 신뢰할 수 있는가?
실제 입출력과 동작이 공유한 계약과 일치하는가?
연결된 생산자·소비자의 전제가 깨지지 않았는가?
같은 역할의 코드 모양이 일관되고 같은 관심사가 모여 있는가?
주석이 hacky하거나 tricky한 구현의 이유와 제약에 한정되는가?
```

worker가 “완료했습니다”라고 말한 것은 completion evidence가 아니다.

### 14.1 코드 형태와 관심사 배치

작업을 배정할 때 관련 저장소 코드에서 따라야 할 형태와 관심사 경계를 전달한다. 작업자는 이를 기준으로 구현하고 주 에이전트가 통합 시 실제 코드를 다시 확인한다.

| 기준 | 구현과 검토에서 확인할 내용 |
| --- | --- |
| 유사한 역할의 형태 통일 | 같은 개념에 같은 용어를 쓰고, 유사한 함수·컴포넌트의 선언 순서, 분기와 오류 처리 방식을 맞춘다. |
| 관심사별 배치 | 같은 이유로 바뀌는 데이터와 로직은 가까이 두고, 서로 다른 책임이 한 흐름 안에서 불필요하게 섞이지 않게 한다. |
| 흐름과 추상화 수준 | 한 함수나 블록이 맡은 책임과 처리 순서를 읽을 수 있게 구성한다. 고수준 조율 사이에 무관한 저수준 처리를 섞지 않는다. |
| 기존 코드와의 일관성 | 적용되는 저장소 지침과 인접한 구현 패턴에 맞춘다. 작업자별 취향 때문에 같은 기능군의 형태가 달라지지 않게 한다. |
| 필요한 범위의 정돈 | 이번 변경과 필요한 통합 범위에서 구조를 정돈한다. 외형이 비슷하다는 이유만으로 다른 관심사를 하나의 추상화에 묶거나 관련 없는 코드를 재작성하지 않는다. |

코드의 모양을 맞춘다는 것은 공백 정렬만을 뜻하지 않는다. 읽는 사람이 한 구현에서 이해한 구조를 유사한 구현에서도 그대로 활용할 수 있어야 한다. 관심사를 묶는다는 것도 하나의 큰 파일이나 함수에 모두 넣는다는 뜻이 아니며, 책임 경계를 유지하면서 관련 내용을 찾기 쉽게 배치하는 것이다.

### 14.2 주석 작성 기준

주석은 hacky한 우회 구현이나 tricky한 로직에서 코드만 읽어서는 알기 어려운 이유와 제약을 설명할 때만 작성한다.

* 일반적인 분기, 값 대입, 함수 호출과 처리 단계의 동작을 반복 설명하는 주석은 추가하지 않는다. 이름과 구조로 읽히게 만든다.
* 쉽게 이해할 수 있는 구현으로 정리할 수 있으면 먼저 코드를 정리한다. 단순히 코드가 복잡하다는 이유로 설명 주석을 늘리지 않는다.
* 피할 수 없는 외부 시스템의 제약, 호환성 우회, 순서에 민감한 동작처럼 비자명한 사유가 남으면 왜 그 구현이 필요한지 짧게 적는다. 제거 조건을 알고 있다면 함께 적을 수 있다.

작업자는 가독성 문제를 설명 주석으로 덮지 않고 구조를 고친다. 주 에이전트도 주석 수나 코드 줄 수로 가독성을 판정하지 않는다.

## 15. Worker 실패 복구 정책

실패한 worker를 무한 반복해서 재시도하지 않는다.

Feature Implementer는 **finite recovery policy**를 사용한다.

기본 흐름은 다음과 같다.

```text
Worker attempt
      │
      ├─ success → inspect + integrate
      │
      └─ failure
            ↓
   Primary investigates failure
            ↓
   invalid edits만 안전하게 정리
            ↓
   Same worker retry × 1
            │
            ├─ success
            │
            └─ failure
                  ↓
       Different worker retry × 1
                  │
                  ├─ success
                  │
                  └─ failure
                        ↓
           small mechanical/integration fix?
               │                 │
              yes               no
               │                 │
           primary fix        BLOCKED
```

Primary Agent가 마지막에 대신 해결할 수 있는 범위는 작은 integration 또는 mechanical alignment 수준이다.

최초 시도와 허용된 재시도가 실패했다고 해서 primary agent가 큰 작업을 몰래 떠맡거나 acceptance criteria를 완화해 완료 처리해서는 안 된다.

현재 Execution Protocol이 동일한 유한 복구 순서를 정의한다.

## 16. 사용자 작업 보호

Feature Implementer에서 가장 강한 안전 요구사항 중 하나다.

다음 작업을 임의로 수행해서는 안 된다.

```text
git reset
git clean
git checkout -- <user file>
git restore <unowned changes>
자동 stash
전체 파일 formatter 실행
광범위 rename/move
```

필요한 파일에 기존 사용자 수정이 존재하면 해당 변경의 의미와 소유권을 확인하고, 그 내용을 보존하면서 요구사항에 필요한 편집을 수행한다.

계획과 사용자 작업이 실제로 충돌하고 저장소 증거만으로 해결할 수 없다면 그때만 사용자 결정이 필요하다.

## 17. 검증 모델

이미 수행한 유효한 검사를 재사용하고 각 인수 기준의 증거가 충분한지 확인한다. 검증은 아래 네 가지 범위로 분류하지만 모든 단계의 명령을 차례대로 다시 실행하도록 강제하지 않는다.

### Level 1: Targeted Validation

특정 요구사항이나 작업 단위의 인수 기준을 확인한다. 단위 테스트, 관련 타입 검사와 동작 관찰 등이 해당한다. 실제 명령은 저장소에서 확인하며 존재하지 않는 스크립트나 범위 옵션을 만들어 내지 않는다.

### Level 2: Integration Validation

변경된 API와 서비스, 스키마와 호출부처럼 작업 단위 사이의 실제 계약을 확인한다. 병렬 구현에 사용한 입출력, 오류와 부수 효과의 가정이 실제 생산자·소비자를 연결한 뒤에도 유효한지 점검한다. fixture나 stub만 통과한 결과로 실제 통합을 검증했다고 판단하지 않는다.

### Level 3: Repository Validation

저장소가 요구하는 검사와 실제 영향 범위에 필요한 넓은 검증을 다룬다. 전체 검사의 성공만으로 모든 개별 인수 기준이 확인됐다고 간주하지 않는다.

### Level 4: Scenario Validation

계획의 정상 흐름, 경계 조건, 실패, 호환성과 마이그레이션 시나리오를 확인한다. 하나의 유효한 테스트가 여러 요구사항과 검증 범위를 함께 충족할 수 있다.

### 17.1 추가 검증 조건

인수 기준의 근거가 빠져 있거나, 통합과 후속 변경이 이전 결과를 무효화한 경우 관련 검증을 추가한다. 유효한 동일 결과를 보고서 형식에 맞추기 위해 반복 실행하지 않는다.

### 17.2 증거 기록

```text
Evidence ID: E-001
Linked requirement: IR-001
Acceptance criterion: 잘못된 토큰에 401을 반환
Level: Targeted / Scenario
Command or observation: 저장소에서 확인한 인증 테스트 명령
Environment and scope: 현재 작업 공간의 인증 처리 변경
Result: 실제 실행 결과
Classification: verified / blocked / unverified / baseline-failure
Relevant output: 로그 또는 관찰 위치
Skipped check and consequence: 생략 검사, 사유와 확인하지 못한 동작
```

위 기록은 작성 예제다. `verified`는 실제 유의미한 검사가 통과한 경우에만 사용한다.

### 17.3 기획 일치와 코드 가독성 확인

주 에이전트는 모든 활성 요구사항을 실제 동작과 대조하고, 누락·임의 변경·범위 밖 추가가 없는지 확인한다. 테스트 통과만으로 이 대조를 생략하지 않는다.

가독성은 실제 diff와 관련 코드의 검토로 확인한다. 14절의 형태 통일, 관심사 배치와 주석 기준을 적용하고 발견한 문제를 해당 쓰기 소유자와 정리한다. 자동 포매터나 린터의 통과, 주석 개수는 이 검토를 대신할 수 없다.

## 18. Evidence 상태 모델

각 Acceptance Criterion은 다음 상태 중 하나를 갖는다.

| 상태                 | 의미                                              |
| ------------------ | ----------------------------------------------- |
| `verified`         | 의미 있는 검증이 성공했다.                                 |
| `blocked`          | 필요한 결정, 계약, 도구 또는 capability가 없어 안전하게 진행할 수 없다. |
| `unverified`       | 구현은 존재하지만 중요한 검증을 수행하지 못했다.                     |
| `baseline-failure` | 실패가 구현 전부터 존재했거나 이번 변경과 무관하다는 증거가 있다.           |

특히 다음은 금지한다.

```text
Implementation exists
        ≠
Requirement verified
```

또한 구현 때문에 새 테스트 실패가 발생했다면 이것을 `baseline-failure`라고 분류해서는 안 된다.

현재 상세 프로토콜 역시 동일한 네 가지 evidence classification을 사용한다.

## 19. 완료 판정

전체 작업의 최종 상태는 다음 중 하나다.

### Complete

모든 필수 Requirement가 충분한 evidence로 검증되었고 기획과의 미해결 불일치나 새 회귀가 남아 있지 않다. 변경 코드가 14절의 가독성 기준을 충족하는지도 확인한다.

### Partially Complete

일부 요구사항은 완료됐지만 나머지가 blocked 또는 unverified 상태다.

### Blocked

핵심 요구사항을 안전하게 구현할 수 없는 계약/결정/환경 문제가 존재한다.

### Unverified

주요 구현은 존재하지만 의미 있는 acceptance evidence가 부족하다.

부분 구현을 Complete로 표현해서는 안 된다.

## 20. 최종 결과 보고

Feature Implementer는 여러 worker의 개별 보고서를 사용자에게 그대로 던지지 않는다.

Primary Agent가 하나의 **Integrated Implementation Report**를 작성한다.

최종 보고에는 최소 다음 정보가 포함되어야 한다.

### 20.1 Overall Outcome

```text
complete
partially complete
blocked
unverified
```

중 하나 또는 이에 상응하는 명확한 상태.

### 20.2 Requirement Ledger

예:

| Requirement | Implementation | Evidence   | Status   |
| ----------- | -------------- | ---------- | -------- |
| R-001       | `auth.ts`      | auth tests | verified |
| R-002       | `user.ts`      | typecheck  | verified |
| R-003       | 미구현            | API 정책 미정  | blocked  |

### 20.3 Change Inventory

변경된 파일마다 왜 변경이 필요했는지 설명한다.

```text
src/auth.ts
- R-001의 인증 실패 동작 구현

tests/auth.test.ts
- R-001 acceptance criterion 검증
```

### 20.4 Execution Summary

필요한 경우 다음을 기록한다.

* direct implementation
* delegated work
* 병렬로 배정한 기능 단위와 공유한 입출력 계약
* 구현 착수와 통합·검증에서 각각 남은 의존성
* 직접 또는 순차 수행한 부분의 실제 사유
* worker ownership
* worker retry
* primary integration

속도를 평가하는 실행에서는 전체 경과 시간과 계약 조율, 대기, 재작업 시간을 기록한다. 측정하지 않은 시간이나 속도 향상을 추정해 성과로 보고하지 않는다.

### 20.5 Validation Evidence

실행한 명령과 결과를 기록한다.

```text
pnpm test auth
PASS

pnpm typecheck
PASS
```

실행하지 않은 중요한 검증이 있다면 이유를 명시한다.

### 20.6 Baseline Separation

기존부터 존재하던 실패와 새 regression을 구분한다.

### 20.7 Residual Risk

검증됐지만 여전히 남아 있는 위험 또는 불확실성을 기록한다.

### 20.8 Authorization Boundary

별도 요청이 없기 때문에 하지 않은 후속 작업도 명시할 수 있다.

예:

```text
Commit not created.
PR not opened.
Deployment not performed.
```

### 20.9 Code Readability

유사한 구현의 형태와 관심사 배치를 어떻게 맞췄는지 필요한 범위에서 설명한다. hacky하거나 tricky한 구현이 남았다면 이유와 관련 위치를 제시한다. 작은 변경은 기존 구현 패턴을 따랐다는 검토 결과로 간단히 표현할 수 있으며 별도 설명 주석이나 문서 작성을 요구하지 않는다.

보고는 작업 크기에 맞춰 간결하게 작성하되, 기획 일치의 근거와 병렬 작업 방식, 코드 가독성 확인 결과를 빠뜨리지 않는다.

## 21. 중요 예외 처리

### Case 1. 일반 Markdown 기획서

작성 도구나 정해진 표 형식 없이도 계획이 충분히 구체적이면 사용할 수 있어야 한다.

특정 생성기와 전용 스키마를 강제하지 않는다.

---

### Case 2. 계획에 필수 결정이 없음

예:

```text
사용자가 탈퇴하면 데이터를 처리한다.
```

하지만 삭제인지 익명화인지 명시되지 않았다.

이 결정이 제품 계약이라면 에이전트가 임의로 선택하지 않는다.

해당 requirement만 blocked 처리한다.

---

### Case 3. Dirty Worktree

사용자가 이미 같은 파일을 수정해 두었다.

기존 사용자 변경을 보존하면서 계획의 구현에 필요한 수정을 수행한다.

사용자 작업을 없애기 위해 reset하지 않는다.

---

### Case 4. 기존 테스트가 실패함

가능하다면 구현 전 baseline을 확인한다.

기존에도 실패한 테스트라면 baseline failure로 분리한다.

---

### Case 5. 전체 테스트 실행 비용이 매우 큼

관련 targeted validation부터 실행한다.

전체 검증이 불가능하거나 지나치게 비싸면 가능한 가장 강한 좁은 증거를 확보하고, 실행하지 않은 검사와 사유, 미검증으로 남은 인수 기준을 명시한다. 저장소의 필수 검사 요구가 없어지는 것은 아니며, 동등한 근거가 없으면 완료로 보고하지 않는다.

---

### Case 6. Worker가 없음

worker availability 자체는 blocker가 아니다.

Primary Agent가 안전하게 수행할 수 있는 작업이라면 직접 계속한다.

---

### Case 7. 여러 작업이 같은 파일을 수정해야 함

같은 파일을 동시에 수정하지 않는다.

공통 선언 등 겹치는 편집은 한 소유자가 처리한다. 이를 제외한 기능을 계약으로 분리할 수 있으면 나머지는 병렬 구현한다. 쓰기 범위를 분리할 수 없는 부분만 순차 처리하거나 하나의 Work Unit으로 합친다.

---

### Case 8. Worker 결과가 scope를 넘어감

결과를 그대로 accept하지 않는다.

변경 ownership을 확인하고 이번 worker가 만든 잘못된 범위만 안전하게 정리한 후 recovery policy를 적용한다.

---

### Case 9. 기능의 실행 순서가 A → B → C임

A의 출력과 B의 입력, B의 출력과 C의 입력 계약을 먼저 맞춘다. 쓰기 범위를 분리해 A·B·C의 구현을 동시에 배정하고, 실제 관련 구현이 준비되는 대로 주 에이전트가 연결하고 검증한다.

계약만으로 알 수 없는 선행 관찰 결과가 필요하면 해당 결과를 얻는 최소 작업만 먼저 수행한다. 중요한 제품 계약이 미정이라면 이를 임의로 채우지 않고 영향받는 부분만 차단한다.

---

### Case 10. 주석 없이는 읽기 어려운 구현

먼저 이름, 처리 흐름과 관심사 배치를 정리한다. 유사한 기능의 모양과도 맞춘다. 피할 수 없는 hacky한 우회나 tricky한 로직만 이유와 제약을 주석으로 설명한다.

| 외형이 비슷하지만 다른 관심사 | 모양만을 이유로 공통 추상화를 강제하지 않음 |
| 일반 흐름을 설명하는 주석이 필요해 보임 | 이름과 구조를 먼저 정리하고 동작을 반복 설명하는 주석을 추가하지 않음 |
| 피할 수 없는 hacky·tricky 구현 | 코드만으로 알기 어려운 이유와 제약을 짧게 주석으로 기록 |
| 빠르게 작성됐지만 기획 누락 또는 가독성 문제 존재 | 관련 코드를 수정하고 재확인하며 속도만으로 성공 판정하지 않음 |
| 다른 스킬이 설치되지 않음 | 일반 계획을 받아 자체 요구사항 분석, 구현, 통합과 검증을 수행 |

이 표는 개정 4의 목표 실행 계약을 평가할 시나리오다. 실제 행동 평가는 수행하지 않았으며 모든 행의 상태는 NOT_RUN이다.

## 25. 성공 지표

Feature Implementer의 품질은 단순한 코드 생성량으로 평가하지 않는다.

좋은 실행은 다음 조건을 만족한다.

### S-001. Requirement Coverage

모든 active requirement가 구현 또는 명확한 blocked/unverified 상태를 갖는다.

### S-002. Traceability

사용자는 어떤 requirement가 어떤 코드 변경과 어떤 검증으로 충족됐는지 확인할 수 있다.

### S-003. Scope Fidelity

각 변경이 활성 요구사항이나 필요한 통합 및 검증에 연결되고 계획의 범위와 계약을 충족한다. 코드 줄 수나 수정 파일 수 자체를 성공 지표로 사용하지 않는다.

### S-004. Workspace Preservation

실행 전 사용자 변경이 손실되지 않는다.

### S-005. Validation Quality

각 인수 기준을 뒷받침하는 의미 있는 acceptance evidence가 존재한다.

### S-006. Honest Completion

검증되지 않은 기능을 완료됐다고 표현하지 않는다.

### S-007. Authorization Safety

요청받지 않은 Git/remote/deployment/external side effect가 발생하지 않는다.

### S-008. Implementation Speed

허용된 협업 도구와 가용 작업자 범위에서 계약으로 분리 가능한 작업까지 병렬로 배정하고, 실제 선행 결과나 공유 쓰기가 필요한 최소 구간만 순차 수행한다. 이런 의존 작업에서는 계약 합의와 실제 구현의 동시 진행을 실행 기록에서 확인할 수 있어야 하며, 착수 가능한 작업이 관계없는 작업의 종료를 기다리지 않아야 한다.

성능 비교 시 동일한 기획, 저장소 상태, 도구·작업자 조건과 품질 기준으로 시작부터 최종 통합·검증까지의 경과 시간을 측정한다. 계약 정렬, 대기, 실패 복구와 통합 재작업 시간도 포함한다. 기획 충실성이나 가독성을 충족하지 못한 실행은 더 빨라도 성공한 비교 대상으로 인정하지 않는다.

작업자 수와 동시 호출 수 자체를 성과 지표로 사용하지 않는다. 측정하지 않은 속도 향상을 주장하거나 이 기준만을 위해 모든 구현을 순차 방식으로 재실행하지 않는다.

### S-009. Independent Execution

다른 스킬이 없는 환경에서도 일반 계획을 접수하고 요구사항 분석, 작업 소유권, 구현, 통합, 검증과 보고를 수행한다. 필요한 호스트 도구의 부재와 다른 스킬의 미설치를 구분한다.

### S-010. Human-Readable Code

실제 변경 코드에서 같은 역할의 이름·구조·처리 흐름이 일관되고 같은 관심사의 데이터와 로직을 함께 찾을 수 있어야 한다. 읽는 사람이 일반적인 동작을 이해하기 위해 설명 주석에 의존하지 않아야 한다.

가독성 검토에서 확인한 코드 위치와 판단 근거를 사용한다. hacky하거나 tricky한 구현의 주석은 비자명한 이유와 제약을 설명해야 한다. 주석 개수, 줄 수, 파일 수나 포매터 통과를 가독성 점수로 대체하지 않는다.

## 26. 최종 사용자 경험

사용자가 기대해야 하는 이상적인 사용 흐름은 다음과 같다.

```text
사용자
"이 기획서대로 구현해줘."

Feature Implementer
        ↓
계획서 전체 분석
        ↓
저장소/기존 변경 조사
        ↓
Requirement → Target → Evidence 매핑
        ↓
구현 착수와 실제 통합에 필요한 의존성 구분
        ↓
A 출력=B 입력, B 출력=C 입력 계약과 쓰기 소유권 확정
        ↓
가능한 기능을 서브 에이전트로 최대한 병렬 구현
        ↓
유사한 코드 형태 통일과 관심사별 배치
        ↓
주석은 hacky·tricky 구현의 비자명한 이유와 제약에만 작성
        ↓
준비된 실제 구현부터 기획·계약·가독성을 확인하고 통합
        ↓
기존 검증 결과를 인수 기준에 연결
        ↓
누락되거나 무효화된 증거에 필요한 검증 추가
        ↓
Baseline failure 분리
        ↓
Requirement별 completion 판정
        ↓
통합 결과 보고
```

최종적으로 사용자는 단순히

```text
구현했습니다.
```

라는 응답을 받는 것이 아니라,

```text
무엇을 구현했고
왜 그 파일을 변경했고
어떤 요구사항을 만족했고
어떤 계약을 먼저 맞춰 무엇을 병렬 구현했고
왜 일부 작업은 기다려야 했고
어떻게 코드의 모양과 관심사 배치를 맞췄고
어떤 검증을 실행했으며
무엇이 실제로 검증됐고
무엇은 검증되지 않았고
기존 실패는 무엇이고
남은 위험은 무엇인지
```

를 확인할 수 있어야 한다.

## 27. 모델별 보정과 실행 재개

공통 실행 계약과 상세 프로토콜을 기본으로 사용하며, 대응하는 모델별 보정을 최대 하나 추가한다. 이 기능은 다른 스킬이나 모델 전환 기능을 호출하지 않는다.

현재 모델 정보가 신뢰할 수 있게 제공되면 `gpt-6-astra` 또는 `GPT-6 Astra`에는 Astra 보정을, `gpt-5.6-sol`, `GPT-5.6 Sol` 또는 OpenAI `gpt-5.6` 별칭에는 Sol 보정을 선택한다. 대소문자를 구분하지 않고 지정된 이름과 일치하는지 확인한다. 모델 정보가 없는 경우 명시적 프로필 선택을 사용할 수 있으며, 알 수 없거나 대응하지 않는 모델에는 공통 계약만 적용한다. `feature-implementer profile: common`은 보정을 끈다.

Astra 보정은 허용된 구현을 증거까지 완수하고 유효한 작업 그래프에서 필요한 위임과 통합 검증을 수행하도록 안내한다. Sol 보정은 간결한 설명 때문에 요구사항과 증거가 누락되지 않도록 하고 현재 작업 공간을 기준으로 재개하도록 안내한다.

모델별 보정도 세 가지 핵심 가치를 동일하게 따른다. 의존 작업의 계약 선합의와 병렬 구현을 지원하고, 코드 가독성을 실행 범위 밖으로 제외하거나 모든 후속 구현을 선행 통합 뒤로 미루는 별도 규칙을 두지 않는다.

모델이 바뀌거나 새 실행으로 이어질 때 다음을 유지한다.

- 현재 계획과 요구사항 ID
- 기존 변경과 작업 단위별 소유권
- 공유한 입출력·동작 계약과 합의본, 계약 소유자
- 각 단위의 구현 착수 조건, 진행 중인 작업과 통합·검증 조건
- 검토하고 통합한 실제 구현과 코드 형태·관심사 기준
- 검증 근거와 그 유효 범위
- 이미 사용한 실패 복구 횟수
- 미정 계약과 잔여 위험
- 사용자에게 허용받은 작업 범위

이전 결과의 근거가 불명확하면 새 작업 공간을 깨끗한 상태라고 가정하거나 과거 검증을 그대로 통과 상태로 가져오지 않는다. 영향받는 근거만 다시 확인한다.

## 28. 일반 Markdown 계획의 상세 처리 예제

다음은 특정 생성기를 사용하지 않고 사람이 작성한 입력 예제다.

```markdown
# 인증 실패 응답 수정

잘못된 토큰으로 요청하면 401을 반환한다.
오류 응답의 JSON 필드와 정상 요청 동작은 유지한다.
로그인 화면과 토큰 발급 기능은 수정하지 않는다.
기존 인증 테스트에 잘못된 토큰 사례를 추가해 확인한다.
```

이를 원본 문서 수정 없이 내부 기록으로 변환한다.

| 내부 ID | 의미 | 구현 또는 확인 대상 |
| --- | --- | --- |
| IR-001 | 잘못된 토큰에 401 반환 | 실제 인증 처리 소유 함수 |
| IAC-001 | 잘못된 토큰 시나리오 통과 | 기존 테스트 방식의 인증 실패 사례 |
| IC-001 | 오류 JSON과 정상 요청 유지 | 기존 응답 계약과 성공 경로 검사 |
| ING-001 | 로그인 화면과 토큰 발급 제외 | 변경 금지 동작 |

저장소 조사에서 확인한 실제 파일과 심볼을 연결한다. 계획에 기록되지 않은 오류 메시지 변경이나 인증 체계 교체는 새 요구사항으로 추가하지 않는다.

검사 결과는 다음처럼 연결할 수 있다. 아래 결과는 설명용이며 실제 실행 증거가 아니다.

| 요구사항 | 구현 상태 | 증거 상태 | 결과 해석 |
| --- | --- | --- | --- |
| IR-001 | 수정 존재 | 테스트 실행 불가 | unverified, 구현은 존재하지만 완료 근거 부족 |
| IR-001 | 수정 존재 | 실패 및 정상 경로 통과 | 해당 기준 verified, 전체 완료는 나머지 필수 기준도 확인 |
| IR-001 | 계약 미정으로 미착수 | 적용할 정책 없음 | blocked, 독립 작업은 진행 가능 |

## 29. 품질 요구사항과 평가 기준

| ID | 품질 기준 | 판정 방법 |
| --- | --- | --- |
| QR-001 | 계획 충실성 | 모든 활성 요구사항의 동작·범위·제약을 실제 구현과 대조하고 누락, 임의 변경과 범위 밖 추가가 없는지 확인한다. |
| QR-002 | 상태 추적성 | 각 필수 요구사항에 구현 상태와 증거 상태가 존재한다. |
| QR-003 | 변경 소유권 보존 | 시작 상태와 최종 상태 비교에서 사용자 작업 손실이 없다. |
| QR-004 | 검증의 정직성 | 실제 명령과 출력이 상태 분류를 뒷받침한다. |
| QR-005 | 구현 속도와 병렬 배정 | 계약으로 분리 가능한 기능을 적극적으로 동시에 배정하고 대기와 순차 실행의 실제 사유를 확인한다. 성능 비교에는 통합·검증까지의 경과 시간을 사용한다. |
| QR-006 | 단독 실행 | 다른 스킬 없이 일반 계획의 구현과 검증, 보고를 마친다. |
| QR-007 | 복구의 유한성 | 재시도 횟수와 실패한 변경의 소유권이 기록된다. |
| QR-008 | 권한 경계 | 구현 요청에서 명시하지 않은 외부 작업이 발생하지 않는다. |
| QR-009 | 경계 계약과 실제 통합 | 작업자에게 같은 입출력·동작 계약을 전달하고, 실제 생산자·소비자의 연결 결과가 합의 계약과 일치하는지 검증한다. |
| QR-010 | 코드 형태와 관심사 | 같은 역할의 이름·구조·흐름이 일관되고 관련 데이터·로직이 모여 있는지 실제 코드로 검토한다. |
| QR-011 | 주석 절제 | 새로 작성한 주석이 hacky하거나 tricky한 구현의 비자명한 이유·제약에만 쓰였는지 검토한다. |

성공 지표는 실제 실행 기록에서 산출한다. 요구사항 상태 기록률은 상태가 기록된 필수 항목 수를 전체 필수 항목 수로 나누고, 검증 커버리지는 유의미한 근거를 가진 인수 기준 수를 전체 필수 인수 기준 수로 나눈다. 완료 보고에는 필수 기준의 커버리지 100%, 기획과의 미해결 불일치와 새 회귀 없음, 코드 가독성 기준 충족이 필요하다.

사용자 변경 손실과 근거 없는 완료 선언은 각각 발생 건수로 기록하며 허용 목표는 0건이다. 이 수치는 현재 성능 측정치가 아닌 수용 기준이다.

평가 시 계획 원본, 시작 파일 상태, 합의한 경계 계약, 작업 배정과 실행 시점, 실제 diff, 가독성 검토, 검증 로그와 최종 보고를 함께 보존한다. 병렬화에 따른 속도는 같은 품질 기준을 통과한 실행끼리 비교하며, 단일 실행의 작업 기록만으로 개선율을 주장하지 않는다. 모든 시나리오는 실행 전 NOT_RUN으로 두고 실제 증거를 확보한 뒤 PASS 또는 FAIL을 기록한다.
