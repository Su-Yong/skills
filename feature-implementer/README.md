# Feature Implementer

구체적인 계획 문서를 입력받아 기획에 충실한 기능을 서브 에이전트 병렬 작업으로 빠르게 구현하고, 사람이 읽기 쉬운 코드로 완성하는 독립적인 실행 스킬입니다. 계획을 만든 도구나 다른 스킬의 설치 여부와 관계없이 사용할 수 있습니다.

[설계서](SPEC.md) · [실행 지침](SKILL.md) · [상세 실행 프로토콜](references/execution-protocol.md)

## 언제 사용하나요?

- 요구사항과 완료 조건이 정리된 계획을 실제 코드로 옮길 때
- 여러 요구사항의 구현 여부와 검증 결과를 함께 추적하고 싶을 때
- 독립적인 기능과 입출력 계약으로 분리할 수 있는 의존 기능을 최대한 병렬 구현하고 싶을 때
- 유사한 구현의 모양을 맞추고 같은 관심사의 코드를 가까이 배치하고 싶을 때
- 기존 사용자 변경을 보존하면서 계획 범위의 구현을 진행할 때

계획 검토, 원인 분석이나 실현 가능성 조사만 요청한 경우에는 구현을 시작하지 않습니다. 무엇을 만들지 아직 정하지 못했다면 필요한 계약을 먼저 구체화해야 합니다.

## 세 가지 핵심 가치

| 기준 | 사용자에게 제공하는 동작 |
| --- | --- |
| 기획 충실성 · Plan Fidelity | 요구사항의 동작·범위·제약을 실제 구현과 대조하고 각 인수 기준을 동작 증거로 확인합니다. |
| 구현 속도 · Fast Implementation | 서브 에이전트를 적극적으로 활용해 가능한 기능을 최대한 동시에 구현합니다. 의존 기능도 입출력과 동작 계약을 먼저 맞춰 병렬 배정합니다. |
| 사람이 읽기 쉬운 코드 · Human-Readable Code | 유사한 역할의 이름·구조·처리 흐름을 맞추고 같은 관심사를 가까이 묶습니다. 주석은 hacky하거나 tricky한 구현의 비자명한 이유와 제약에만 작성합니다. |

속도는 기획 충실성과 가독성을 충족하면서 통합과 검증까지의 전체 완료 시간을 줄이는 방향으로 판단합니다. 사용자 작업 보존, 증거 기반 완료 판단과 다른 스킬에 의존하지 않는 실행은 세 가치를 뒷받침하는 필수 실행 조건입니다.

## 빠르게 시작하기

스킬을 사용할 수 있는 에이전트 환경에서 구현할 프로젝트를 열고 계획 경로와 구현 요청을 전달합니다. `$feature-implementer`는 채팅에 입력하며 터미널 명령이 아닙니다.

```text
$feature-implementer
docs/plans/session-expiry.md를 전체 읽고 이 계획대로 구현해 줘.
병렬 구현할 수 있는 기능은 계약을 먼저 맞춰 서브 에이전트에 배정하고,
유사한 코드의 모양과 관심사 배치를 맞춰 줘.
현재 작업 공간의 기존 수정은 보존하고,
요구사항별 구현 결과와 검증 근거를 정리해 줘.
```

스킬은 계획 전체와 저장소 상태를 확인하고 다음 관계를 만듭니다.

```text
요구사항 → 구현 대상 → 경계 계약과 쓰기 소유권
         → 구현 착수 조건 / 통합·검증 조건 → 인수 기준과 검증 근거
```

이후 준비된 기능을 가용 작업자에게 곧바로 배정하고, 주 에이전트가 공유 계약과 통합을 관리합니다. 작업자와 쓰기 범위가 겹치지 않는 구현이나 검증도 주 에이전트가 수행합니다. 계획 승인만으로는 구현을 시작하지 않으므로, 실행할 때는 위 예시처럼 구현 의사를 명확히 적습니다.

## 어떤 계획을 준비하면 되나요?

특정 템플릿은 필요하지 않습니다. 다음 내용이 있으면 구현 범위와 완료 조건을 판단하기 쉽습니다.

| 내용 | 예시 |
| --- | --- |
| 요구사항 | 만료된 세션으로 요청하면 401을 반환합니다. |
| 인수 기준 | 만료된 세션은 실패하고 유효한 세션은 정상 처리됩니다. |
| 제약 | 오류 JSON 형식은 유지합니다. |
| 제외 범위 | 로그인 화면과 세션 발급 정책은 변경하지 않습니다. |
| 미정 사항 | 장기 미사용 세션의 보존 기간은 아직 미정입니다. |

사람이 직접 작성한 다음 정도의 Markdown도 입력할 수 있습니다.

```markdown
# 세션 만료 응답 수정

- 만료된 세션으로 인증 요청을 보내면 401을 반환한다.
- 오류 JSON 필드와 유효한 세션의 동작은 유지한다.
- 로그인 화면과 세션 발급 정책은 변경하지 않는다.
- 기존 인증 테스트에서 만료 및 유효 세션 사례를 검증한다.
```

문서에 ID가 있으면 그대로 사용하고, 없으면 내부 추적용 ID를 만듭니다. ID 추가를 위해 원본 계획을 다시 작성하지 않습니다.

## 사용 예시와 시나리오

### 1. 작은 계획을 바로 구현하기

```text
$feature-implementer
docs/plans/session-expiry.md대로 구현해 줘.
계획에서 정한 오류 응답과 정상 세션 동작을 검증해 줘.
```

분해와 조율 비용이 이점보다 큰 작은 단일 변경은 주 에이전트가 직접 처리할 수 있습니다. 직접 또는 순차 수행을 선택한 부분은 실제 제약이나 비용을 짧게 기록합니다.

### 2. 의존하는 기능까지 병렬 구현하기

```text
$feature-implementer
docs/plans/admin-export.md를 구현해 줘.
독립적인 기능은 쓰기 범위를 분리해 서브 에이전트로 최대한 동시에 구현해 줘.
조회 → 가공 → 화면 표시처럼 의존하는 기능도 입출력 계약을 먼저 맞춰
각 구현을 동시에 진행하고, 실제 구현이 준비되면 연결해서 검증해 줘.
```

기획과 저장소의 근거로 작업별 요구사항, 구현 착수 조건, 통합·검증 조건과 쓰기 범위를 정합니다. 관련 작업자에게 같은 입출력 자료형과 데이터 의미, 오류·빈 결과 처리, 부수 효과·호환성 제약을 전달하고 공유 계약의 소유자와 합의본을 정합니다. 아래 흐름은 기능과 계약이 기획에서 확정된 경우의 예시입니다.

```text
실제 동작: A 조회 → B 가공 → C 화면 표시

계약 정렬: A 출력 = B 입력, B 출력 = C 입력
           공유 선언이 필요하면 한 소유자가 최소 편집
                 ↓
동시 구현: Worker A · Worker B · Worker C
           서로 다른 쓰기 범위, 같은 합의 계약과 코드 형태 기준
                 ↓
실제 통합: A와 B 준비 → A+B 계약 검증
           C까지 준비 → 전체 시나리오 검증
```

B와 C는 합의한 계약을 기준으로 코드를 작성합니다. 착수 가능한 작업은 관계없는 작업 묶음의 종료를 기다리지 않고 곧바로 배정합니다. 같은 파일의 공유 선언은 한 소유자가 처리하고, 나머지 기능은 계속 병렬 구현합니다. 실제 선행 관찰 결과가 필요한 경우에는 그 결과를 얻는 최소 작업만 먼저 수행합니다.

구현 중 계약 변경이 필요하면 작업자가 주 에이전트에게 알리고, 주 에이전트가 영향받는 생산자·소비자와 변경을 맞춥니다. 관련 구현과 검증 근거만 갱신하고 다른 작업은 계속 진행합니다. 계약을 맞추기 위해 미정 제품 동작을 임의로 결정하지 않습니다.

필요한 fixture나 stub은 개발·검증 격리 범위에서 사용할 수 있습니다. 최종 실행 경로를 실제 구현에 연결하고 검증해야 해당 통합 기준이 충족됩니다. 주 에이전트는 실제 변경과 검증 근거를 확인하며 작업자 보고만으로 완료를 인정하지 않습니다.

### 3. 기존 수정이 있는 파일에서 구현하기

```text
$feature-implementer
docs/plans/search-filter.md대로 구현해 줘.
src/search/form.ts에는 내가 수정 중인 UI 문구가 있어.
해당 변경과 현재 스테이징 상태를 보존하면서 작업해 줘.
```

파일 경로는 실제 프로젝트에 맞게 바꿉니다. 기존 변경의 의미와 소유권을 확인하고 새 작업을 진행합니다. 소유권 충돌은 영향받는 작업에 한정해 처리합니다.

### 4. 일부 요구사항에 중요한 결정이 빠진 경우

```text
$feature-implementer
docs/plans/account-settings.md를 구현해 줘.
프로필 수정 요구사항은 확정됐지만 탈퇴 데이터 처리 정책은 아직 미정이야.
미정 정책에 의존하는 작업은 표시하고 독립적인 항목부터 진행해 줘.
```

삭제와 익명화처럼 결과가 달라지는 계약을 임의로 선택하지 않습니다. 해당 요구사항과 실제 의존 작업만 차단하고 독립적인 항목은 계속 구현할 수 있습니다.

### 5. 계획에 여러 파일이나 구조 변경이 포함된 경우

```text
$feature-implementer
docs/plans/payment-module-split.md를 구현해 줘.
계획에 명시한 모듈 분리와 호출부 변경을 모두 반영하고,
공개 API 호환성과 관련 통합 시나리오를 검증해 줘.
```

계획이 요구하는 구조 변경도 수행 대상입니다. 파일 수를 줄이는 것보다 계획의 계약과 인수 기준을 충족하는지를 확인합니다.

### 6. 차단된 항목을 다시 진행하기

```text
$feature-implementer
docs/plans/account-settings.md에 탈퇴 데이터 처리 정책을 확정해 뒀어.
현재 계획과 실제 작업 공간, 남아 있는 실행 기록을 확인하고
차단됐던 요구사항을 이어서 구현해 줘.
이미 검증된 독립 작업은 유지해 줘.
```

현재 저장소와 기록을 다시 맞춰 보고, 변경 때문에 유효하지 않게 된 근거만 재확인합니다. 공유 계약과 합의본, 쓰기 소유권, 구현·통합 조건, 가독성 기준과 이미 사용한 복구 횟수도 이어받습니다. 과거의 완료 보고만으로 현재 상태를 통과로 간주하지 않습니다.

### 7. 코드 자체로 읽기 쉬운 구현 만들기

```text
$feature-implementer
docs/plans/notification-preferences.md대로 구현해 줘.
저장소의 유사한 설정 기능과 이름, 선언 구조, 분기와 오류 처리 모양을 맞추고,
같은 관심사의 데이터와 로직을 가까이 배치해 줘.
주석은 피할 수 없는 hacky하거나 tricky한 구현의 이유와 제약에만 써 줘.
```

각 작업자에게 따라야 할 저장소 코드 형태와 관심사 경계를 전달하고, 주 에이전트가 실제 변경을 검토합니다. 일반적인 흐름은 이름과 구조로 드러내며 설명 주석을 늘려 가독성을 대신하지 않습니다. 서로 다른 책임을 모양만 보고 하나로 추상화하거나 관련 없는 기존 코드를 정리하지 않습니다. 검토는 이번 변경과 필요한 통합 범위에서 수행합니다.

## 결과는 어떻게 받나요?

주 에이전트가 요구사항별 결과를 하나로 모아 보고합니다.

- 전체 결과와 그 판단 이유
- 요구사항별 구현 대상, 검증 근거와 상태
- 변경 파일과 각 변경이 필요한 이유
- 병렬 배정한 기능과 먼저 맞춘 입출력 계약, 구현 착수와 통합·검증에 남은 의존성
- 직접·순차 수행한 부분의 실제 사유, 작업 소유권과 실패 복구 내역
- 기획과 실제 구현의 일치 여부, 코드 형태·관심사 배치와 주석 기준의 검토 결과
- 실제 검사 결과, 생략한 검사와 미검증 범위
- 확인된 기존 실패, 새로운 회귀와 잔여 위험

보고는 작업 크기에 맞춰 간결하게 작성합니다. 속도를 평가할 때는 계약 조율·대기·재작업과 통합·검증까지의 전체 경과 시간을 기록하며, 측정하지 않은 시간이나 속도 향상을 성과로 보고하지 않습니다.

아래는 보고 형식을 설명하는 예시이며 실제 검사 결과가 아닙니다.

| 요구사항 | 구현 | 검증 | 상태 |
| --- | --- | --- | --- |
| 세션 만료 응답 | 인증 처리 변경 | 만료 및 정상 세션 검사 통과 | verified |
| 탈퇴 데이터 처리 | 미착수 | 데이터 정책 미정 | blocked |
| 파일 다운로드 | 구현 존재 | 통합 검증 환경 사용 불가 | unverified |

## 완료 상태 읽는 법

| 전체 결과 | 의미 |
| --- | --- |
| Complete | 모든 필수 항목의 인수 기준이 검증됐고 기획과의 미해결 불일치나 새 회귀가 없으며, 변경 코드의 가독성 기준도 충족합니다. |
| Partially Complete | 일부 독립 항목은 검증됐지만 나머지가 차단됐거나 미검증입니다. |
| Blocked | 핵심 결정이나 환경 문제로 유효한 구현을 거의 진행할 수 없습니다. |
| Unverified | 주요 구현은 있지만 핵심 인수 기준의 증거가 부족합니다. |

`baseline-failure`는 변경 전부터 존재했거나 이번 수정과 무관함이 입증된 검사 실패입니다. 기존 실패라는 이유만으로 관련 요구사항을 검증 완료로 바꾸지는 않습니다.

## 자주 생기는 상황

| 상황 | 처리 방식 |
| --- | --- |
| 작업자 도구를 사용할 수 없음 | 안전하게 직접 수행할 수 있는 작업은 계속 진행합니다. |
| 여러 작업이 같은 파일을 수정해야 함 | 동시 쓰기를 금지하고 겹치는 편집을 한 소유자에게 모읍니다. 쓰기 범위를 분리할 수 없는 부분만 묶거나 순차 처리하며 나머지는 병렬 구현합니다. |
| 구현 순서가 A → B → C임 | 입출력과 동작 계약을 먼저 맞춰 A·B·C를 병렬 구현하고, 실제 구현이 준비되는 대로 관련 통합을 검증합니다. |
| 실제 선행 결과가 있어야 다음 결정을 할 수 있음 | 결과를 얻는 최소 작업만 먼저 수행하고 영향받지 않는 작업은 계속 진행합니다. |
| 작업자가 실패함 | 소유권과 원인을 확인해 잘못된 작업자 변경만 안전하게 정리합니다. 같은 작업자 1회 → 다른 작업자 1회 재시도 후, 작은 통합·기계적 수정만 주 에이전트가 처리하고 그보다 크면 해당 작업을 차단합니다. |
| stub 검증만 통과함 | 실제 생산자·소비자를 연결해 검증하기 전에는 해당 통합 기준이나 전체 작업을 완료로 판단하지 않습니다. |
| 기획 누락이나 가독성 문제가 남음 | 관련 코드를 수정하고 재확인합니다. 빠르게 코드를 작성했어도 완료로 판단하지 않습니다. |
| 테스트 환경이 없음 | 가능한 근거를 확보하고 실행하지 못한 검사와 미검증 항목을 밝힙니다. |
| 구현을 마침 | 계획 범위의 변경과 검증 결과를 보고합니다. 커밋·브랜치 변경·push·PR·배포나 외부 시스템 변경은 별도 요청이 있어야 합니다. |

## 선택 사항: 공통 규칙만 사용하기

```text
$feature-implementer
feature-implementer profile: common
docs/plans/session-expiry.md대로 구현하고 검증해 줘.
```

`profile`은 모델별 추가 지침의 선택을 제어합니다. 모델이나 추론 수준을 변경하지 않으며 일반적인 사용에는 지정하지 않아도 됩니다.
