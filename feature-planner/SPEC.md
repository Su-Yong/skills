# Feature Planner 스킬 명세

작성일: 2026-09-07 / 개정일: 2026-10-12 / 개정: 9

이 문서는 **Feature Planner라는 대화형 구현 기획 스킬**을 만드는 데 필요한 목적, 사용 조건, 입력과 출력, 대화 규칙, 문서 양식과 완료 기준을 정의한다.

## 목표

질문을 통해 사용자가 원하는 결과와 구현 방법을 계속 좁혀, 바로 구현에 사용할 수 있는 구체적인 계획을 만든다.

항상 구현 기획을 수행한다. 아이디어 구체화와 구현 방식 결정은 하나의 연속적인 대화이며, 일반 기획과 구현 기획을 별도 모드로 나누지 않는다. 질문의 깊이에 고정된 단계나 상한을 두지 않는다.

사용자와의 질답이 주된 활동이다. 진행 중 문서는 다른 세션에서도 결정과 맥락을 이어받기 위한 한국어 메모리다. 문서 완성이나 정리가 질문을 기다리게 해서는 안 된다.

## 사용 조건과 입출력

### 어떤 요청에 사용하는가

- 스킬 식별자는 `feature-planner`, 표시 이름은 `Feature Planner`다.
- 사용자는 `$feature-planner`를 지정하거나 아이디어 구체화, 기능 기획, 구현 방법 결정, 기존 기획 수정·재개를 요청해 사용할 수 있다. 명시 호출만으로 제한하지 않는다.
- 새 프로젝트와 기존 프로젝트 모두 지원한다. 초기 아이디어만 있어도 시작하고, 이미 결정한 내용이 있으면 그 지점에서 구체화를 이어간다.
- 코드 작성 자체가 아니라 무엇을 어떻게 구현할지 결정하는 작업을 맡는다. 기획의 승인이나 종료만으로 실제 구현을 실행하지 않는다.

예를 들어 “팀에서 사용할 회의실 예약 서비스를 기획해 줘”라는 요청을 받으면, 대상 사용자와 예약 동작부터 시작해 필요한 제약·예외·데이터 처리·구현 위치·완료 기준을 질문과 조사로 좁힌다. 정해진 설문을 순서대로 소진하지 않으며, 어떤 영역이든 답변에 따라 더 깊게 들어갈 수 있다.

### 입력

| 구분 | 내용 | 처리 |
| --- | --- | --- |
| 시작 입력 | 만들거나 바꾸려는 대상, 목표 또는 한 문장의 아이디어 | 완성된 요구사항 문서를 요구하지 않고 질문을 시작한다. |
| 선택 자료 | 저장소, 파일, 링크, 참고 자료, 기존 결정, 제약 | 관련 부분만 확인한다. 전체 자료 조사를 첫 질문의 선행 조건으로 두지 않는다. |
| 후속 입력 | 선택 번호, 자유로운 답변, 추가 조건, 정정, 여러 질문의 답변 | 표현 형식보다 의미를 읽고 모든 조건을 반영한다. |
| 제어 입력 | 건너뛰기, 보류, 중단, 재개, 명시적 종료 | 자연스러운 표현을 받아들이고 아래 제어 규칙에 따라 처리한다. |

자료에서 확인한 사실과 에이전트의 추론을 구분한다. 자료에 접근하지 못했거나 서로 충돌하면 확인되지 않은 부분을 미정으로 남긴다. 필요한 사실 확인과 관계없이 진행할 수 있는 질문은 함께 제시한다.

### 출력

| 시점 | 사용자에게 보여줄 내용 | 저장할 내용 |
| --- | --- | --- |
| 질답 진행 | 새로 생기거나 변경된 에이전트 임시 결정, 상세한 질문 묶음 | 질문·선택지·답변 원문, 자체 결정과 변경 내용 |
| 중단 | 저장 상태와 남은 미정 사항을 짧게 안내 | 마지막 답변까지 포함한 질답 기록과 중단 상태 |
| 명시적 종료 | 최종 기획서 위치와 남은 미정 사항을 안내하며 추가 질문은 하지 않음 | 기존 질답 기록과 별도의 한국어 최종 기획서 |

두 파일의 역할은 다르다. **질답 기록**은 결정의 과정과 수정 이력을 보존하는 메모리이고, **최종 기획서**는 현재 유효한 구현 계획이다. 최종 기획서에는 필요한 결정 내용을 직접 적어 원문 기록 없이도 무엇을 어떻게 구현할지 이해할 수 있게 한다.

저장 경로는 사용자 지정과 프로젝트 관례를 우선한다. 별도 지정이나 관례가 없으면 프로젝트의 `docs/specs/` 아래에 `<기획명>-interview.md`와 `<기획명>-spec.md`를 구분해 저장할 수 있다. 같은 기획을 재개할 때는 기존 기록을 사용하며 관련 없는 문서를 덮어쓰지 않는다. 저장하지 못하면 실제 저장 상태를 알리고 기록 내용을 응답으로 보존한다. 저장 실패를 이유로 기획서 전체를 먼저 작성하는 절차를 만들지 않는다.

### 결정의 구분

- **사용자 결정:** 사용자가 명시적으로 선택하거나 추가·수정한 내용이다.
- **확인한 사실:** 코드나 자료에서 실제로 확인한 내용이다. 다시 확인할 수 있는 위치나 출처를 함께 남긴다.
- **추천:** 사용자에게 제시하는 선택지다. 추천 표시만으로 사용자 결정이 되지 않는다.
- **에이전트 임시 결정:** 허용된 사소한 사항을 에이전트가 잠정적으로 정한 내용이다. 사용자 결정과 구분해 공개한다.
- **미결정 사항:** 아직 답하지 않았거나 건너뛰고 보류한 내용, 해결되지 않은 충돌이다. 종료하더라도 임의로 확정하지 않는다.

이 구분을 위해 별도의 코드형 원장이나 여러 중복 표를 만들 필요는 없다. 질문·답변·자체 결정 기록 안에서 의미가 분명하면 된다.

## 핵심 동작

1. 요청과 관련 문서의 필요한 부분만 짧게 확인하고 첫 질문을 시작한다. 완성된 기획 초안이나 전면 조사를 먼저 요구하지 않는다.
2. 답변을 기다리지 않아도 물을 수 있는 질문은 주제와 관계없이 최대한 한 번에 제시한다. 앞선 답변에 의존하는 후속 질문만 다음으로 넘긴다.
3. 모든 질문을 상세한 고정 양식으로 작성한다. 배경, 결정할 지점, 영향과 선택지의 실제 차이를 설명한다.
4. 답변이 쌓이면 원하는 기능과 동작을 계속 구체화한다. 구현 논의에 필요한 코드와 자료만 그때 확인하여 구현 방법까지 정한다.
5. 중요한 결정이나 되돌리기 어려운 결정은 사용자에게 묻는다. 사소하고 쉽게 되돌릴 수 있는 사항만 에이전트가 임시 결정하고 다음 질문 위에 공개한다.
6. 질문·선택지·답변 원문과 자체 결정을 기록한다. 답변마다 변경된 기록만 짧게 저장하고, 전체 문서를 매번 재작성하지 않는다.
7. 사용자가 명시적으로 종료하면 추가 질문을 멈추고, 기록과 별개로 목표·핵심 동작·구체적인 할 일·미결정 사항을 담은 한국어 기획서를 만든다.

구현 기획의 완료는 실제 코드 구현, 설치, 배포나 외부 시스템 변경의 실행 허가가 아니다.

## 구현 할 일

아래 체크박스는 이 명세를 실행 가능한 스킬로 구현할 작업이다. 각 항목에 필요한 동작을 본문에 모두 적었으며, 완료 기준은 아직 실행하지 않은 검증 조건이다.

### 1. 질문을 먼저 시작하는 공통 흐름으로 변경

- [ ] `SKILL.md`에 이 문서의 목적·사용 조건과 다음 운영 순서를 구현한다.
  - 처음부터 기획서 전체를 작성하거나 빈 영역을 가정으로 채우지 않는다. 첫 질문에 필요한 문맥만 확인한다.
  - 매 질문 전 전체 문서 갱신·파급효과 전면 수정·정합성 검사를 강제하지 않는다.
  - 최신 답변과 조건을 이해한 상태에서 다음 질문을 만들고, 저장은 변경된 기록 위주로 처리한다.
  - 문서 경로·수정 번호·전체 상태표를 매번 질문 앞에 길게 보고하지 않는다.
  - **완료 기준:** 한 줄 아이디어와 기존 문서가 주어져도 필요한 부분만 확인한 뒤 질문 묶음을 제시한다. 첫 질문 전 완성된 초안 작성이 선행되지 않는다.

### 2. 질문을 가능한 한 묶어서 제시

- [ ] 다음 기준으로 질문을 선택하고 한 응답에 묶는다.
  - 기본 기준은 5개지만, 7~10개 이상도 가능하다. 5개나 10개를 상한으로 삼지 않는다.
  - 지금 답할 수 있는 질문을 형식적인 개수 제한 때문에 다음 응답으로 나누지 않는다. 반대로 개수를 채우려고 불필요한 질문을 만들지 않는다.
  - 30~40개를 한꺼번에 쏟아내는 과도한 묶음은 피한다.
  - 동일 주제나 밀접하게 연관된 질문만 묶도록 제한하지 않는다. 초반에는 여러 주제가 자연스럽게 섞일 수 있다.
  - 질문은 답변에 따라 계속 깊어진다. 반드시 거쳐야 하는 단계, 영역별 완료 순서, 중요한 질문만 허용하는 제한을 두지 않는다.
  - 이미 답한 질문과 확인 가능한 사실은 다시 묻지 않는다. 확인이 필요한 사실은 관련 부분을 조사한다.
  - **완료 기준:** 서로 다른 주제의 독립적인 질문은 함께 제시하고, 답변에 따라 선택지가 달라지는 후속 질문만 미룬다. 후반에는 필요한 세부 동작과 예외도 질문한다.

### 3. 모든 질문에 상세한 응답 템플릿 적용

- [ ] `SKILL.md`의 질문 계약을 아래 양식으로 통일한다. 짧은 확인·충돌 해결·종료 선택 질문도 같은 형식을 따른다.
  - 질문 번호와 제목, 상세 설명, 번호 선택지를 반드시 포함한다.
  - 질문 번호는 인터뷰 전체에서 `Q-001`, `Q-002`처럼 이어서 부여한다. 이미 제시한 질문을 다시 다룰 때는 같은 번호를 사용하고, 다른 질문에 번호를 재사용하지 않는다.
  - 상세 설명에는 배경, 이미 정한 내용과의 관계, 이번에 결정할 내용과 영향을 적는다.
  - 선택지마다 구체적인 동작 차이, 장단점과 적합한 상황을 설명한다. 설명만으로 이해하기 어렵다면 예시를 추가한다.
  - 근거가 있을 때만 추천 표시와 이유를 붙인다. 대안을 채우기 위해 실질적으로 같은 선택지를 만들지 않는다.
  - 여러 질문은 구분선으로 나누고, 끝에 번호 또는 자유로운 문장으로 답할 수 있음을 안내한다.
  - 숫자·선택지 이름·추가 조건·자유로운 결정·여러 질문의 답변을 함께 해석한다. 의미가 명확한 선택지 조합도 수용한다.
  - **완료 기준:** 질문이 단순 제목이나 짧은 목록으로 축약되지 않는다. 추천 근거와 선택지 차이를 읽고 판단할 수 있으며, 사용자가 정해진 답변 문법을 지키도록 요구하지 않는다.

```markdown
## 에이전트 임시 결정

### A. <결정 제목>

- 무엇을: <판단한 항목>
- 어떻게: <임시로 정한 구체적인 내용 또는 변경 내용>
- 왜: <판단 근거와 선택 이유>

### B. <다음 결정 제목>

- 무엇을: <판단한 항목>
- 어떻게: <임시로 정한 구체적인 내용 또는 변경 내용>
- 왜: <판단 근거와 선택 이유>

## 질문

**[Q-001] : <결정할 내용>**

<배경, 이미 정한 내용과의 관계, 이번에 좁힐 지점과 결정이 바꾸는 동작>

1. **<선택지> — 추천**
   <구체적인 동작, 장단점, 적합한 상황과 추천 이유>
2. **<실질적으로 다른 선택지>**
   <구체적인 동작, 장단점과 적합한 상황>

---

**[Q-002] : <다음 결정할 내용>**

<같은 형식의 상세 설명과 선택지>

번호나 자유로운 문장으로 답하시면 됩니다. 예: `Q-001: 1, Q-002: 원하는 조건`
```

꺾쇠 안은 실제 논의 내용으로 채운다. 예시의 질문 수와 선택지 수는 고정 개수가 아니다. 새로 생기거나 변경된 자체 결정이 있을 때 해당 결정만 질문 위에 넣으며, 없는 결정을 만들어 이 구역을 채우지 않는다. 템플릿을 출력 전에 짧게 확인하는 것은 허용하지만 문서 전체 검사로 질문을 지연시키지 않는다.

### 4. 자체 결정의 권한과 표시를 명확히 구분

- [ ] `SKILL.md`의 사용자 결정권·추천·가정 처리에 다음 기준을 반영한다.
  - 기능 범위·사용자 경험·데이터 처리·비용·핵심 구현 구조는 사용자에게 질문한다.
  - 이 밖의 항목도 되돌리기 어렵거나 수정 비용이 크거나 다른 결정에 미치는 영향이 크면 질문한다.
  - 그 외의 사소하고 쉽게 되돌릴 수 있는 사항은 임시 결정할 수 있다. 사용자 결정과 구분하고, 사용자 미응답을 승인으로 바꾸지 않는다.
  - 자체 결정은 인터뷰 전체에서 A, B, C … Z, AA, AB 순서로 구분한다. 같은 결정의 수정·재표시에는 같은 알파벳을 유지한다.
  - 새로 생기거나 변경된 결정만 다음 질문 위의 별도 헤더 아래에 표시한다. 무엇을·어떻게·왜 정했는지 모두 설명한다.
  - 결정과 변경 이유는 원문 기록에도 남긴다. 변경되지 않은 결정을 매번 반복하지 않는다.
  - **완료 기준:** 중요한 선택은 질문으로 남고, 허용된 자체 결정은 알파벳·세 항목·별도 헤더를 갖춰 공개된다. Z 이후와 다음 세션에서도 식별자가 이어지며, 수정 전 기록도 보존된다.

### 5. 진행 중 문서를 질답 메모리로 축소

- [ ] 아래의 질답 기록 양식을 기준으로 저장과 재개를 구현한다. 양식을 별도 파일로 제공하더라도 필수 내용은 이 명세와 동일해야 한다.
  - 진행 중에는 질문의 상세 설명과 모든 선택지, 사용자 답변을 원문 그대로 누적한다. 에이전트 자체 결정과 수정도 함께 남긴다.
  - 목표, 결정 이유, 확인한 사실과 출처, 미결정 사항 등 질답을 이해하는 데 필요한 맥락을 보존한다. 추측을 확인된 사실로 기록하지 않는다.
  - 답변마다 새 기록과 변경분만 저장한다. 원문 기록을 요약문으로 대체하지 않는다.
  - 별도의 다음 논의 지점, 방대한 영역별 표, 모든 항목의 중복 원장·파급효과 전면 갱신을 필수로 요구하지 않는다.
  - 사용자가 기존 결정을 바꾸면 이전 원문은 보존하면서 무엇이 대체되었는지 명확하게 기록한다. 후속 질문과 최종 기획에는 최신 결정을 사용한다.
  - **완료 기준:** 다른 세션에서 기록만 읽고 목표·최신 결정·추가 조건·가정·미답변을 구분할 수 있다. “2번인데 조건을 추가”라는 답변의 선택지 내용과 조건이 모두 남는다.

### 6. 구현 방식과 구체적인 작업까지 계속 좁히기

- [ ] 적용 범위·질문 선택·자료 조사·최종 정리 전반에서 항상 구현 기획을 수행한다.
  - 일반 기획과 구현 기획을 나누거나 모드를 선택하게 하지 않는다. 아이디어 구체화와 구현 방법 결정을 항상 함께 담당한다.
  - 원하는 기능을 먼저 좁히고, 구현 논의에서는 해당 질문에 필요한 코드·자료만 그때 확인한다. 고정된 단계 전환이나 전면 조사 대기 절차를 만들지 않는다.
  - 동작, 조건, 예외, 완료 기준을 질답으로 구체화하고 실제 구현 방법을 결정한다.
  - 관련 파일·함수와 작업 의존 순서는 조사로 확인한 내용에 근거해 포함한다. 확인하지 않은 위치나 새로 제안하는 구조를 이미 존재하는 코드로 표현하지 않는다.
  - **완료 기준:** 질답에서 “댓글 등록 시 로그인 여부를 확인하고 비회원 요청을 거절한다”고 정했다면 그 조건을 구현 작업과 확인 기준에 유지한다. 최종 문서에서 다시 “댓글 기능 만들기”로 축약하지 않는다.

### 7. 부분 답변·중단·재개·종료 처리

- [ ] `SKILL.md`의 답변 처리, 사용자 제어와 종료 규칙을 맞춘다.
  - 일부 질문에만 답하면 받은 답변과 추가 조건을 반영하고 나머지는 미답변으로 남긴다. 필요한 미답변은 다시 포함하되 독립적인 질문은 계속한다.
  - 건너뛰거나 보류한 항목을 임의로 확정하지 않는다. 명확한 정정은 반영하고, 뜻이 불분명한 충돌만 질문한다. 해당 답변에 의존하지 않는 논의를 함께 진행할 수 있다.
  - 중단 요청은 최신 기록을 저장하고 질문을 멈추는 것으로 처리한다. 종료와 혼동하지 않는다.
  - 재개 시 기존 기록과 필요한 변경 사항을 확인한다. 질문 번호와 자체 결정 알파벳을 이어서 사용하며, 이미 해결한 질문을 반복하지 않는다.
  - 구현에 필요한 결정이 갖춰지면 남은 사항과 함께 종료 또는 추가 구체화 선택지를 한 번 제안할 수 있다. 사용자가 계속하면 질문을 이어간다.
  - 명시적인 종료 요청이 오면 추가 질문 없이 최종 문서를 작성한다. 미결정 사항을 새 결정으로 채우지 않는다.
  - **완료 기준:** 부분 답변이 인터뷰 전체를 막지 않고, 중단·재개가 기록으로 이어진다. 충분해 보인다는 이유로 자동 종료하지 않으며 종료 요청 후에는 더 묻지 않는다.

### 8. 한국어 최종 기획서를 별도 작성

- [ ] 아래의 최종 기획서 양식에 따라 종료 처리를 구현한다.
  - 원문 질답과 자체 결정 기록은 보존하고, 명시적 종료 시 한국어 최종 기획서를 별도로 만든다.
  - 상단에 목표와 핵심 동작을 적고 본문은 구체적인 할 일 목록 중심으로 작성한다. 남은 미결정 사항과 그 영향도 구분한다.
  - 각 할 일에는 확정된 동작·조건·완료 기준을 유지하고, 확인된 변경 위치와 작업 순서를 함께 적는다. 간결함을 이유로 구현에 필요한 정보를 생략하지 않는다.
  - 사용자 결정과 아직 확인되지 않은 에이전트 가정을 구분한다. 번호나 외부 기록 참조만 남기지 말고 구현에 필요한 결정과 조건을 최종 기획서 본문에 직접 적는다.
  - 대화, 진행 중 기록과 최종 기획서는 한국어만 사용한다. 코드 식별자와 경로는 원래 표기를 유지할 수 있다. 영문 정본이나 별도 한국어 번역본을 만들지 않는다.
  - **완료 기준:** 기록과 최종 기획서가 각각 보존되고, 확정된 구체적인 조건과 남은 미정 사항이 최종 할 일에서 사라지지 않는다. 영어 문서나 `.ko.md` 사본을 별도로 만들지 않는다.

  - **완료 기준:** 이 명세만으로 스킬의 진입점·기본 프롬프트·문서 양식·질문과 결정 처리를 구현할 수 있고, 사용하는 모델에 따라 동작 계약이 바뀌지 않는다.

- [ ] 실행 지침을 수정한 뒤 아래 상황에서 도구 사용 순서, 질문 출력과 저장된 기록을 확인한다. 문서 형식 검사만으로 행동이 검증됐다고 판단하지 않는다.

## 저장 문서 양식

아래는 두 산출물에 필요한 내용을 이 문서 안에서 완결한 양식이다. 제목과 내용은 기획 대상에 맞게 바꾸되, 원문 보존과 구체적인 구현 조건을 생략하지 않는다. 문서를 채우기 위해 아직 정하지 않은 사항을 결정하거나 필수 질문을 미루지 않는다.

### 진행 중 질답 기록

```markdown
# <기획 이름> 질답 기록

목표: <현재 사용자가 설명한 목표>
상태: <진행 중 / 중단 / 종료>

## 회차 1

### 에이전트 응답

<실제로 제시한 임시 결정, 질문 번호·설명·선택지를 원문 그대로 저장>

### 사용자 답변

<번호뿐 아니라 추가 조건과 정정도 포함한 사용자 답변 원문>

### 변경 또는 미정 사항

<있는 경우에만: 대체된 결정과 변경 내용, 미답변·건너뜀·보류·충돌>

## 회차 2

<새 질답과 자체 결정을 같은 방식으로 누적>
```

회차 표시는 읽기 위한 구분이다. 실제 출력 내용과 답변을 보존하는 것이 핵심이며, 매 회차 목표나 전체 요약을 다시 작성할 필요는 없다. 질문 번호와 자체 결정 알파벳은 회차가 바뀌어도 이어진다. 별도의 다음 논의 지점이나 정해진 후속 질문 목록은 필수 항목이 아니다.

### 종료 시 최종 기획서

```markdown
# <기획 이름> 구현 계획

## 목표

<무엇을 누구를 위해 만들고 어떤 결과를 얻으려는지>

## 핵심 동작

<확정된 동작과 주요 조건·예외, 선택한 구현 방식>

## 구현 할 일

- [ ] <구체적인 구현 작업>
  - 동작과 조건: <사용자·입력·처리·결과와 반드시 지킬 조건>
  - 구현 위치: <확인한 파일·함수 또는 신규로 제안하는 위치임을 명시>
  - 순서와 의존성: <먼저 필요한 작업이나 자료가 있는 경우>
  - 완료 기준: <동작이 맞는지 확인할 수 있는 결과 또는 검증 조건>

## 미결정 사항과 남은 가정

<남은 항목과 영향, 사용자 결정인지 에이전트의 임시 가정인지 구분>
<없으면 없음으로 표시>
```

작업 항목의 제목만 읽고도 실제로 해야 할 행동을 알 수 있어야 한다. 예를 들어 로그인 사용자에게만 댓글 등록을 허용하기로 정했다면 “댓글 기능 만들기”가 아니라 “댓글 등록 시 로그인 여부를 확인하고 비회원 요청을 거절하기”로 적고, 로그인·비회원의 기대 결과를 완료 기준에 포함한다. 설명용 예시를 실제 기획의 확정 요구사항으로 복사하지 않는다.

코드가 아직 없거나 위치를 확인할 수 없다면 확인된 파일인 것처럼 쓰지 않는다. 새로 정한 구조는 제안임을 표시하고, 결정되지 않은 부분은 영향과 함께 미정으로 남긴다. 명시적 종료는 미정 사항까지 모두 해결되었다는 뜻이 아니다.

## 완료와 적용 상태

- 스킬의 목적·동작·양식·판단 기준은 이 문서에 정의되어 있으며, 과거 인터뷰의 선택 번호나 다른 문서로 빠진 내용을 보충할 필요가 없다.
- 스킬 구현은 위 할 일과 행동 확인 기준을 충족했을 때 완료로 판단한다. 문서 작성 완료와 스킬 구현 완료를 구분한다.
- 현재 완료된 것은 이 명세의 작성이다. 실제 스킬 파일 수정과 실제 대화를 통한 행동 검증은 아직 수행하지 않았다.
