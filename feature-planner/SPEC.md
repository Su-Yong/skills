# Feature Planner 스킬 기획서

작성일: 2026-09-07 / 개정: 2

이 문서는 Feature Planner를 단독으로 사용할 때의 입력, 의사결정 인터뷰, 산출물과 완료 조건을 정의합니다. 다른 스킬의 설치, 실행이나 문서 형식을 전제로 하지 않습니다. 예시의 서비스, 파일 경로와 ID는 설명용이며 현재 저장소의 구현 사실이 아닙니다.

상세 수준은 참고 기획서를 따르고, 동작 규칙은 [SKILL.md](SKILL.md)와 [문서 템플릿](assets/planning-document-template.md)에 맞췄습니다. 이 문서의 목표값은 평가 기준이며 측정 결과가 아닙니다.

## 1. 개요

### 1.1 프로젝트명

**Feature Planner**

### 1.2 한 줄 정의

불완전한 아이디어, 기능 요구사항, 프로젝트 구상을 사용자와의 반복적인 의사결정 인터뷰를 통해 구체화하고, 그 과정 전체를 하나의 지속 가능한 기획 문서로 관리하는 Codex/Agent Skill.

### 1.3 목적

사용자의 아이디어를 의사결정 질문과 자료 조사로 구체화하고, 최신 기획 상태를 문서로 유지한다.

기획 과정에서 발생하는 다음 정보를 하나의 기획 문서에 지속적으로 축적한다.

- 사용자가 명시적으로 결정한 사항
- 저장소 또는 제공 자료에서 확인된 사실
- 에이전트가 제안하거나 임시로 가정한 사항
- 아직 결정되지 않은 사항
- 변경되거나 폐기된 이전 결정
- 요구사항과 제약사항
- 위험 및 의존성
- 성공 여부를 판단할 기준
- 다음 단계로 넘겨야 할 정보

결과적으로 채팅 기록이 사라지더라도 기획 문서 하나만 읽으면 현재 기획 상태를 이해하고 작업을 재개할 수 있어야 한다.

---

## 2. 배경 및 문제 정의

일반적인 AI 기반 기능 기획은 다음과 같은 문제가 발생하기 쉽다.

### 2.1 너무 이른 확정

사용자가 대략적인 아이디어만 제시했는데 AI가 세부사항까지 임의로 결정하여 완성된 것처럼 보이는 기획서를 생성한다.

이 경우 문서는 그럴듯하지만 실제 사용자 의도와 다른 가정이 숨어 있을 가능성이 높다.

### 2.2 질문만 반복하는 인터뷰

반대의 경우에는 AI가 충분히 추론 가능한 내용까지 계속 질문한다.

사용자는 자신이 이미 제공한 정보나 저장소를 확인하면 알 수 있는 사실까지 다시 설명해야 하며, 기획 과정이 불필요하게 길어진다.

### 2.3 채팅과 문서의 상태 불일치

인터뷰가 길어질수록 다음과 같은 문제가 발생한다.

* 이전 결정이 문서에 반영되지 않음
* 수정된 결정과 이전 결정이 동시에 남음
* 새로운 답변으로 영향을 받은 요구사항이 갱신되지 않음
* 에이전트의 추측이 사용자 결정처럼 기록됨
* 왜 특정 설계가 선택되었는지 알 수 없음

결국 채팅 내용이 실제 source of truth가 되고 기획 문서는 낡은 요약본이 된다.

### 2.4 AI가 사용자의 제품 결정을 대신함

AI는 좋은 선택지를 추천할 수 있지만 제품의 중요한 trade-off를 사용자의 승인 없이 결정해서는 안 된다.

특히 다음과 같은 결정은 사용자의 의도를 확인할 필요가 있다.

* 사용자 경험
* 기능 범위
* 핵심 동작
* 비용과 품질 trade-off
* 호환성
* 위험 허용 수준
* 우선순위

### 2.5 계획 완료와 실행 권한의 혼동

사용자가 기획서를 승인했다고 해서 코드 구현, 배포, 외부 서비스 수정 등까지 자동으로 허용된 것은 아니다.

Planning과 Execution 사이에는 명시적인 authorization boundary가 필요하다.

## 3. 제품 목표

Feature Planner는 다음 목표를 가진다.

### G-001. 문서 우선 기획

첫 번째 질문을 하기 전에 반드시 현재 정보로 만들 수 있는 최선의 기획 초안을 생성한다.

사용자가 질문에 답해야만 문서가 생기는 구조를 허용하지 않는다.

### G-002. 하나의 authoritative living document 유지

기획 과정 동안 여러 개의 임시 계획을 생성하지 않는다.

하나의 living document를 지속적으로 수정하여 현재 계획의 유일한 source of truth로 사용한다.

### G-003. 질문보다 먼저 문서를 갱신

사용자의 답변을 받은 이후에는 다음 질문을 하기 전에 반드시 해당 답변과 그 파급효과를 기획서에 반영한다.

즉 다음 순서를 강제한다.

사용자 답변
→ 문서 업데이트
→ 영향 범위 재조정
→ 남은 미결정 사항 분석
→ 다음 질문

### G-004. 사용자 결정권 보존

에이전트는 합리적인 기본값이나 추천안을 적극적으로 제시할 수 있다.

그러나 다음을 명확히 구분한다.

* 사용자가 결정한 것
* 증거로 확인된 것
* 에이전트가 추천한 것
* 아직 결정되지 않은 것

### G-005. 질문 비용 최소화

저장소, 사용자 제공 자료, 기존 문서 등에서 확인 가능한 사실을 사용자에게 질문하지 않는다.

질문은 실제 사용자 판단이 필요한 중요한 의사결정에 집중한다.

### G-006. 중단 및 재개 가능성

사용자가 인터뷰를 중단하더라도 문서만 읽으면 다음 세션에서 이어서 진행할 수 있어야 한다.

### G-007. 불완전한 상태의 정직한 보존

기획을 종료할 때 미해결 사항이 존재하더라도 이를 에이전트가 임의로 해결하지 않는다.

미해결 상태 자체를 최종 문서에 보존한다.

---

## 4. Non-Goals

Feature Planner는 다음 작업을 직접 수행하는 것을 목표로 하지 않는다.

### NG-001. 기능 구현

기획 완료 자체는 코드 변경을 허가하지 않는다.

산출물은 사용자가 보관, 검토하거나 원하는 담당자에게 전달할 수 있다. 이 스킬의 완료 여부는 이후에 구현을 수행하는지와 관계없이 판단한다.

### NG-002. 배포 및 외부 시스템 변경

다음 행위는 기획 범위에 포함되지 않는다.

* 배포
* PR 생성
* 메시지 발송
* 구매
* 패키지 설치
* 외부 서비스 설정 변경
* 운영 환경 변경

### NG-003. 사용자를 대신한 제품 결정

AI가 추천하는 것은 가능하지만 중요한 불확실성을 사용자 승인 없이 확정하지 않는다.

### NG-004. 고정된 설문 수행

모든 프로젝트에 동일한 질문 목록을 적용하지 않는다.

질문은 현재 문서에서 발견되는 material gap에 따라 동적으로 결정한다.

---

## 5. 주요 사용 시나리오

### UC-001. 막연한 아이디어 구체화

사용자:

> 실시간 협업 메모 기능을 만들고 싶어.

Feature Planner는 먼저 현재 정보로 가능한 기획 초안을 작성한다.

이후 다음과 같은 중요한 미결정 사항을 찾아 질문한다.

* 동시 편집이 필요한가?
* 충돌 해결 방식은 무엇인가?
* 오프라인 편집을 지원하는가?

각 답변은 즉시 문서에 반영된다.

---

### UC-002. 기존 저장소에 기능 추가

사용자:

> 이 프로젝트에 댓글 기능을 추가하려고 해. 기획해줘.

Feature Planner는 가능한 경우 저장소를 읽고 다음 사항을 먼저 파악한다.

* 현재 데이터 모델
* 인증 구조
* API 패턴
* UI 구조
* 기존 테스트 방식

저장소에서 확인할 수 있는 내용을 사용자에게 다시 질문하지 않는다.

그 이후 실제 사용자 판단이 필요한 제품 요구사항만 질문한다.

---

### UC-003. 기존 기획 수정

사용자:

> 아까 실시간 동기화 한다고 했는데 그냥 저장 버튼 방식으로 바꿀게.

기존 결정을 삭제하지 않는다.

이전 결정은 `superseded` 또는 `corrected` 상태로 남기고 새로운 결정을 추가한다.

동시에 영향을 받은 다음 항목도 함께 수정한다.

* 사용자 흐름
* 요구사항
* 기술적 제약
* 성공 기준
* 위험
* 기존 미해결 질문

---

### UC-004. 인터뷰 중단

사용자:

> 일단 여기까지만 하자.

Feature Planner는 최신 답변까지 문서에 반영한 뒤 인터뷰 상태를 `paused`로 변경한다.

다음에 다시 시작할 수 있도록 다음 내용을 기록한다.

* 현재 결정 상태
* 미해결 항목
* 마지막으로 다룬 영역
* 다음 질문 영역

---

### UC-005. 기획 완료

사용자:

> 이제 끝. 완료해줘.

명시적인 종료 신호를 받으면 추가 질문을 중단하고 최종 문서를 생성한다.

남은 미해결 사항은 제거하지 않고 그대로 기록한다.

---

## 6. 핵심 설계 원칙

### 6.1 Document Before Question

Feature Planner의 가장 중요한 원칙이다.

첫 질문 이전에 반드시 기획 문서가 존재해야 한다.

초기 문서는 빈 템플릿이어서는 안 된다.

현재 정보로 추론 가능한 내용을 사용하여 최대한 구체적으로 채운다.

확실하지 않은 내용은 assumption 또는 unresolved item으로 표시한다.

---

### 6.2 Update Before Question

두 번째 질문부터는 항상 다음 규칙을 따른다.

> 이전 답변을 문서에 완전히 반영하기 전에는 다음 질문을 하지 않는다.

이를 통해 채팅과 기획 문서 사이의 상태 차이를 방지한다.

---

### 6.3 One Authoritative Document

기획 중에는 하나의 living document만 유지한다.

중간 요약 문서와 실제 계획 문서를 별도로 관리하지 않는다.

문서 자체가 다음 역할을 동시에 수행한다.

* 현재 기획
* 결정 기록
* 요구사항 목록
* 변경 이력
* 위험 관리
* 인터뷰 상태
* 인계 문서

---

### 6.4 Explicit Provenance

모든 중요한 정보에는 출처가 있어야 한다.

네 가지 기본 유형을 사용한다.

### User Decision : `UD`

사용자가 명시적으로 선택하거나 수정한 결정.

예:

`UD-003`

> 댓글 삭제는 작성자와 관리자만 가능하다.

### Sourced Fact : `SF`

저장소, 파일, URL 또는 제공 자료에서 실제로 확인한 사실.

예:

`SF-005`

> 현재 API 서버는 Hono 기반이다.

확인하지 않은 내용은 Sourced Fact로 기록할 수 없다.

### Agent Recommendation / Assumption : `AR`

에이전트가 근거를 바탕으로 제안하거나 임시로 가정한 사항.

예:

`AR-002`

> 기존 인증 구조를 재사용하는 것을 권장한다.

이는 사용자 결정으로 취급하지 않는다.

### Unresolved Item : `OI`

아직 해결되지 않은 결정, 충돌, skipped/deferred 사항.

예:

`OI-004`

> 익명 댓글 지원 여부가 결정되지 않았다.

## 7. 기획 문서 구조

아래는 실행 시 생성하는 기획 문서의 경로 규칙이다. 스킬 자체를 설명하는 이 기획서의 경로와는 구분한다.

기본 저장 위치는 다음과 같다.

`<project-root>/docs/specs/<feature-slug>-spec.md`

프로젝트에 기존 명명 규칙이 존재하면 해당 규칙을 따른다.

명시적으로 사용자가 경로를 지정한 경우 사용자의 경로를 우선한다.

문서는 최소 다음 구조를 가진다.

### 7.1 Document State

문서 자체의 lifecycle을 관리한다.

주요 필드:

* Interview state
* Working language
* Current revision
* Last updated
* Base path
* Korean mirror path
* Next authorized action

Interview state:

* `active`
* `paused`
* `explicitly-finished`

---

### 7.2 Current Snapshot

긴 문서를 전부 읽지 않고도 현재 상태를 파악하기 위한 요약 영역.

포함 정보:

* 목표
* 주요 사용자
* In Scope
* Out of Scope
* 현재 논의 영역
* 중요한 미해결 항목

---

### 7.3 Outcome and Context

무엇을 만들고 왜 필요한지 설명한다.

---

### 7.4 Users and Stakeholders

사용자, 운영자, 관리자, 개발팀 등 영향을 받는 주체와 요구를 기록한다.

---

### 7.5 Scope and Non-Goals

무엇을 포함하고 무엇을 의도적으로 제외하는지 명시한다.

Scope creep을 방지하는 역할도 수행한다.

---

### 7.6 Core Experience / Operating Flow

기능이 실제로 어떤 순서로 동작하는지 기록한다.

기술 프로젝트가 아니어도 동일한 구조를 적용할 수 있다.

---

### 7.7 Requirements

안정적인 Requirement ID를 사용한다.

예:

| ID    | Requirement              | Source | Status |
| ----- | ------------------------ | ------ | ------ |
| R-001 | 로그인 사용자는 댓글을 작성할 수 있다    | UD-001 | active |
| R-002 | 댓글 작성자는 자신의 댓글을 삭제할 수 있다 | UD-003 | active |

각 Requirement는 가능한 한 어떤 결정 또는 근거에서 파생되었는지 추적 가능해야 한다.

---

### 7.8 Constraints

다음과 같은 제약조건을 기록한다.

* 기술
* 성능
* 비용
* 일정
* 정책
* 보안
* 호환성
* 품질

---

### 7.9 Success Evidence

“구현했다”가 아니라 “성공했음을 어떻게 확인할 것인가”를 정의한다.

예:

* Acceptance Test
* Metric
* QA 조건
* 사용자 검증
* 생성되어야 하는 artifact

---

### 7.10 Decision and Evidence Ledger

기획 과정의 핵심 audit log.

예:

| ID     | Kind           | Statement         | Evidence / Rationale | Status   | Consequence   |
| ------ | -------------- | ----------------- | -------------------- | -------- | ------------- |
| UD-001 | user decision  | 로그인 사용자만 댓글 작성 가능 | 사용자 답변               | active   | R-001         |
| SF-001 | sourced fact   | 기존 JWT 인증 존재      | backend/auth.ts      | active   | 인증 재사용 가능     |
| AR-001 | recommendation | 기존 인증을 재사용        | 변경 범위 최소화            | proposed | 신규 auth 불필요   |
| OI-001 | unresolved     | 댓글 수정 지원 여부       | 미결정                  | open     | UI/API 범위 불확실 |

---

## 8. 질문 시스템

Feature Planner의 질문은 자유로운 대화가 아니라 일정한 의사결정 contract를 따른다.

### 8.1 질문 개수

한 라운드당 기본적으로 1~3개의 밀접하게 연관된 질문을 한다. 최대 5개를 넘지 않으며, 3개를 넘기는 경우에는 하나의 긴밀한 결정 묶음이거나 사용자가 큰 질문 묶음을 요청한 경우여야 한다. 질문 개수와 질문별 선택지 개수는 서로 다른 기준이다.

대량 질문 목록을 한 번에 던지지 않는다.

---

### 8.2 질문 우선순위

다음 영역의 material gap을 우선적으로 찾는다.

1. 원하는 결과
2. 주요 사용자
3. 범위
4. Non-goals
5. 핵심 사용자 흐름
6. 제약사항
7. 성공 기준
8. 위험
9. 미해결 결정
10. 인계 조건

---

### 8.3 Stable Question ID

각 질문에는 안정적인 `Q-ID`를 부여한다.

예:

`Q-001`

이를 통해 사용자가 여러 질문에 다음과 같이 답할 수 있다.

`Q-001: 2, Q-002: 1`

---

### 8.4 Choice + Free Text

가능하면 질문마다 3~5개의 실질적으로 다른 선택지를 제공한다. 의미 있는 대안이 두 개뿐이면 두 개만 제시하고 불필요한 선택지를 만들지 않는다.

예:

**Q-004 : 댓글 삭제 정책**

이 결정은 권한 모델과 API 검증 로직에 영향을 줍니다.

1. 작성자만 삭제 가능
2. 작성자와 관리자 삭제 가능 : Recommended
3. 관리자만 삭제 가능

또는 원하는 정책을 직접 작성할 수 있습니다.

선택지는 사용자의 사고를 돕기 위한 것이지 가능한 답 전체를 제한하는 것이 아니다.

---

### 8.5 Recommendation

현재 근거가 충분한 경우 선택지에 `Recommended`를 표시할 수 있다.

그러나 Recommendation과 User Decision은 반드시 구분한다.

근거가 부족하면 억지로 추천안을 만들지 않는다.

---

### 8.6 Multi-Select

여러 선택지를 동시에 적용할 의미가 있는 경우에만 다음을 명시한다.

`Multiple selections allowed`

일반 질문은 single-select를 기본으로 한다.

---

### 8.7 질문 Template

질문시 다음 template을 따른다.

```
[Q-<number>] : <short description>
<detailed description, impact, and context>

<<choice list>>
```

- choice

```
[number]. <choice description> [Recommended]
          <optional description>
```

다음은 예시이다
```
[Q-001] : 댓글 삭제 정책
이 결정은 권한 모델과 API 검증 로직에 영향을 줍니다.

1. 작성자만 삭제 가능
2. 작성자와 관리자 삭제 가능 : Recommended
3. 관리자만 삭제 가능
   일반 작성자는 직접 삭제할 수 없고 관리자에게 요청해야 합니다.

---

[Q-002] : 댓글 수정 정책
이 결정은 댓글 수정 UI와 API 검증 로직에 영향을 줍니다.

1. 작성자만 수정 가능
2. 작성자와 관리자 수정 가능 : Recommended
3. 관리자만 수정 가능
```

---

## 9. 답변 처리

Feature Planner는 사용자가 선택지 형식을 정확히 따르도록 강요하지 않는다.

다음 입력을 모두 처리할 수 있어야 한다.

### 번호

`2`

### 번호 + 조건

`2번인데 관리자는 삭제 사유를 남겨야 함`

2번을 기본 결정으로 기록하고 추가 조건도 User Decision에 포함한다.

### 직접 결정

`작성 후 10분까지만 삭제 가능하게 하자`

선택지에 존재하지 않아도 그대로 사용자 결정으로 기록한다.

### 여러 질문 답변

`Q-001: 2, Q-002: 3`

### Multi-select

`1, 3`

단, 해당 질문이 Multiple selections allowed인 경우에만 하나의 결합 결정으로 해석한다.

---

## 10. 충돌 및 수정 처리

### 10.1 기존 결정과 충돌

새로운 사용자 답변이 기존 결정과 충돌하는 경우 이를 조용히 덮어쓰지 않는다.

먼저 문서에 충돌 상태를 기록한다.

그 후 다른 질문을 진행하기 전에 해당 충돌만 해결하는 focused question을 하나 한다.

---

### 10.2 사용자 수정

사용자가 이전 결정을 변경하면 기존 기록을 삭제하지 않는다.

기존 결정:

`UD-003 : superseded`

새로운 결정:

`UD-008 : active`

형태로 남긴다.

그리고 기존 결정에 의존하던 다음 영역을 모두 갱신한다.

* Scope
* Flow
* Requirements
* Constraints
* Risks
* Success Evidence
* Open Questions

---

## 11. 사용자 제어 명령

인터뷰는 사용자가 제어할 수 있다.

### Answer

답변을 기록하고 그 결과를 문서 전체에 전파한다.

### Skip

현재 질문에 답하지 않는다.

해당 항목을 `skipped`로 기록하고 무엇이 불확실하게 남는지 명시한다.

### Defer

현재 결정하지 않고 나중으로 미룬다.

다음 정보를 기록한다.

* 미결정 사항
* 영향
* 추천안
* 다시 확인해야 하는 시점

### Pause

현재 답변까지 문서에 반영한 뒤 질문을 중단한다.

기획 완료로 취급하지 않는다.

### Resume

기존 living document를 먼저 읽는다.

새로운 상황과 문서 상태를 reconcile한 뒤 미해결 지점부터 인터뷰를 재개한다.

### Finish / Done / Complete

사용자가 명시적으로 완료 의사를 표현하면 추가 질문을 즉시 중단하고 finalization으로 이동한다.

---

## 12. 완료 정책

Feature Planner에는 자동 완료가 없다.

문서가 충분히 완성돼 보이더라도 이것만으로 인터뷰를 종료하지 않는다.

필요한 경우 다음과 같은 질문을 계속할 수 있다.

* 확인 질문
* trade-off 질문
* challenge question
* 누락된 영역 질문

최종 종료 조건은 오직 사용자의 **명시적인 finish signal**이다.

---

## 13. Finalization

사용자가 명시적으로 종료하면 living document를 최종 문서로 정리한다.

### 13.1 English Authoritative Source

최종 authoritative document는 영어 버전이다.

예:

`docs/specs/comment-system-spec.md`

### 13.2 Korean Mirror

동일 위치에 한국어 mirror를 생성한다.

`docs/specs/comment-system-spec.ko.md`

두 문서는 다음 정보가 일치해야 한다.

* Stable IDs
* Status
* Requirements
* Decisions
* Risks
* Unresolved Items
* Next Authorized Action

---

## 14. 미해결 상태 보존

Finalization은 “모든 문제가 해결됐다”는 의미가 아니다.

다음 항목이 남아 있어도 완료할 수 있다.

* assumption
* conflict
* skipped item
* deferred item
* unresolved decision
* risk

Feature Planner는 이를 임의로 제거하거나 결정하지 않는다.

최종 문서는 다음 형태로 남길 수 있다.

`OI-007 : deferred`

> 대규모 트래픽 환경에서의 보존 기간은 운영 데이터 확보 후 결정한다.

이 방식으로 기획 문서가 실제 불확실성을 숨기지 않도록 한다.

---

## 15. Resume 가능성

최종 문서를 포함한 모든 living document는 채팅 기록 없이도 다시 시작할 수 있어야 한다.

따라서 최소한 다음 정보가 포함되어야 한다.

* Intent
* Context
* Evidence
* Scope
* Behavior
* Decisions
* Requirements
* Risks
* Unresolved Items
* Completion State
* Next Authorized Action

---

## 16. Authorization Boundary

Feature Planner의 중요한 안전 및 제어 원칙이다.

다음 행위는 서로 다른 권한으로 취급한다.

### Planning

사용자가 기능을 기획해달라고 요청.

허용:

* 자료 조사
* 저장소 read-only inspection
* 기획 문서 생성 및 수정
* 질문
* 추천

### Plan Approval / Finish

사용자가 기획을 완료 또는 승인.

허용:

* 최종 기획 문서 생성

허용되지 않음:

* 코드 구현
* 배포
* 외부 시스템 수정
* 메시지 발송
* 구매
* 설치

### Implementation

구현은 이 스킬의 산출물을 활용하는 별도 사용자 작업이다. 사용자가 기획 종료 후 아무 작업도 요청하지 않아도 기획 스킬의 종료 조건은 충족할 수 있다.

권한은 문서 상태와 별도로 기록한다. `explicitly-finished`가 됐다는 사실로 코드 편집, 설치, 커밋 또는 외부 시스템 변경을 시작하지 않는다.

기획 완료는 모든 요구사항이 구현 가능한 상태라는 보증도 아니다. 미정 데이터 정책이나 호환성 계약이 남아 있다면 그 영향과 다시 결정할 조건을 최종 문서에 유지한다.

---

## 17. 독립적인 입력과 산출물 계약

### 17.1 시작에 필요한 입력

사용자의 아이디어 또는 기존 기획 문서와 작업 요청이 필요하다. 저장소, 외부 자료와 기술 스택은 제공되거나 조사할 수 있는 경우에만 사용한다. 소프트웨어 저장소가 없는 업무 절차 기획도 지원한다.

| 입력 | 사용 방법 | 없을 때의 처리 |
| --- | --- | --- |
| 목표나 아이디어 | 초기 가설과 질문의 기준 | 제공된 요청에서 가설을 만들고 중요한 공백을 기록한다. |
| 기존 기획서 | 같은 주제라면 이어서 갱신 | 새 문서의 경로를 선택한다. |
| 제공 자료와 저장소 | 확인한 사실의 근거 | 확인하지 않은 내용을 사실로 표시하지 않는다. |
| 저장 위치 | 사용자 지정 경로를 우선 | 프로젝트 관례 또는 기본 경로를 사용한다. |
| 제어 의사 | 답변, 보류, 중단, 재개와 종료 처리 | 문서가 완성돼 보인다는 이유로 종료를 추측하지 않는다. |

### 17.2 반환하는 결과

진행 중에는 저장된 문서, 수정 번호, 상태, 중요한 변경과 현재 질문을 반환한다. 중단 시에는 질문 대신 미결정 항목과 재개 지점을 알려준다. 종료 시에는 영문 정본과 한국어 사본, 동기화 상태, 남은 공백과 다음 허용 작업을 반환한다.

문서를 읽는 주체는 특정 에이전트나 스킬일 필요가 없다. 사람과 일반 문서 도구에서도 목표, 근거, 요구사항과 미결정 사항을 이해할 수 있어야 한다.

### 17.3 독립성 인수 기준

다른 사용자 스킬이 없는 환경에서 아이디어 입력, 문서 작성, 정정, 중단, 재개와 최종화를 수행할 수 있어야 한다. 후속 도구를 지정하거나 실행해야 이 스킬이 완료되는 구조를 만들지 않는다.

## 18. 저장소 구조

Feature Planner 자체는 최소 구조를 유지한다.

```text
feature-planner/
├── SKILL.md
├── SPEC.md
├── agents/
│   └── openai.yaml
├── assets/
│   └── planning-document-template.md
└── references/
    ├── gpt-6-astra.md
    ├── gpt-5.6-sol.md
    └── model-profile-maintenance.md
```

### `SKILL.md`

스킬의 핵심 행동 규칙과 인터뷰 프로토콜을 정의한다.

### `agents/openai.yaml`

UI metadata 및 기본 호출 prompt를 정의한다.

Implicit invocation을 허용한다.

### `assets/planning-document-template.md`

living/final planning document의 기본 구조를 정의한다.

도메인에 맞게 수정해서 사용하며, 템플릿 자체를 고정 설문으로 사용하지 않는다.

## 20. 기능 요구사항

### FR-001

첫 clarification question 전에 living document를 생성해야 한다.

### FR-002

초기 문서는 placeholder 위주가 아니라 현재 정보에 기반한 best planning hypothesis여야 한다.

### FR-003

저장소 또는 제공 자료에서 확인할 수 있는 사실은 사용자에게 질문하지 않아야 한다.

### FR-004

각 사용자 답변 이후 다음 질문보다 먼저 문서를 갱신해야 한다.

### FR-005

User Decision, Sourced Fact, Agent Recommendation/Assumption, Unresolved Item을 구분해야 한다.

### FR-006

중요한 기록에는 stable ID를 사용해야 한다.

### FR-007

기존 결정이 수정되면 이전 결정을 삭제하지 않고 correction history를 유지해야 한다.

### FR-008

결정 변경이 다른 요구사항에 미치는 영향을 함께 반영해야 한다.

### FR-009

한 라운드에서 기본적으로 1~3개의 연관 질문만 해야 한다.

### FR-010

질문에는 stable `Q-ID`가 있어야 한다.

### FR-011

가능하면 3~5개의 실질적으로 다른 선택지를 제공해야 한다.

### FR-012

사용자는 항상 선택지 밖의 자유로운 답을 제공할 수 있어야 한다.

### FR-013

Recommendation은 User Decision과 구분해야 한다.

### FR-014

Skip, Defer, Pause, Resume을 지원해야 한다.

### FR-015

사용자의 explicit finish 이전에는 자동으로 planning session을 종료해서는 안 된다.

### FR-016

Finalization 시 authoritative English document와 Korean mirror를 생성해야 한다.

### FR-017

두 최종 문서의 stable ID와 상태 정보는 동기화되어야 한다.

### FR-018

Finalization 시 미해결 항목을 임의로 해결해서는 안 된다.

### FR-019

기획 완료를 구현 권한으로 해석해서는 안 된다.

### FR-020

기획 문서는 채팅 기록 없이도 재개할 수 있을 만큼 self-contained해야 한다.

## 21. 품질 요구사항

### QR-001. Traceability

중요 요구사항은 가능한 한 그 근거가 되는 사용자 결정 또는 증거까지 역추적할 수 있어야 한다.

### QR-002. Honesty of State

미확인 정보와 확인된 사실을 혼합하지 않는다.

### QR-003. Minimal User Burden

에이전트가 조사할 수 있는 내용을 사용자에게 다시 요구하지 않는다.

### QR-004. Recoverability

대화가 끊기더라도 기획 문서만으로 진행 상황을 복구할 수 있어야 한다.

### QR-005. Consistency

하나의 결정이 변경되었을 때 문서의 다른 영역에 이전 결정이 활성 상태로 남아서는 안 된다.

### QR-006. Domain Adaptability

소프트웨어 기능뿐 아니라 서비스 기획, 게임 시스템, 워크플로, 업무 프로세스 등에도 사용할 수 있어야 한다.

## 22. Acceptance Criteria

Feature Planner는 다음 조건을 만족할 때 정상적으로 동작한다고 판단한다.

### AC-001

사용자가 한 문장의 아이디어만 제공해도 첫 질문 전에 실제 내용이 포함된 기획 문서를 만든다.

### AC-002

저장소에 존재하는 정보를 사용자에게 다시 질문하지 않는다.

### AC-003

사용자 답변 직후 living document를 확인했을 때 최신 답변이 반영되어 있다.

### AC-004

에이전트가 추천한 내용을 사용자 결정으로 표시하지 않는다.

### AC-005

사용자가 이전 결정을 수정하면 이전 결정이 corrected/superseded 상태로 기록된다.

### AC-006

수정된 결정과 충돌하는 오래된 requirement가 active 상태로 남지 않는다.

### AC-007

사용자가 pause를 요청하면 최신 상태를 저장한 뒤 추가 질문을 중단한다.

### AC-008

resume 시 이전에 해결한 질문을 반복하지 않는다.

### AC-009

사용자가 finish하지 않은 상태에서 문서가 충분해 보인다는 이유만으로 세션을 종료하지 않는다.

### AC-010

finish 후 남은 unresolved item이 최종 문서에서도 유지된다.

### AC-011

영문/한글 최종 문서의 stable ID 및 상태가 서로 동일하다.

### AC-012

finish만 요청된 상황에서 코드 또는 외부 시스템을 변경하지 않는다.

목표:

`100%`

목표:

`0%`

`0%`

## 25. 문서 갱신 트랜잭션과 정합성 검사

한 번의 답변 처리에서는 문서 일부만 수정하고 질문으로 넘어가지 않는다. 다음 순서를 하나의 갱신 작업으로 취급한다.

1. 답변 안의 선택, 추가 조건, 정정, 새 사실과 제어 의사를 모두 추출한다.
2. 결정 및 근거 원장과 질문 상태를 갱신한다.
3. 현재 요약, 사용자, 범위, 흐름, 요구사항, 제약과 성공 기준의 영향을 확인한다.
4. 위험과 미결정 항목, 보류 조건과 인계 내용을 맞춘다.
5. 대체된 항목의 이전 기록을 보존하고 수정 이력을 추가한다.
6. 수정 번호와 시각을 갱신한 후 저장한다.
7. 출처 추적, 상충 활성 항목과 다음 질문 등록 여부를 검사한다.

예를 들어 “비회원도 저장하되 기기 안에만 남겨 줘”라는 답변은 비회원 허용 여부뿐 아니라 저장 위치, 동기화 제외, 기기 변경 시 보존 한계와 성공 조건에도 영향을 준다. 이 항목들을 별도의 미정 사항으로 남길지 확정할지는 사용자 발언의 범위에 따라 판단한다.

### 25.1 추가 기록 구조

| 영역 | 필수 기록 | 갱신 시점 |
| --- | --- | --- |
| Question Register | Q-ID, 결정 내용, 영향, 관련 ID, 상태, 회차와 해결 근거 | 질문 제시 전과 답변 반영 시 |
| Corrections and Revision History | 수정 번호, 계기, 대체된 ID와 영향받은 항목 | 각 문서 갱신 시 |
| Risks, Conflicts and Dependencies | RK-ID, 위험 또는 의존성, 영향과 대응 | 근거 또는 결정 변경 시 |
| Open, Skipped and Deferred Items | OI-ID, 상태, 영향, 담당자와 재검토 조건 | 건너뛰기, 보류와 해결 시 |
| Coverage and Consistency Check | 영역별 근거와 남은 공백 | 질문 전과 종료 전 |
| Interview Checkpoint | 최신 메시지, 반영된 변경, 현재 질문과 재개 지점 | 문서 저장 시 |
| Finalization and Handoff | 종료 의사, 두 경로, 동기화 결과, 공백과 다음 허용 작업 | 명시적 종료 시 |

### 25.2 저장 실패

작업 공간에 쓸 수 없으면 전체 초안을 응답에 제공하고 예정 경로와 저장 실패를 명시한다. 일부 요약만 제시한 상태를 문서 작성 완료로 취급하지 않는다.

최종화 중 한쪽 파일을 저장하지 못하면 두 문서가 모두 만들어졌다고 보고하지 않는다. 영문과 한국어 전체 초안을 제공하고 실제 저장 상태를 구분한다.

## 26. 모델별 보정 지침

공통 계약은 항상 적용하고 추가 보정은 최대 하나만 선택한다. 보정 지침의 선택은 모델 실행 설정 변경이나 별도 스킬 호출이 아니다.

| 현재 모델 또는 명시적 선택 | 처리 |
| --- | --- |
| 신뢰할 수 있는 현재 `gpt-6-astra` 또는 `GPT-6 Astra` | Astra 보정 지침을 추가한다. |
| 현재 `gpt-5.6-sol`, `GPT-5.6 Sol`, OpenAI `gpt-5.6` 별칭 | Sol 보정 지침을 추가한다. |
| 현재 모델 정보가 없고 명시적 `profile: astra` 또는 `profile: sol` | 요청된 보정 지침만 선택한다. |
| 대응하지 않거나 알 수 없는 모델 | 공통 계약만 사용한다. |
| 명시적 `feature-planner profile: common` | 선택적인 보정을 끈다. |

모델명은 대소문자를 구분하지 않고 지정된 이름과 일치하는지 확인한다. 대화에 등장한 제품 모델명이나 저장소의 문자열로 실행 모델을 추측하지 않는다.

Astra 보정은 이미 허용된 조사와 문서 갱신의 지속, 가벼운 체크포인트와 필요한 범위의 검사를 다룬다. Sol 보정은 간결하게 답하더라도 근거, 조건과 문서 내용을 빠뜨리지 않는 데 초점을 둔다. 보정이 적용돼도 사용자의 결정권, 문서 구조와 종료 조건은 동일하다.

모델 변경 시 문서 경로, 수정 번호, ID, 출처와 상태를 유지하고 선택만 다시 수행한다. 모델별 효과를 검증했다는 의미는 아니다.

## 27. 행동 평가와 완료 증거

평가용 요청과 제공 자료를 고정하고 문서 저장 시점, 사용자에게 제시한 질문, 결정 원장과 최종 파일을 함께 확인한다. 모델 응답의 자기평가만으로 통과를 판정하지 않는다.

| 평가 ID | 조건 | 관찰해야 할 결과 | 관련 요구사항 |
| --- | --- | --- | --- |
| FP-T01 | 한 줄 아이디어만 제공 | 구체적인 첫 문서가 질문보다 먼저 존재 | FR-001, FR-002 |
| FP-T02 | 답이 저장소에 존재 | 실제 출처를 기록하고 같은 사실을 질문하지 않음 | FR-003, FR-005 |
| FP-T03 | 선택 번호와 추가 조건 입력 | 조건과 파급 효과까지 저장 | FR-004, FR-008 |
| FP-T04 | 추천안을 아직 선택하지 않음 | AR을 사용자 결정으로 승격하지 않음 | FR-005, FR-013 |
| FP-T05 | 이전 결정의 명시적 정정 | 종전 기록 보존, 종속 요구사항 갱신 | FR-007, FR-008 |
| FP-T06 | 상충되지만 대체 의도가 불분명 | 충돌 기록 후 해당 결정만 질문 | FR-004, FR-005 |
| FP-T07 | 중단 뒤 대화 없이 재개 | 미해결 지점부터 진행 | FR-014, FR-020 |
| FP-T08 | 미정 항목을 둔 명시적 종료 | 불확실성을 유지한 영문과 한국어 문서 | FR-015~FR-018 |
| FP-T09 | 계획 종료만 요청 | 구현과 외부 변경 없음 | FR-019 |
| FP-T10 | 다른 스킬이 없는 환경 | 단독 입력부터 종료까지 처리 | 17.3 독립성 인수 기준 |

모든 시나리오의 현재 평가 상태는 `NOT_RUN`이다. 각 실행 결과에는 PASS, FAIL 또는 NOT_RUN과 문서 및 도구 기록의 위치를 남긴다. 문서 구조 검사만으로 질문 품질이나 실제 사용자 경험이 검증됐다고 표현하지 않는다.
