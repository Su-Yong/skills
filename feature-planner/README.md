# Feature Planner

아이디어를 질문과 답변으로 구체화하고, 결정과 수정 이력을 하나의 기획 문서에 계속 반영하는 스킬입니다.

## 언제 사용하나요?

- 만들고 싶은 기능은 있지만 사용자, 범위와 동작을 아직 정하지 못했을 때
- 기존 프로젝트에 추가할 기능을 코드 변경 전에 구체화하고 싶을 때
- 이미 작성한 기획의 결정을 바꾸고 관련 요구사항까지 수정하고 싶을 때
- 여러 차례 대화를 이어가도 결정 이유와 미정 항목을 보존하고 싶을 때
- 서비스, 게임 시스템이나 업무 절차를 기획할 때

이 스킬의 결과는 기획 문서입니다. 코드를 구현하거나 배포하는 작업은 수행 범위에 포함하지 않습니다.

## 빠르게 시작하기

스킬을 사용할 수 있는 에이전트 환경에서 작업할 프로젝트나 문서 폴더를 열고 다음처럼 요청합니다.

```text
$feature-planner
팀에서 사용할 회의실 예약 서비스를 기획해 줘.
우선 사내 구성원만 사용하는 작은 서비스로 시작하고 싶어.
```

스킬은 제공 자료를 확인하고 현재 정보로 작성할 수 있는 초안을 먼저 저장합니다. 이후 중요한 미결정 사항을 질문합니다. 사용자가 답하면 관련 결정, 요구사항과 흐름을 문서에 반영한 뒤 다음 질문으로 넘어갑니다.

질문은 기본적으로 한 회차에 1~3개입니다. 추천 선택지를 제시하더라도 사용자가 선택하기 전까지는 제안으로 기록합니다.

### 예시 확인

위 요청 이후의 대화 예시입니다. 질문과 선택지는 현재 기획 내용에 따라 달라집니다.

```text
Feature Planner:
  회의실 예약 서비스의 초안을 docs/specs/room-booking-spec.md에 저장했습니다.
  현재 문서는 수정 1, 인터뷰 상태는 active입니다.
  사내 구성원용 예약 서비스를 목표로 기록했고, 예약 확정 방식은 미정입니다.

  [Q-001] 예약은 어떻게 확정할까요?
  이 결정에 따라 승인 대기 화면과 관리자의 처리 업무가 달라집니다.

  1. 빈 시간이면 즉시 확정
  2. 관리자가 승인한 뒤 확정

  번호로 답하거나 원하는 방식을 직접 설명해 주세요.

사용자:
  1번으로 할게. 대신 한 번에 최대 2시간까지만 예약할 수 있게 해 줘.

Feature Planner:
  즉시 확정과 최대 2시간 제한을 사용자 결정으로 기록했습니다.
  예약 흐름, 시간 제한 요구사항과 검증 기준을 반영해 수정 2로 저장했습니다.
  다음은 예약 취소 권한을 정할 차례입니다.

  [Q-002] 누가 예약을 취소할 수 있나요?
  이 결정은 취소 버튼의 표시 대상과 권한 검사에 영향을 줍니다.

  1. 예약자만 취소 가능
  2. 예약자와 관리자 모두 취소 가능
  3. 관리자만 취소 가능

  번호로 답하거나 다른 정책을 적어 주세요.

사용자:
  2번. 관리자가 취소할 때는 사유를 남겨야 해.
  오늘은 여기서 중단하고 다음에 이어가자.

Feature Planner:
  예약자와 관리자의 취소 권한, 관리자 취소 사유 기록을 반영했습니다.
  취소 흐름과 요구사항, 검증 기준을 갱신해 수정 3으로 저장했습니다.
  인터뷰 상태는 paused이며, 반복 예약 허용 여부는 미정으로 남겼습니다.
  다음에는 이 문서를 읽고 반복 예약 정책부터 이어갈 수 있습니다.
```

### 처음 요청할 때 알려주면 좋은 내용

만들고 싶은 내용을 간단하게 설명합니다. 그 내용을 구체화하는데 도움되는 자료나 내용, 문서등을 추가로 제공하면 좋습니다.

저장소에서 확인할 수 있는 기술 정보는 스킬이 먼저 조사합니다. 확정하지 않은 내용은 가정이나 미결정 항목으로 구분합니다.

## 사용 예시와 시나리오

### 1. 기존 프로젝트의 새 기능 기획

```text
$feature-planner
현재 프로젝트에 게시글 북마크 기능을 추가하려고 해.
기존 로그인과 게시글 구조를 확인해서 기획해 줘.
북마크 폴더와 공개 공유는 이번 범위에서 제외해 줘.
기획서는 docs/plans/bookmark-spec.md에 작성해 줘.
```

기존 자료를 근거로 초안을 만들고, 북마크 사용 대상이나 저장 정책처럼 제품 판단이 필요한 항목을 질문합니다. 프로젝트 코드는 수정하지 않습니다.

### 2. 질문에 조건을 덧붙여 답하기

```text
Q-001: 2번으로 할게. 다만 관리자가 예약을 취소할 때는 사유를 남겨야 해.
Q-002: 주말 예약은 허용하지 않을게.
```

선택 번호뿐 아니라 추가 조건도 결정에 포함합니다. 실제 질문 ID와 선택지 번호를 사용하면 됩니다. 제시된 선택지에 원하는 답이 없다면 자유롭게 정책을 설명할 수 있습니다.

### 3. 이전 결정 변경하기

```text
아까 관리자 승인 후 예약이 확정된다고 했는데,
빈 시간이라면 바로 확정되는 방식으로 바꿀게.
관련 흐름과 요구사항도 함께 수정해 줘.
```

이전 결정을 삭제하지 않고 대체된 기록으로 남깁니다. 승인 대기 흐름, 알림, 취소 정책과 검증 기준 등 영향을 받는 항목도 함께 갱신합니다.

### 4. 결정을 보류하거나 대화 중단하기

```text
반복 예약 정책은 다음 운영 회의 이후에 정할게.
그 항목은 보류하고, 오늘 인터뷰는 중단해 줘.
지금까지의 내용과 다음에 이어갈 지점을 저장해 줘.
```

보류 항목의 영향과 재검토 시점을 기록하고 인터뷰를 `paused`로 저장합니다. 중단은 기획 완료로 처리하지 않습니다.

### 5. 기존 문서에서 재개하기

```text
$feature-planner
docs/plans/room-booking-spec.md를 읽고 기획을 이어가자.
반복 예약은 최대 4주까지만 허용하기로 정했어.
이 결정을 반영하고 남은 항목을 확인해 줘.
```

문서를 먼저 읽고 최신 결정을 반영합니다. 이미 해결한 질문은 반복하지 않고 남은 지점부터 이어갑니다.

### 6. 미정 항목을 남긴 채 종료하기

```text
기획은 여기서 완료해 줘.
모바일 알림 정책은 미정 상태로 남겨 두고,
최종 영문 문서와 한국어 문서를 정리해 줘.
```

명확한 종료 요청을 받으면 추가 질문을 멈춥니다. 미정 항목을 임의로 결정하지 않고 최종 문서에도 유지합니다.

### 7. 소프트웨어가 아닌 업무 절차 기획

```text
$feature-planner
신규 입사자의 첫 주 온보딩 절차를 기획해 줘.
인사 담당자, 팀 리더, 신규 입사자가 해야 할 일을 구분하고 싶어.
제공한 체크리스트를 확인하고 빠진 의사결정부터 질문해 줘.
```

저장소나 기술 스택이 없어도 제공한 자료와 목표를 바탕으로 사용자, 절차, 책임과 성공 기준을 구체화합니다.

## 결과 문서는 어디에 생기나요?

사용자가 지정한 경로를 우선하고, 지정하지 않았다면 프로젝트 관례를 따릅니다. 둘 다 없으면 다음 형식을 사용합니다.

```text
docs/specs/<feature-slug>-spec.md
```

기획 중에는 사용자의 작업 언어로 같은 문서를 계속 갱신합니다. 명시적으로 종료하면 기본 파일은 영문 정본으로 정리하고 한국어 사본을 함께 만듭니다.

```text
docs/specs/room-booking-spec.md
docs/specs/room-booking-spec.ko.md
```

## 문서에서 확인할 항목

| 표시 | 의미 |
| --- | --- |
| `UD-*` | 사용자가 명시적으로 결정한 내용 |
| `SF-*` | 파일이나 자료에서 실제로 확인한 사실 |
| `AR-*` | 에이전트의 추천 또는 가정 |
| `OI-*` | 미정, 충돌, 건너뛰거나 보류한 항목 |
| `R-*` | 요구사항 |
| `Q-*` | 결정할 질문 |
| `RK-*` | 위험과 의존성 |

기획서에는 범위, 흐름, 요구사항, 성공 기준, 결정과 수정 이력, 위험, 미결정 사항과 재개 지점이 포함됩니다. 영문과 한국어 최종 문서의 ID와 상태는 같아야 합니다.

## 자주 생기는 상황

| 상황 | 해결법 |
| --- | --- |
| 초안이 완성돼 보이는데 질문이 계속됨 | 문서의 충실도만으로 인터뷰를 종료하지 않습니다. 끝내려면 기획 완료 의사를 명확히 전달합니다. |
| 어떤 질문에 지금 답할 수 없음 | 건너뛰거나 보류할 수 있습니다. 영향과 미정 상태를 문서에 남깁니다. |
| 질문을 하지 않음 | 질문을 해달라고 요청합니다. |
| 질문을 하나만 받음 | 질문을 여러개 해달라고 요청합니다. |

## 선택 사항: 공통 규칙만 사용하기

이 스킬은 모델별로 추가 지시가 적용되어있습니다. 만약 모델별 지시를 제외하고 기본 규칙만 사용하려면 다음처럼 요청하면 됩니다.

```text
$feature-planner
feature-planner profile: common
이 아이디어를 기획해 줘.
```

현재 `profile`은 `gpt-5.6 sol`, `gpt-6-astra` 모델만 지원하며 나머지 모델은 자동으로 `common` 프로필을 사용합니다.
