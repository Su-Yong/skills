# Feature Planner

상세한 질문을 묶어서 제시하고, 아이디어와 구현 방법을 함께 좁혀 가는 스킬입니다. 질문과 답변 원문은 한국어 질답 기록에 보존하고, 종료 시 구체적인 구현 계획을 별도로 작성합니다.

## 언제 사용하나요?

- 만들고 싶은 기능은 있지만 사용자, 범위, 동작과 구현 방법을 아직 정하지 못했을 때
- 기존 프로젝트에 추가할 기능의 구현 위치와 작업 순서를 코드 변경 전에 구체화하고 싶을 때
- 이미 작성한 기획의 결정을 바꾸고 관련 요구사항까지 수정하고 싶을 때
- 여러 차례 대화를 이어가도 결정 이유와 미정 항목을 보존하고 싶을 때
- 서비스, 게임 시스템이나 업무 절차를 기획할 때

항상 구현 기획을 수행하며, 아이디어 구체화와 구현 방법 결정을 별도 모드나 단계로 나누지 않습니다. 결과는 질답 기록과 구현 계획입니다. 기획 승인이나 종료만으로 코드 작성, 설치 또는 배포를 실행하지 않습니다.

## 빠르게 시작하기

스킬을 사용할 수 있는 에이전트 환경에서 작업할 프로젝트나 문서 폴더를 열고 다음처럼 요청합니다.

```text
$feature-planner
팀에서 사용할 회의실 예약 서비스를 기획해 줘.
우선 사내 구성원만 사용하는 작은 서비스로 시작하고 싶어.
```

스킬은 첫 질문에 필요한 문맥만 짧게 확인하고 질문을 시작합니다. 완성된 초안이나 전체 자료 조사를 먼저 요구하지 않습니다. 답변을 받으면 원문과 추가 조건을 기록하고, 그 내용을 바탕으로 동작·예외·구현 방법·완료 기준을 계속 구체화합니다.

질문 묶음의 기본 기준은 5개지만 고정 개수나 상한은 아닙니다. 7~10개 이상도 가능하며, 서로 다른 주제라도 독립적으로 답할 수 있으면 함께 묻습니다. 앞선 답변에 따라 내용이 달라지는 후속 질문만 미루고, 30~40개를 한꺼번에 쏟아내는 과도한 묶음은 피합니다. 추천은 사용자가 선택하기 전까지 제안으로 남습니다.

### 예시 확인

위 요청 이후의 대화에서 질문 두 개를 발췌한 예시입니다. 실제 질문 묶음과 선택지는 현재 기획 내용에 따라 달라집니다.

```text
Feature Planner:
  ## 에이전트 임시 결정

  ### A. 질답 기록의 파일 이름

  - 무엇을: 별도로 지정하지 않은 질답 기록의 파일 이름.
  - 어떻게: room-booking-interview.md로 정했습니다.
  - 왜: 회의실 예약 기획의 기록임을 알아보기 쉽고, 필요하면 바꿀 수 있기 때문입니다.

  ## 질문

  **[Q-001] : 예약은 어떻게 확정할까요?**
  사내 구성원용 작은 서비스에서 예약을 신청한 사람이 바로 회의실을 사용할 수 있을지,
  운영자의 확인을 기다려야 할지 정합니다. 승인 대기 화면과 관리자의 처리 업무에 영향을 줍니다.

  1. **빈 시간이면 즉시 확정**
     대기 없이 예약할 수 있고 승인 업무가 없습니다. 별도의 사전 심사가 필요 없는 팀에 맞습니다.
  2. **관리자가 승인한 뒤 확정**
     이용 목적을 사전에 확인할 수 있지만, 사용자는 승인 결과를 기다려야 합니다.
     회의실 이용을 운영자가 통제해야 하는 경우에 맞습니다.

  ---

  **[Q-002] : 누가 확정된 예약을 취소할 수 있나요?**
  예약한 사람이 직접 취소할 수 있는지, 운영자도 취소할 수 있는지 정합니다.
  취소 버튼의 표시 대상과 권한 검사가 달라지며, 위의 승인 방식과는 독립적으로 정할 수 있습니다.

  1. **예약자만 취소 가능**
     예약자의 통제권이 분명하지만, 부재 중에는 운영자가 대신 처리할 수 없습니다.
     운영자의 개입이 필요 없는 경우에 맞습니다.
  2. **예약자와 관리자 모두 취소 가능**
     예약자가 부재 중이어도 운영할 수 있지만 관리자에게 추가 권한을 부여하게 됩니다.
     시설 점검 등으로 운영자가 일정을 조정해야 하는 경우에 맞습니다.

  번호나 자유로운 문장으로 답하시면 됩니다. 예: Q-001: 1, Q-002: 2

사용자:
  Q-001은 1번. 대신 한 번에 최대 2시간까지만 예약할 수 있게 해 줘.
  Q-002는 2번. 관리자가 취소할 때는 사유를 남겨야 해.
  오늘은 여기서 중단하고 다음에 이어가자.

Feature Planner:
  즉시 확정, 최대 2시간 제한, 취소 권한과 관리자 취소 사유 조건을 원문과 함께 저장했습니다.
  docs/specs/room-booking-interview.md의 상태를 ‘중단’으로 기록했습니다.
  반복 예약 정책 등 아직 결정하지 않은 사항은 미정으로 남겼습니다.
```

### 처음 요청할 때 알려주면 좋은 내용

만들고 싶은 내용을 간단하게 설명합니다. 그 내용을 구체화하는데 도움되는 자료나 내용, 문서등을 추가로 제공하면 좋습니다.

한 문장의 아이디어만으로도 시작할 수 있습니다. 구현 논의에 필요한 기술 정보는 해당 질문을 다룰 때 관련 코드·자료만 확인합니다. 확인한 사실과 출처를 남기고, 제안이나 가정은 사용자 결정과 구분합니다.

## 사용 예시와 시나리오

### 1. 기존 프로젝트의 새 기능 기획

```text
$feature-planner
현재 프로젝트에 게시글 북마크 기능을 추가하려고 해.
기존 로그인과 게시글 구조를 확인해서 기획해 줘.
북마크 폴더와 공개 공유는 이번 범위에서 제외해 줘.
기획서는 docs/plans/bookmark-spec.md에 작성해 줘.
```

필요한 맥락만 확인하고 북마크 사용 대상이나 저장 정책 등 독립적인 질문을 함께 제시합니다. 답변을 바탕으로 구체적인 동작과 구현 방법을 좁히고, 실제로 확인한 변경 위치와 작업 순서를 계획에 포함합니다. 프로젝트 코드는 수정하지 않습니다.

### 2. 질문에 조건을 덧붙여 답하기

```text
Q-002: 2번으로 할게. 다만 관리자가 예약을 취소할 때는 사유를 남겨야 해.
Q-003: 주말 예약은 허용하지 않을게.
```

선택 번호뿐 아니라 추가 조건도 결정에 포함합니다. 실제 질문 ID와 선택지 번호를 사용하거나 자유로운 문장으로 답할 수 있습니다. 일부 질문에만 답하면 나머지는 미답변으로 남기고, 그 답변에 의존하지 않는 논의는 계속합니다.

### 3. 이전 결정 변경하기

```text
아까 관리자 승인 후 예약이 확정된다고 했는데,
빈 시간이라면 바로 확정되는 방식으로 바꿀게.
이후 질문과 구현 계획에는 바뀐 결정을 반영해 줘.
```

이전 질문과 답변 원문은 보존하고 무엇이 바뀌었는지 덧붙입니다. 후속 질문과 최종 구현 계획에는 최신 결정을 사용하며, 매번 문서 전체를 다시 작성하지 않습니다.

### 4. 결정을 보류하거나 대화 중단하기

```text
반복 예약 정책은 다음 운영 회의 이후에 정할게.
그 항목은 보류하고, 오늘 인터뷰는 중단해 줘.
지금까지의 질문과 답변, 결정 변경 내용을 저장해 줘.
```

보류 항목과 영향을 미정으로 남기고, 마지막 답변까지 기록한 뒤 상태를 `중단`으로 저장합니다. 추가 질문을 멈추며, 중단을 기획 완료로 처리하거나 최종 기획서를 만들지 않습니다.

### 5. 기존 문서에서 재개하기

```text
$feature-planner
docs/plans/room-booking-interview.md를 읽고 기획을 이어가자.
반복 예약은 최대 4주까지만 허용하기로 정했어.
이 결정을 반영하고 남은 항목을 확인해 줘.
```

기존 질답 기록과 필요한 변경 사항을 확인하고 최신 결정을 반영합니다. 이미 해결한 질문은 반복하지 않으며, 질문 번호와 자체 결정의 알파벳도 이어서 사용합니다.

### 6. 미정 항목을 남긴 채 종료하기

```text
기획은 여기서 완료해 줘.
모바일 알림 정책은 미정 상태로 남겨 두고,
질답 기록은 보존하고 별도의 한국어 구현 계획을 정리해 줘.
```

명확한 종료 요청을 받으면 추가 질문 없이 별도의 한국어 최종 기획서를 작성합니다. 확정한 동작·조건·완료 기준을 구체적인 할 일로 유지하고, 미정 항목과 남은 가정도 영향과 함께 기록합니다.

### 7. 코드가 없는 새 프로젝트 기획

```text
$feature-planner
신규 입사자의 첫 주 온보딩을 관리하는 서비스를 기획해 줘.
인사 담당자, 팀 리더, 신규 입사자가 해야 할 일을 구분하고 싶어.
아직 코드는 없어. 필요한 동작과 구현 방법을 함께 구체화해 줘.
```

저장소나 기술 스택이 없어도 시작할 수 있습니다. 사용자, 동작, 조건과 완료 기준을 좁히면서 구현 방법도 결정합니다. 새 파일이나 구조는 제안으로 표시하고, 확인하지 않은 위치를 이미 존재하는 코드처럼 쓰지 않습니다.

## 결과 문서는 어디에 생기나요?

사용자가 지정한 경로를 우선하고, 지정하지 않았다면 프로젝트 관례를 따릅니다. 둘 다 없으면 다음 형식을 사용합니다.

```text
docs/specs/<기획명>-interview.md
docs/specs/<기획명>-spec.md
```

기획 중에는 `-interview.md`에 질문·선택지·답변 원문과 자체 결정을 누적합니다. 명시적으로 종료하면 이 기록을 보존하고 `-spec.md`에 현재 유효한 구현 계획을 별도로 작성합니다. 대화와 문서는 한국어로 유지하며 코드 식별자와 경로, 사용자 답변 원문은 그대로 보존합니다.

```text
docs/specs/room-booking-interview.md
docs/specs/room-booking-spec.md
```

## 문서에서 확인할 항목

| 표시 | 의미 |
| --- | --- |
| `Q-001`, `Q-002`, … | 인터뷰 전체에서 이어지는 질문 번호 |
| `A`, `B`, … `Z`, `AA`, … | 에이전트의 임시 결정. 같은 결정의 수정에는 같은 알파벳 사용 |
| 사용자 결정 | 사용자가 명시적으로 선택하거나 추가·수정한 내용 |
| 확인한 사실 | 코드나 자료에서 실제로 확인한 내용과 재확인할 수 있는 출처 |
| 추천 | 근거를 들어 제시한 선택지. 사용자가 선택하기 전까지는 제안 |
| 미결정 사항 | 미답변, 보류, 건너뜀, 확인되지 않은 사실이나 해결되지 않은 충돌 |

중요하거나 되돌리기 어려운 결정은 사용자에게 묻습니다. 사소하고 쉽게 되돌릴 수 있는 사항만 에이전트가 임시 결정하고, 새로 생기거나 변경된 내용을 질문 위에 ‘무엇을·어떻게·왜’로 공개합니다. 변경되지 않은 결정은 반복해서 표시하지 않습니다.

질답 기록에는 원문과 수정 이력을 보존합니다. 최종 기획서는 목표, 핵심 동작, 구체적인 구현 할 일, 미결정 사항과 남은 가정을 담습니다. 각 할 일에는 동작과 조건, 확인한 구현 위치 또는 신규 제안 표시, 작업 순서와 의존성, 완료 기준을 포함합니다. 원문 기록을 열지 않아도 무엇을 어떻게 구현할지 이해할 수 있어야 합니다.

## 자주 생기는 상황

| 상황 | 해결법 |
| --- | --- |
| 구현할 내용이 충분히 정해졌는데 질문이 계속됨 | 자동으로 종료하지 않습니다. 종료 또는 추가 구체화를 한 번 제안할 수 있으며, 명시적으로 종료하면 최종 기획서를 작성합니다. |
| 어떤 질문에 지금 답할 수 없음 | 건너뛰거나 보류할 수 있습니다. 영향과 미정 상태를 문서에 남깁니다. |
| 질문을 하지 않음 | 전체 초안 작성을 기다릴 필요가 없습니다. 필요한 맥락만 짧게 확인하고 질문을 시작하도록 요청할 수 있습니다. |
| 질문을 하나만 받음 | 독립적으로 답할 수 있는 질문은 주제와 관계없이 함께 묻도록 요청할 수 있습니다. 앞선 답변에 의존하는 후속 질문만 미룹니다. |
