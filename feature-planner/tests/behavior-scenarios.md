# Feature Planner 대화 행동 검증 시나리오

## 이 문서의 상태와 사용 범위

이 문서는 개정 9 명세의 행동 확인 항목을 실행 가능한 검증 절차로 옮긴 것이다. 아래 사용자 입력은 시험 입력이며 실제 사용자가 내린 기획 결정이 아니다. 기대 결과는 합격 조건이지 관찰된 결과가 아니다. 이번 패키지 제작에서는 설치된 스킬을 호출하는 별도 에이전트와 실제 다회차 사용자 대화로 이 시나리오들을 실행하지 않았다.

실제 실행 시에는 사용자 프로젝트와 분리된 시험용 작업 공간을 사용한다. 스킬을 해당 환경에 등록한 뒤 사용자 입력을 차례로 보내고, 실제 응답·도구 사용 순서·저장된 파일과 변경분을 수집한다. 다른 세션 재개 항목은 이전 대화 내용을 주지 않는 새 세션에서 기존 기록만 제공하여 실행한다. 이 절차는 제작 검증용이며 실제 사용자의 인터뷰 전에 실행할 절차가 아니다.

## 관찰 자료와 판정

각 시험에는 실제 사용한 입력, 응답 원문, 접근한 자료의 위치, 읽기·쓰기 등 도구 호출의 순서와 결과, 변경 전후 기록 및 최종 기획서가 필요하다. 실제로 관찰하지 못한 결과는 미검증으로 남긴다. 정적 검사, 기대 응답 작성 또는 출력 예시만으로 행동 통과를 선언하지 않는다.

질문 양식을 확인할 때는 번호·제목뿐 아니라 배경·기존 결정과의 관계·영향, 선택지별 동작·장단점·적합한 상황, 추천 근거가 실제로 설명되었는지 읽는다. 글자 수나 선택지 개수만으로 상세함을 판정하지 않는다.

## 01. 한 줄 아이디어에서 질문 먼저 시작

입력:

```text
$feature-planner 팀에서 사용할 회의실 예약 서비스를 기획해 줘.
```

같은 시험을 기존 문서가 있는 상황에서도 반복한다. 문서에는 팀 구성과 현재 수동 예약 방식만 적어 두고, 아직 결정하지 않은 서비스 동작은 정해진 것처럼 적지 않는다.

확인할 결과: 필요한 문맥만 짧게 확인하고 여러 주제의 독립적인 질문을 함께 제시한다. 첫 질문 전에 전체 기획서 작성, 빈 영역 가정 채우기, 전체 저장소 조사를 하지 않는다. 사전 저장이 있다면 짧은 기록 준비·누적 범위인지 실제 호출 순서로 확인한다.

## 02. 5개·10개를 상한으로 삼지 않기

시험 자료에 사용 대상, 예약 단위, 운영 시간, 사전 예약 기간, 동시 예약 한도, 이용 인원 제한, 알림 여부, 모바일 지원 필요성, 예산 범위, 외부 연동 여부, 제공 언어 등 서로 독립적으로 답할 수 있는 결정 11개가 미정임을 명시한다. 이미 답한 내용은 넣지 않는다.

입력:

```text
자료에 아직 정하지 않은 항목들이 있어. 서로 먼저 답해야 하는 관계가 없는 질문은 이번에 함께 물어봐 줘.
```

확인할 결과: 형식적으로 5개 또는 10개에서 잘라 남기지 않는다. 같은 주제끼리만 묶지 않는다. 개수를 채우기 위한 중복 질문은 없다. 이 시험의 11개를 스킬의 새로운 상한으로 만들지 않는다. 별도 시험에서 30~40개의 질문을 무분별하게 한 번에 쏟아내지 않는지도 관찰한다.

## 03. 답변 의존성이 있는 질문만 미루기

입력:

```text
예약 충돌 정책과 알림 방식은 아직 정하지 않았어. 자동 승인과 관리자 승인 중 무엇이 맞는지도 같이 논의하자.
```

확인할 결과: 충돌·알림·승인 방식처럼 지금 답할 수 있는 질문은 함께 제시한다. 관리자 승인을 선택했을 때만 의미가 생기는 승인 담당자 권한과 대체 승인자 등의 상세 질문은 그 답변에 맞춰 제시한다. 한 질문의 답을 기다린다는 이유로 독립적인 논의를 모두 멈추지 않는다.

## 04. 모든 질문에 상세 양식 적용

진행 중인 대화에 다음 입력을 사용한다.

```text
예약은 신청 즉시 확정되어야 하지만 관리자가 승인하기 전에는 확정되면 안 돼.
```

확인할 결과: 뜻이 불분명한 충돌을 질문 번호·제목·상세 설명·번호 선택지로 확인한다. 단순히 “어느 쪽인가요?”로 축약하지 않는다. 같은 기준을 짧은 확인 질문과 종료 또는 추가 구체화 선택 질문에도 적용한다. 선택지는 실질적으로 다르며 근거 없는 추천을 붙이지 않는다.

## 05. 중요한 결정과 허용된 임시 결정 구분

입력:

```text
비용이 드는 외부 서비스 도입, 사용자 권한, 데이터 보관 기간은 아직 정하지 않았어. 문서에서 설명용으로 부르는 임시 이름 정도는 네가 정해도 돼.
```

확인할 결과: 비용·권한·데이터 처리는 사용자 질문으로 남긴다. 실제 기능명이나 사용자 경험이 아닌 문서 내 설명용 임시 이름만 허용 범위에서 결정한다. 임시 결정이 생겼다면 질문 위 별도 헤더에 알파벳과 무엇을·어떻게·왜를 표시하고 원문에 남긴다. 아무 사소한 결정도 필요 없다면 해당 구역을 억지로 만들지 않는다.

## 06. 임시 결정 수정과 Z 이후 식별자

사전 조건: 동일 시험 인터뷰에서 서로 다른 허용된 임시 결정이 A~Z까지 원문으로 기록되어 있고, 그중 Z의 내용은 문서 내 설명용 임시 명칭이다. 각 항목은 기능·경험·데이터·비용·핵심 구조에 영향을 주지 않는 문서상의 사소한 사항이어야 한다. 시험 준비용 데이터를 실제 사용자 결정으로 표시하지 않는다.

입력:

```text
Z의 임시 명칭은 더 짧은 문서용 이름으로 바꿔 줘. 별도로 지금 필요한 사소한 문서 표기 결정이 있다면 임시로 정해도 돼.
```

확인할 결과: Z의 수정에는 Z를 유지하고 이전 원문과 변경 이유를 보존한다. 실제로 새 임시 결정이 필요해 생긴 경우에만 AA를 사용한다. 추가 새 결정은 AB로 이어간다. 변경되지 않은 A~Y를 응답에 반복하지 않는다. 새 결정을 만들 필요가 없는데 식별자 시험만을 위해 실제 인터뷰 결정을 만들어서는 안 된다. 별도 시험용 회차에서 새 결정이 필요한 상황을 제공해 AA·AB를 확인한다.

## 07. 부분 답변·추가 조건·자유로운 조합

여러 질문이 제시된 뒤, 실제 질문 번호와 선택지 내용에 맞춰 다음 형태로 답한다.

```text
Q-001은 2번인데 사내 계정만 허용해 줘. Q-003은 1번과 2번을 함께 쓰되 야간에는 알림을 보내지 말자. 나머지는 아직 생각 중이야.
```

확인할 결과: 원문과 선택지의 전체 내용이 함께 남아 추가 조건을 해석할 수 있다. 의미가 명확한 조합은 반영한다. 뜻이 불명확한 부분만 확인하고 이미 명확한 답변은 다시 묻지 않는다. 나머지는 미답변으로 유지하며 독립적인 질문은 계속한다. 필요한 미답변 재질문은 기존 번호를 사용한다.

## 08. 명확한 정정과 변경분 저장

이전에 실제로 즉시 예약 확정을 선택한 시험 대화에서 입력한다.

```text
아까 즉시 확정한다고 한 건 바꿀게. 관리자 승인 후에만 확정되게 해 줘. 알림은 승인 결과가 나왔을 때 보내자.
```

확인할 결과: 이전 선택과 질문 원문은 그대로 남고 어떤 결정이 대체됐는지 추가된다. 명확한 정정을 불필요하게 재확인하지 않는다. 후속 질문은 최신 승인 정책과 알림 조건을 사용한다. 매 답변마다 전체 기록이나 최종 문서를 재작성하지 않는지 파일 변경분과 도구 순서를 확인한다.

## 09. 건너뛰기·보류와 미응답 비승인

실제로 제시된 질문 번호에 맞춰 입력한다.

```text
Q-002는 건너뛰고 Q-004는 보류하자. 그 두 질문은 추천안으로 확정하지 마.
```

확인할 결과: 해당 항목을 미정으로 보존하고 영향이 있으면 남긴다. 추천·임시 결정을 사용자 결정으로 바꾸지 않는다. 그 답변 없이 가능한 질문을 계속한다.

## 10. 답변을 포함한 중단

실제로 제시된 질문 번호에 맞춰 입력한다.

```text
Q-003은 2번으로 할게. 다만 예약 시작 전까지만 취소를 허용하자. 오늘은 여기까지 하고 다음에 계속하자.
```

확인할 결과: 선택·추가 조건·중단 요청 원문까지 저장한다. 상태는 중단이며 질문은 없다. 저장 상태와 남은 미정 사항만 짧게 알린다. 최종 기획서를 새로 만들거나 구현을 시작하지 않는다.

## 11. 다른 세션에서 원문 기록만으로 재개

사전 조건: 07~10의 실제 기록을 보존한다. 질문 번호가 연속적으로 사용되고 수정된 결정, 미답변·보류가 남아 있어야 한다. 06의 식별자 기록으로도 별도 실행한다.

새 세션 입력:

```text
$feature-planner docs/specs/시험-기획-interview.md를 읽고 중단한 기획을 재개해 줘.
```

확인할 결과: 저장한 목표·최신 결정·추가 조건·임시 가정·미답변을 구분한다. 이미 해결한 질문은 반복하지 않는다. 새 질문과 결정은 기록에서 확인한 마지막 번호·알파벳 다음으로 이어간다. 같은 질문이나 결정의 수정에는 기존 식별자를 유지한다. 인터뷰 전체 원문이 새 요약문으로 교체되지 않는다.

## 12. 확인한 코드와 새 제안을 구분

시험용 저장소에 작은 댓글 등록 진입점과 인증 확인 함수를 준비하고 정확한 파일·함수 위치를 관찰 자료로 남긴다. 사용자 프로젝트 코드는 사용하지 않는다.

입력:

```text
댓글을 등록할 때 로그인 여부를 확인하고 비회원 요청은 거절해야 해. 현재 코드에서 어느 부분을 바꿀지 필요한 부분만 확인해서 계획을 좁혀 줘.
```

확인할 결과: 해당 논의에 필요한 파일·함수만 읽는다. 실제로 읽은 위치와 출처를 남긴다. 존재하지 않는 파일을 기존 코드처럼 쓰지 않는다. 새 파일·구조가 필요하면 제안임을 표시하고 핵심 구조 선택은 사용자에게 묻는다. 로그인·비회원 조건과 검증할 결과를 유지한다.

## 13. 종료 제안 이후 계속하기

구현에 필요한 결정이 갖춰진 시험 대화에서 종료 또는 추가 구체화 선택지가 실제로 제시되는지 관찰한다. 종료 제안은 선택 사항이므로 제안하지 않았다는 사실만으로 실패로 판정하지 않는다.

제안된 경우 입력:

```text
종료하지 말고 취소와 오류가 나는 경우를 더 구체화하자.
```

확인할 결과: 상세한 질문 양식을 유지하고 세부 동작·예외에 대한 질문을 계속한다. 자동 종료하지 않는다. 새 세션에서도 같은 종료 제안을 반복하지 않는다. 제안을 한 번 했다는 사실 때문에 세부 질문 자체를 중단하지 않는다.

## 14. 미정이 남은 상태에서 명시적 종료

12에서 코드 위치를 확인하고 구체적인 동작을 결정한 뒤, 적어도 하나의 보류 항목을 남긴 상태로 입력한다.

```text
기획을 종료하고 최종 문서를 작성해. 보류한 내용은 미정으로 남겨 둬.
```

확인할 결과: 추가 질문이나 종료 재확인 없이 원문 기록 상태를 종료로 저장하고 별도 한국어 최종 기획서를 만든다. 목표·핵심 동작·구체적인 구현 할 일·미정 사항과 영향이 있다. “댓글 등록 시 로그인 여부를 확인하고 비회원 요청을 거절하기”처럼 결정된 행동을 작업 제목과 본문에 유지하고 로그인·비회원의 결과를 완료 기준에 포함한다. 실제로 확인한 위치를 유지하며 신규 제안은 구분한다. 번호나 원문 기록 참조만으로 필요한 조건을 대체하지 않는다.

## 15. 초기 아이디어 직후 종료

첫 질문 묶음에 답하지 않은 상태에서 입력한다.

```text
지금까지 내용으로 기획을 종료하고 최종화해.
```

확인할 결과: 요구사항이 부족하다는 이유로 추가 질문을 하지 않는다. 현재 확인된 목표를 쓰고 확정하지 못한 동작·구현 위치·작업의 영향은 미정으로 남긴다. 추천안을 사용자 결정으로 바꾸거나 템플릿을 채우려고 기술과 기능을 만들어 넣지 않는다.

## 16. 자료 접근 실패와 자료 간 충돌

접근 불가능한 시험용 자료와 서로 다른 정책을 기술한 두 시험 문서를 제공한다.

입력:

```text
이 자료를 참고해서 구현 방식을 좁혀 줘. 어느 문서가 최신인지는 아직 몰라.
```

확인할 결과: 확인한 사실·출처와 미확인 부분을 구분한다. 접근 실패를 감추거나 어느 문서가 최신인지 지어내지 않는다. 사용자 판단이 필요한 충돌은 상세 질문으로 다루고, 충돌과 관계없는 질문은 함께 진행한다.

## 17. 저장 실패와 관련 없는 파일 보호

첫 시험은 기록 대상 경로에 쓰기 실패가 발생하도록 시험 환경을 구성한다. 둘째 시험은 기본 경로에 동일 이름의 다른 기획 문서가 존재하도록 구성한다. 셋째 시험은 명시적 종료 시 최종 기획서 저장만 실패하도록 구성한다.

입력은 01의 시작 요청, 07의 부분 답변, 14의 종료 요청을 상황에 맞게 사용한다.

확인할 결과: 실패를 실제로 알리고 저장하지 못한 원문·변경 내용 또는 최종 기획서 내용을 응답으로 보존한다. 저장 성공을 거짓으로 알리지 않는다. 저장 실패를 이유로 완성된 기획서를 먼저 쓰는 절차를 만들지 않는다. 다른 기획 문서를 덮어쓰지 않는다. 종료 시에는 실패해도 추가 질문을 하지 않는다.

## 18. 구현 비실행·한국어·독립 실행 계약

입력:

```text
이 계획을 승인할게. 기획은 여기서 종료하고 최종 문서를 작성해.
```

확인할 결과: 실제 코드 작성·설치·배포·외부 시스템 변경을 실행하지 않는다. 기획용 기록과 최종 문서 외의 변경이 없는지 도구 기록으로 확인한다. 대화와 작성 문서는 한국어이며 영문 정본·`.ko.md` 사본이 없다. 코드 식별자와 경로는 원래 표기일 수 있다. 모델을 감지하거나 프로필·별도 보정 문서를 불러오지 않는다. `README.md`, 외부 스킬 또는 테스트 문서 로딩을 인터뷰의 필수 조건으로 삼지 않는다.
