# Feature Planner Old 스킬 기획서

작성일: 2026-09-07 / 개정: 2

이 문서는 Feature Planner Old의 기획, 검토, 작업 위임과 검증을 하나의 독립적인 사용 흐름으로 정의합니다. 다른 스킬을 먼저 설치하거나 실행할 필요가 없습니다. 스킬 내부 작업자 기능과 문서 검사 스크립트는 자체 실행 구성 요소입니다.

근거: [SKILL.md](SKILL.md), [문서 계약](references/spec-contract.md), [기획 갱신 규칙](references/living-spec.md), [구체화 규칙](references/refinement.md), [최소 변경 정책](references/minimal-change.md), [구현 조율](references/implementation.md).

예시의 서비스, 경로, ID와 예산은 설명용입니다. 실제 실행에서는 대상 저장소를 조사해 결정하며, 이 기획서는 검사기에 넣는 실행용 명세가 아닙니다.

## 1. 개요

### 1.1 제품명과 한 줄 정의

Feature Planner Old는 모호한 기능 요청을 영문 정본과 한국어 검토 사본으로 구체화하고, 사용자가 검토한 수정본의 작은 작업 단위를 위임해 최소한의 올바른 변경을 검증하는 스킬입니다.

### 1.2 제품의 범위

주 에이전트가 조사, 설계, 질문, 문서 갱신, 최종 검토, 작업 조율과 수용을 책임집니다. 구현 편집은 한 번에 작업 단위 하나를 받은 작업자가 수행합니다.

이름의 `old`는 저장소의 구버전 분류를 나타냅니다. 실행을 위해 다른 버전의 스킬이나 문서를 거쳐야 한다는 의미는 아닙니다.

## 2. 배경과 문제 정의

### 2.1 검토할 설계 없이 질문하는 문제

질문만 이어지면 사용자는 어떤 구현을 검토하는지 알기 어렵습니다. 첫 질문 전부터 현재 가능한 구체적인 설계와 가정을 문서로 제공합니다.

### 2.2 에이전트 판단이 숨는 문제

기존 함수를 확장할지, 새 파일을 만들지와 같은 결정도 구현 범위에 영향을 줍니다. 사용자 답변이 아닌 판단에는 에이전트 출처, 근거, 영향과 검토 필요 상태를 남깁니다.

### 2.3 최종 승인 뒤 설계가 바뀌는 문제

사용자가 검토한 수정본과 작업자가 읽은 수정본이 다르면 승인 범위와 실제 코드가 어긋납니다. 설계 수정 번호와 검토한 수정 번호가 같아야 구현을 진행할 수 있습니다.

### 2.4 위임 작업이 커지는 문제

파일 범위만 지정하고 심볼과 변경 이유를 정하지 않으면 작업자가 더 넓은 리팩터링과 추상화를 만들 수 있습니다. 정확한 변경 지도와 현실적인 변경 예산을 함께 전달합니다.

### 2.5 테스트 통과만으로 과도한 변경을 수용하는 문제

동작 검사가 통과해도 필요 없는 의존성, 파일과 공통 추상화가 추가될 수 있습니다. 실제 diff의 범위, 예산, 로컬 관례와 필요성을 별도로 확인합니다.

## 4. 비목표

- 검토할 문서 없이 대화만으로 구현을 시작하는 흐름
- 계획 승인과 실제 구현 요청을 구분하지 않는 자동 실행
- 편리함만을 이유로 기존 구조를 교체하는 광범위한 리팩터링
- 작업자에게 여러 작업을 한 번에 맡기거나 범위 밖의 설계를 위임하는 방식
- 코드 줄 수를 맞추기 위한 오류 은폐와 검증 축소
- 문서의 의미적 정확성과 실제 코드 동작을 정적 검사기만으로 보증하는 방식

기획만 요청한 경우에도 초안과 문서 갱신은 수행합니다. 이후 구현 요청이 없어도 문서가 `ready` 상태로 남아 있을 수 있습니다.

## 5. 호출과 입력 계약

### 5.1 대표 호출

```text
$feature-planner-old
이 프로젝트에 주문 취소 기능을 기획해 줘.
기존 주문 처리 구조를 유지하고 취소 조건부터 구체화하자.
```

기존 문서 재개 예시는 다음과 같습니다.

```text
$feature-planner-old
지정한 영문 명세의 현재 상태를 확인하고 이어서 진행해 줘.
```

‘계속’이라는 표현만으로 무조건 구현 단계로 가지 않습니다. 요청 맥락, 현재 제어 상태, 검토 수정본과 실제 허용 작업을 함께 확인합니다.

### 5.2 입력 목록

| 입력 | 역할 | 처리 기준 |
| --- | --- | --- |
| 기능 요청 | 목표와 초기 범위 | 읽을 수 있는 자료를 확인한 뒤 설계 가설을 작성합니다. |
| 기존 저장소 | 현재 구현 방향과 재사용 근거 | 가까운 코드, 테스트와 적용 지침을 읽습니다. |
| 문서 쌍 | 기획과 검토, 진행 상태 | 영문 정본을 기준으로 한국어 사본을 맞춥니다. |
| 사용자 답변 | 선택, 조건과 정정 | 결정 원장과 파급 설계를 갱신합니다. |
| 실행 권한 | 기획 또는 구현의 범위 | 문서 승인과 별도로 확인합니다. |
| 호스트 도구 | 파일, Python과 내부 작업자 기능 | 사용할 수 없는 기능을 있다고 가정하지 않습니다. |

### 5.3 입력 형식의 경계

새 아이디어는 자체 템플릿으로 문서화합니다. 기존 문서의 실행에는 이 스킬의 제어 블록과 표 계약을 적용합니다. 임의의 Markdown을 검사 없이 준비된 실행 문서로 취급하지 않습니다.

## 8. 흐름 분기

| 단계 | 진입 조건 | 담당 작업 | 다음 단계 |
| --- | --- | --- | --- |
| REFINE | 문서 없음, 열린 질문 또는 미완성 구현 설계 | 조사, 문서 작성과 갱신, 결정 질문 | REFINE 또는 FINAL_REVIEW |
| FINAL_REVIEW | 중요한 질문이 해소되고 구현 설계가 준비됨 | 준비 검사, 최종 검토 질문 | 수정 필요 시 REFINE, 확인 시 ready |
| IMPLEMENT | 검토 수정본, 검증과 구현 권한 확보 | 작업 위임, 실제 변경 검토와 통합 | 완료 또는 TARGETED_REFINE |
| TARGETED_REFINE | 구현에서 계약, 변경 대상이나 예산 공백 발견 | 영향 영역의 설계와 검토 갱신 | 검토 후 해당 작업 재개 |

위 명칭은 실행 흐름의 분기입니다. 제어 블록의 `state` 값과 같은 필드가 아닙니다.

## 9. 제어 블록 설계

두 문서 상단에는 같은 JSON을 기록합니다. 아래는 열린 질문을 가진 기획 중 상태의 설명용 예시이며, 이 블록만으로 실행 가능한 명세가 완성되는 것은 아닙니다.

```json
{
  "workflow": "feature-planner/v7",
  "state": "refining",
  "source_spec": "docs/specs/2026-09-07-order-cancel-spec.md",
  "korean_mirror": "docs/specs/2026-09-07-order-cancel-spec.ko.md",
  "spec_revision": 1,
  "reviewed_revision": null,
  "selected_strategy": "STRAT-1",
  "implementation_direction": "preserve",
  "direction_decision_id": null,
  "minimal_change_policy": "strict",
  "final_domain_gate": "not_ready",
  "open_question_ids": ["Q-001"],
  "active_slices": [],
  "next_action": "answer_questions"
}
```

실제 실행 명세에서는 이 JSON을 `feature-planner-control` 주석 블록에 둡니다. 한국어 사본에서도 키, 값과 경로를 번역하지 않습니다.

## 10. 상태 전이와 수정 번호

| state | 필수 일관성 | next_action |
| --- | --- | --- |
| refining, 열린 질문 있음 | 검토 번호 null, 게이트 not_ready, 활성 작업 없음 | answer_questions |
| refining, 열린 질문 없음 | 검토 번호 null, 게이트 required, 활성 작업 없음 | review_final_draft |
| ready | 검토 번호 일치, 게이트 confirmed_none, 열린 질문과 활성 작업 없음 | await_implementation_request 또는 implement |
| implementing | 검토 번호 일치, 활성 ID와 in_progress 작업 일치 | implement |
| blocked | 정확한 공백과 영향받은 영역 기록 | targeted_refinement |
| complete | 검토 번호 일치, 열린 질문과 활성 작업 없음 | none |

### 10.1 설계 변경

동작, 전략, 변경 대상, 예산과 작업 구성을 중요하게 바꾸면 `spec_revision`을 올리고 이력을 추가합니다. 이미 검토받았더라도 `reviewed_revision`을 비우고 필요한 검토로 돌아갑니다.

### 10.2 진행 변경

같은 설계의 작업이 `pending`에서 `in_progress`, `verified`로 이동하는 것은 진행 상태 변경입니다. 이 변경만으로 설계 수정 번호를 올리지 않습니다. 영문 진행 상태를 갱신한 뒤 한국어를 동기화합니다.

## 12. 안정적인 ID와 결정 출처

| 기록 | ID |
| --- | --- |
| 결정 | D-001 |
| 질문 | Q-001 |
| 재사용 자산 | R-001 |
| 기능 및 비기능 요구사항 | FR-001, NFR-001 |
| 인수 기준 | AC-001 |
| 전략 | STRAT-1 |
| 변경 | CH-001 |
| 작업 단위 | WS1 |

이 문서에서 `R-*`는 재사용 자산입니다. 요구사항은 `FR-*`와 `NFR-*`로 기록합니다.

결정 원장은 다음 필드를 갖습니다.

```text
ID / Domain / Decision / Source / Rationale or Evidence
/ Impact / User review / Status
```

| Source | User review | 상태 의미 |
| --- | --- | --- |
| user | confirmed | 사용자가 명시한 현재 결정 |
| repository | not-required | 실제 자료에서 확인한 사실 |
| agent | review-needed | 에이전트가 선택한 검토 필요 판단 |
| 대체된 결정 | overridden | superseded 상태로 이전 기록 보존 |

결정 `Status`는 `open`, `resolved`, `superseded`를 사용합니다. 현재 에이전트 판단이 내용상 `resolved`여도 사용자 검토가 끝났다는 뜻은 아닙니다. `User review`를 별도로 확인합니다.

## 13. 질문과 답변 처리

### 13.1 질문 전 작업

가까운 구현과 테스트를 조사하고 현재 가능한 설계를 문서에 기록합니다. 확인할 수 있는 사실을 사용자에게 반복해서 묻지 않습니다. 질문은 결과, 계약, 범위와 검증을 바꿀 수 있는 중요한 결정에 집중합니다.

### 13.2 질문 회차

기본적으로 관련 질문 1~4개를 제시합니다. 문서 경로와 수정 번호, 이번 변경, 검토가 필요한 판단과 열린 질문 ID를 먼저 보여줍니다. 사용자는 문서를 열지 않아도 어떤 판단을 정정해야 하는지 알 수 있어야 합니다.

질문 예시:

```text
Q-001: 주문 취소 허용 시점
이 결정은 상태 전이, 환불 처리와 인수 기준에 영향을 줍니다.

1. 결제 전 주문만 취소
2. 결제 후 출고 전까지 취소
3. 운영자가 승인한 경우만 취소

원하는 조건을 직접 설명할 수도 있습니다.
```

추천은 현재 문서의 잠정 전략과 일치해야 합니다. 예시의 어떤 선택지도 이 저장소의 확정 정책이 아닙니다.

### 13.3 질문 상태

`open` 질문 ID는 제어 블록의 `open_question_ids`와 정확히 일치합니다. 답변을 받으면 `answered`로 바꾸고 현재의 해결된 결정 하나를 연결합니다. 더는 영향을 주지 않는 질문은 `withdrawn`으로 남기고 이유를 적습니다.

## 14. 정정과 파급 변경

사용자가 “결제 후 취소도 허용하자”고 이전 결정을 바꾸면 다음을 함께 처리합니다.

1. 이전 결정을 `superseded`, 검토 상태를 `overridden`으로 보존합니다.
2. 새 사용자 결정을 기록하고 대체 관계를 남깁니다.
3. 취소 상태 전이와 관련 요구사항을 갱신합니다.
4. 선택 전략, 수정할 심볼과 재사용 항목을 다시 확인합니다.
5. 필요한 파일과 추가 코드가 달라지면 변경 지도와 예산을 맞춥니다.
6. 작업 의존성, 인수 기준, 위험과 검증 계획을 갱신합니다.
7. 수정 번호를 올리고 한국어 사본을 동기화한 뒤 다음 질문을 제시합니다.

기존 구현 경로와 새 경로를 모두 활성 상태로 남겨 두지 않습니다. 이전 내용은 감사 가능한 이력에 보존합니다.

## 15. 구현 전략과 기존 방향 보존

구현 방법은 다음 순서로 확인하고 충분한 방법을 찾으면 더 넓은 대안을 기본값으로 고르지 않습니다.

1. 기존 동작, 설정과 확장 지점만으로 해결
2. 기존 함수, 컴포넌트, 서비스와 테스트 도우미 재사용
3. 가장 가까운 기존 소유 함수의 작은 확장
4. 유사 코드 옆의 작은 로컬 구현
5. 실제 중복을 줄이고 기존 관례에 맞는 로컬 도우미
6. 방향 변경이 승인된 새 공유 추상화, 계층과 의존성

아키텍처 계층, 상태 소유 위치, 데이터 접근 방식이나 향후 다른 코드도 따라야 할 공개 패턴을 바꾸는 선택은 방향 변경으로 다룹니다. 기존 방향을 유지할 대안과 바꿀 대안의 정확한 표면, 장점, 비용과 위험을 문서로 제시합니다.

방향 변경 승인은 해결된 `user` 결정으로 기록하고 허용된 변경 행에만 연결합니다. 관련 없는 현대화까지 승인받은 것으로 확대하지 않습니다.

## 16. 변경 지도

실제 실행용 Modification Map은 다음 열을 사용합니다.

```text
ID / Kind / Target / Symbol / Action / Existing anchor
/ Required change / Why necessary / Slice / Direction
```

| 필드 | 제약 |
| --- | --- |
| Kind | production, test, config, migration, generated, docs |
| Target | 정확한 저장소 상대 파일 경로 |
| Action | reuse, extend, edit, add, remove |
| Existing anchor | 따를 기존 경로와 심볼 |
| Why necessary | 정의된 요구사항 또는 인수 기준 ID를 포함 |
| Slice | reuse 외의 모든 변경 행은 작업 단위 하나 소유 |
| Direction | preserve 또는 approved-divergence |

`reuse` 행은 읽고 사용하는 근거이며 해당 파일을 수정할 권한을 만들지 않습니다. 디렉터리 glob만으로 실제 변경 설계를 대신하지 않습니다.

예를 들어 `CH-001`이 기존 주문 서비스의 상태 전이 함수 확장이라면 소유 심볼과 필요한 분기, `FR-001` 충족 이유, `WS1` 소유권까지 기록합니다. 실제 경로는 저장소에서 확인해야 합니다.

## 17. 변경 예산

작업마다 다음을 기록합니다.

| 항목 | 의미 |
| --- | --- |
| Max changed files | 전체 변경 파일 수 상한 |
| Max production files | 운영 코드 파일 수 상한 |
| Max new production files | 새 운영 코드 파일 수 상한 |
| Max production added lines | 운영 코드 추가 줄 수의 현실적인 추정 상한 |
| New dependencies | 허용한 새 의존성 이름 또는 None |
| New shared abstractions | 허용한 새 공통 추상화 이름 또는 None |

예산은 예상치 못한 확장을 찾는 기준입니다. 읽기 어려운 압축 코드, 오류 은폐와 검증 축소로 숫자를 맞추지 않습니다. 새 운영 파일, 의존성과 공유 추상화는 기본적으로 없는 설계를 먼저 검토합니다.

작업자는 승인되지 않은 예산 초과를 발견하면 `PATCH_BUDGET_GAP`을 반환합니다. 같은 전략의 추정치 오류라면 주 에이전트가 근거를 정리해 문서를 고칠 수 있지만, 실행 재개에는 수정 번호와 검토 상태가 다시 맞아야 합니다. 방향, 유지보수 부담과 동작이 달라지면 영향 영역을 다시 구체화합니다.

## 18. 작업 단위와 의존성

Work Plan의 열은 다음과 같습니다.

```text
ID / Goal / Depends on / Parallel group / Change IDs
/ Write scope / Do not touch / Covers / Validation / Status
```

작업 상태는 `pending`, `in_progress`, `verified`, `blocked`, `skipped`를 사용합니다. 각 요구사항과 인수 기준은 적어도 하나의 작업이 담당해야 합니다.

### 18.1 준비된 작업

pending 상태이며 선행 작업이 verified 또는 사유가 있는 skipped 상태여야 합니다. 정확한 변경 행과 예산이 있고 충돌하는 기존 변경이 없어야 하며 해당 시점에서 검증이 가능한지 확인합니다.

### 18.2 병렬 조건

같은 비직렬 그룹에서 의존 경로, 정확한 변경 대상과 쓰기 범위가 모두 겹치지 않는 작업만 병렬 후보입니다. 마이그레이션, 스키마, lockfile, 중앙 export와 불안정한 공통 계약을 동시에 수정하지 않습니다.

검증도 독립적이어야 하며 결과를 바로 통합하고 검토할 수 있어야 합니다. 독립성이 불확실하면 직렬로 실행합니다.

## 19. 최종 검토

중요한 질문이 없고 구현 설계가 준비되면 다음을 수행합니다.

1. state를 refining, 게이트를 required, next_action을 review_final_draft로 맞춥니다.
2. 문서에 열린 질문이 없고 모든 구현 대상, 예산과 작업이 구체적인지 확인합니다.
3. `specctl.py review-ready`를 실행하고 실패를 해결합니다.
4. 목표, 전략, 운영 코드 대상, 새 파일과 의존성, 작업 순서와 위험을 요약합니다.
5. 검토가 필요한 에이전트 판단을 모두 보여주고 추가로 구체화하거나 정정할 영역을 묻습니다.

추가 사항이 없다는 사용자 답변을 받으면 남은 에이전트 판단을 confirmed로 바꾸고 `reviewed_revision = spec_revision`, 게이트 confirmed_none, state ready로 설정합니다.

이 확인은 이미 준비된 문서의 검토 결과입니다. 답변 뒤 새로 설계를 시작하거나 검토되지 않은 범위를 추가하지 않습니다. 구현 요청이 없으면 ready 문서와 재개 방법을 제공합니다.

## 20. 작업자 위임 계약

구현 진입 전에 영문 정본 전체, 제어 상태, 검토 수정 번호와 구현 권한을 확인하고 `validate`, `ready`를 수행합니다.

[작업자 템플릿](assets/worker-task-template.md)에 다음을 전달합니다.

- 정확한 영문 정본 경로와 검토 수정 번호
- 작업 단위 하나의 WS 행
- 해당 작업이 소유한 CH 행과 예산
- 현재 패턴과 재사용 자산의 실제 근거
- 담당 요구사항과 인수 기준 원문
- 허용 쓰기와 수정 금지 범위
- 보존할 기존 사용자 변경
- 실행할 검증 명령과 반환 형식

작업자는 명세 쌍을 수정하거나 다른 작업을 구현하거나 재귀적으로 위임하지 않습니다. 기존 소유 위치에서 가장 작은 명료한 변경을 수행합니다.

## 21. 작업자 결과와 재작업

| 반환 상태 | 주 에이전트의 처리 |
| --- | --- |
| COMPLETE | 실제 전체 diff와 검증 결과를 확인한 뒤 수용 판단 |
| BLOCKED | 환경과 의존성의 차단 원인과 영향 기록 |
| SPEC_GAP | 해당 작업을 멈추고 필요한 계약만 다시 구체화 |
| PATCH_BUDGET_GAP | 전략과 추정치 점검, 문서 수정과 검토 후 재개 |
| DIRECTION_CHANGE_PROPOSAL | 제안한 변경을 실행하지 않고 대안과 영향 검토 |

반환 기록에는 changed_files, new_files, 재사용 근거, 변경 필요성, 실제 예산 사용, 구현 내용, 검증 명령과 PASS/FAIL/NOT_RUN, 정확한 공백을 포함합니다.

동일한 발견 사항에 대한 수정 회차는 최대 두 번입니다. 이후에는 같은 요청을 반복하지 않고 작업을 다시 나누거나 재배정하거나 설계를 구체화합니다. 별도의 스킬에서 쓰는 재시도 규칙을 가져오지 않습니다.

## 22. 작업별 검증과 수용

1. 작업자 보고와 실제 전체 diff를 읽습니다.
2. 모든 수정 파일이 해당 작업의 변경 행에 속하는지 확인합니다.
3. `check-scope`로 변경 범위를 확인합니다.
4. `check-patch`로 새 파일, 운영 코드 추가량과 의존성, 공유 추상화를 점검합니다.
5. 이름을 기록한 기존 코드와 테스트에 비춰 패턴을 비교합니다.
6. 없어도 요구사항이 충족되는 코드와 구조가 남았는지 검토합니다.
7. 작업의 동작 검사와 필요한 정적 및 빌드 검사를 수행합니다.
8. 사용할 수 있으면 읽기 전용 검토 관점도 활용합니다.
9. 모든 수용 조건을 통과한 경우에만 verified로 바꿉니다.
10. 영문 진행 상태를 먼저 갱신하고 한국어를 동기화합니다.

동작이 맞아도 필요 없는 공통 추상화, 파일이나 정리가 있으면 그대로 수용하지 않습니다. 기존 사용자 변경은 제거 대상이 아닙니다.

## 23. 영향 영역만 다시 구체화

구현에서 취소 시 환불 방식 같은 중요한 공백을 발견했다고 가정합니다.

영향받는 작업을 중단하고 저장소 근거, 관련 요구사항과 최소 대응안을 문서에 기록합니다. 설계 수정 번호를 올리고 이전 검토 번호를 비운 뒤 한국어를 동기화합니다.

그 결정에 필요한 질문만 제시합니다. 답변은 전략, 방향, 변경 대상과 예산, 검증과 작업 의존성에 반영합니다. 변경 수정본에 대한 검토 기회를 제공하고 검사한 뒤 영향받은 준비 작업부터 재개합니다.

좁은 정정에서는 해당 답변이 그 수정본 확인을 겸할 수 있습니다. 중요한 범위 확대라면 넓은 최종 검토를 다시 수행합니다. 독립적으로 검증된 작업은 보존하되 변경이 기존 증거를 무효화했는지 확인합니다.

## 25. 검증 명령의 계약

[specctl.py](scripts/specctl.py)에는 다음 명령이 정의돼 있습니다.

| 명령 | 입력 | 확인 목적 |
| --- | --- | --- |
| validate | 영문 정본 경로 | 현재 문서 쌍과 제어 상태 정합성 |
| status | 영문 정본 경로 | 사용자 검토용 상태 요약 |
| review-ready | 영문 정본 경로 | 최종 검토 질문을 할 만큼 설계가 준비됐는지 확인 |
| ready | 영문 정본 경로 | 의존성을 충족한 작업과 독립 병렬 후보 |
| check-scope | 영문 경로, WS-ID, --changed 경로 목록 | 작업 범위와 변경 지도에 맞는 실제 파일 |
| check-patch | 위 입력과 실제 추가량 | 변경 범위 및 예산 |

`check-patch`는 필수 `--production-added-lines`와 선택적 `--new`, 반복 가능한 `--dependency`, `--shared-abstraction`을 받습니다. 실제 diff에서 수집한 값을 전달해야 하며 작업자의 주장만으로 숫자를 채우지 않습니다.

```text
python <skill-path>/scripts/specctl.py validate <english-spec>
python <skill-path>/scripts/specctl.py review-ready <english-spec>
python <skill-path>/scripts/specctl.py ready <english-spec>
python <skill-path>/scripts/specctl.py check-scope <english-spec> WS1 --changed <paths>
python <skill-path>/scripts/specctl.py check-patch <english-spec> WS1 --changed <paths> --production-added-lines <actual-count>
```

위 명령은 호출 형식 예시입니다. 이번 기획서 작성에서 실행한 검증 결과가 아닙니다. 문서 구조가 유효하다는 사실만으로 코드 정확성, 번역 의미와 수정 소유권이 검증되는 것은 아닙니다.

## 26. 예외와 권한 경계

### 26.1 작업자 기능이 없음

기획과 준비 가능한 문서 작업은 수행합니다. 구현 편집은 주 에이전트가 임의로 대신하지 않고 필요한 기능과 차단 이유, 준비한 작업자 요청을 제공합니다. 이는 이 스킬 자체의 위임 계약입니다.

### 26.2 문서 쌍 불일치와 검증 실패

영문 정본을 먼저 고치고 한국어를 동기화합니다. 현재 수정본이 준비되지 않았는데 ready 또는 complete로 표시하지 않습니다.

### 26.3 환경 문제와 기존 사용자 변경

검증을 실행할 수 없으면 결과에 NOT_RUN과 정확한 원인을 남깁니다. 충돌하는 기존 작업이 있으면 해당 작업의 시작을 보류하며 사용자 내용을 없애서 환경을 정리하지 않습니다.

### 26.4 중요한 확장

파괴적 행동, 외부 쓰기, 되돌리기 어려운 마이그레이션, 운영 의존성 추가와 프로젝트 방향 변경은 현행 권한 규칙에 따라 다룹니다. 이미 허용된 조사와 문서 갱신, 비파괴적 검증을 매번 다시 승인받는 흐름은 만들지 않습니다.

목표 지표는 질문 시점의 문서 최신성 100%, 현재 수정본과 검토 수정본이 어긋난 구현 시작 0건, 무단 수정 대상 0건, 사용자 작업 손실 0건입니다. 완료를 보고할 때는 필수 인수 기준에 모두 유의미한 근거가 있어야 합니다. 이 값은 성과 측정치가 아닌 수용 목표입니다.

## 29. 완료 판정과 사용자 경험

기획 요청만 있었다면 검토가 끝난 ready 문서 쌍과 재개 상태가 결과입니다. 구현 완료는 모든 필수 작업과 인수 기준의 증거를 확인하고 계획에 필요한 통합 및 저장소 검사를 마친 상태입니다.

마지막으로 기능 전체에 불필요한 코드, 파일, 의존성, 포맷 변경과 거부된 방향 변경이 남아 있지 않은지 확인합니다. 호환성과 남은 위험을 점검하고 state를 complete, active_slices를 빈 목록, next_action을 none으로 맞춘 뒤 한국어를 동기화합니다.

최종 보고에는 실제 구현 결과, 중요한 변경 파일, 재사용과 변경 필요성, 검증 결과, 명세 수정 번호와 작업 상태, 한계를 담습니다. 사용자에게 설계 전체를 다시 읽히는 대신 구현 결과를 판단할 근거를 제공합니다.

## 30. 미결정 유지보수 사항

문서 계약은 예산 수정 시 검토한 수정본에서 재개하도록 요구하고, 최소 변경 정책은 같은 전략의 명백한 추정치 오류를 추가 질문 없이 정정할 수 있도록 설명합니다. 이 기획서는 ‘문서 정정’과 ‘검토가 맞춰진 수정본의 구현 재개’를 구분했습니다. 향후 원본 지침을 유지보수할 때 두 설명을 같은 용어로 정리할 여지가 있습니다.

실제 평가용 정상 및 비정상 문서 쌍, 예산 초과와 상태 불일치 사례의 실행 기록은 이번 작업에서 만들지 않았습니다. 검증기와 작업 위임의 품질은 해당 평가 증거로 별도 판단해야 합니다.
