# Feature Planner Old

> 해당 스킬은 더이상 유지보수하지 않습니다. 새 스킬은 다음 3가지 스킬을 참고해주세요
> 
> - [feature-planner](../feature-planner/README.md)
> - [feature-implementer](../feature-implementer/README.md)
> - [respect-project-code](../respect-project-code/README.md)

영문과 한국어 기획 문서를 함께 관리하고, 최종 검토를 거친 계획의 작업 단위를 위임해 구현과 검증을 진행하는 스킬입니다. 저장소에서는 구버전으로 분류하지만 다른 스킬의 설치나 선행 실행 없이 자체 흐름으로 사용합니다.

[설계서](SPEC.md) · [실행 지침](SKILL.md) · [문서 계약](references/spec-contract.md) · [문서 검사 도구](scripts/specctl.py)

## 언제 사용하나요?

- 첫 질문 전부터 영문 정본과 한국어 검토 문서를 함께 유지하고 싶을 때
- 기획 중 에이전트가 선택한 구현 방법까지 확인하고 정정하고 싶을 때
- 수정 파일과 심볼, 변경 예산과 작은 작업 단위를 문서로 검토하고 싶을 때
- 이 스킬의 `feature-planner-control` 문서를 이어서 진행할 때
- 검토한 수정본에서 구현 작업을 위임하고 결과를 단계별로 검증할 때

기획만 요청할 수도 있습니다. 구현까지 진행하려면 검토된 문서와 구현 요청이 필요합니다.

## 시작 전에 알아둘 점

스킬을 사용할 수 있는 에이전트 환경에서 대상 프로젝트를 엽니다. 자료 읽기와 문서 편집 기능이 필요하며, 제공된 문서 검사 도구를 실행하려면 Python을 사용할 수 있어야 합니다.

구현 편집은 내부 작업자가 담당합니다. 작업자 기능이 없는 환경에서는 그 이유와 준비된 작업 요청을 제공하며, 주 에이전트가 조용히 대신 구현하는 방식으로 전환하지 않습니다.

아래 `$feature-planner-old`는 채팅용 호출 표현입니다. 뒤에서 소개하는 `specctl.py` 호출 예시는 터미널에서 실행하는 검사 명령입니다.

## 빠르게 시작하기

```text
$feature-planner-old
현재 프로젝트에 주문 취소 기능을 기획해 줘.
기존 주문 상태와 서비스 구조를 먼저 확인하고,
취소 조건, 수정 대상과 검증 방법을 문서로 구체화해 줘.
이번 요청에서는 기획과 검토까지만 진행해 줘.
```

스킬은 관련 코드와 테스트를 조사하고 두 언어의 초안을 먼저 작성합니다. 이후 중요한 질문을 기본 1~4개씩 제시하며 답변과 파급 변경을 문서에 반영합니다.

문서에는 사용자가 결정한 내용, 저장소에서 확인한 사실, 에이전트가 선택한 구현 방법을 구분해 기록합니다. 에이전트 판단은 검토가 필요한 항목으로 보여 줍니다.

## 전체 사용 흐름

| 단계 | 사용자가 하는 일 | 스킬이 제공하는 결과 |
| --- | --- | --- |
| 기획 시작 | 목표와 알고 있는 제약 전달 | 영문과 한국어 초안, 중요한 질문 |
| 구체화 | 질문에 답하고 잘못된 판단 정정 | 결정, 요구사항, 수정 대상과 예산이 갱신된 문서 |
| 최종 검토 | 현재 설계와 에이전트 판단 확인 | 구현 준비 검사 결과와 변경 범위 요약 |
| 검토 확인 | 추가로 정정할 내용이 없는지 답변 | 검토 수정본이 일치하는 `ready` 문서 |
| 구현 요청 | 검토한 문서의 구현을 명시적으로 요청 | 작업 위임, 실제 변경과 검증 결과 |
| 완료 또는 보완 | 남은 결정이 있으면 해소 | 통합 결과 또는 정확한 차단 이유와 재개 지점 |

최종 검토 시점에 “추가로 구체화할 내용 없음”이라고 확인하는 것은 준비된 설계를 검토했다는 의미입니다. 기획만 요청했다면 이 답변만으로 코드를 구현하지 않습니다.

## 사용 예시와 시나리오

### 1. 기획 문서 위치 지정하기

```text
$feature-planner-old
주문 취소 기능을 기획해 줘.
영문 정본은 docs/plans/order-cancel-spec.md에 작성하고
한국어 검토 문서도 같은 위치에 만들어 줘.
새 의존성 없이 기존 주문 서비스를 확장하는 방향을 우선 검토해 줘.
```

지정한 위치에 정본과 `order-cancel-spec.ko.md`를 만듭니다. 새 의존성이나 방향 변경이 필요하다고 판단하면 기존 방향을 유지하는 대안과 함께 이유 및 영향을 보여 줍니다.

### 2. 에이전트가 선택한 구현 방법 정정하기

```text
D-004의 새 취소 서비스 추가 방향은 원하지 않아.
기존 주문 서비스에서 처리하도록 바꾸고,
변경 대상, 작업 단위와 예산도 함께 갱신해 줘.
```

실제 문서에 있는 결정 ID를 사용합니다. 이전 결정을 대체된 이력으로 남기고 새 결정이 영향을 주는 전략, 파일, 심볼, 예산과 검증 계획까지 반영합니다.

### 3. 최종 검토를 마치고 기획 상태로 남기기

최종 검토 질문을 받은 뒤 다음처럼 답할 수 있습니다.

```text
추가로 구체화하거나 수정할 내용 없어.
현재 문서와 검토가 필요한 판단들을 확인했어.
구현은 아직 하지 말고 ready 상태로 남겨 줘.
```

현재 수정 번호와 검토 번호를 맞추고 `ready` 상태를 저장합니다. 이 답변 뒤 새 설계를 시작하지 않습니다.

### 4. 검토한 계획 구현하기

```text
$feature-planner-old
docs/plans/order-cancel-spec.md의 검토된 계획을 구현해 줘.
현재 수정본의 준비 상태를 검사한 뒤 작업 단위별로 진행하고,
실제 변경 범위와 예산, 동작 검증 결과를 확인해 줘.
```

영문 정본 전체와 문서 쌍을 확인합니다. 현재 수정본과 검토한 수정본이 다르면 그대로 구현하지 않습니다. 준비된 작업 단위를 작업자에게 하나씩 배정하고 결과를 검토합니다.

### 5. 구현 중 설계 공백이 발견된 경우

```text
취소 시 환불 방식은 원래 결제 수단으로 전액 환불하는 것으로 정할게.
이 결정 때문에 영향받는 요구사항과 작업만 갱신해 줘.
현재 변경 내용을 검토할 수 있게 보여 주고, 독립적으로 검증된 작업은 유지해 줘.
```

관련 설계를 수정하고 검토 상태를 갱신합니다. 변경된 수정본을 확인할 기회를 제공한 뒤 준비된 해당 작업부터 재개합니다. 전체 기획을 처음부터 다시 진행하지 않습니다.

### 6. 기존 문서에서 이어가기

```text
$feature-planner-old
docs/plans/order-cancel-spec.md와 한국어 사본의 현재 상태를 확인해 줘.
열린 질문, 검토할 판단과 작업 진행 상태를 정리하고
기획에서 남은 결정부터 이어서 진행해 줘.
```

문서의 제어 상태와 실제 기록을 기준으로 현재 단계를 판단합니다. 예시 경로는 작업 대상 프로젝트의 실제 문서 경로로 바꿉니다.

## 생성되는 문서와 상태

경로를 지정하지 않고 별도 프로젝트 관례도 없으면 다음 형식을 사용합니다.

```text
docs/specs/YYYY-MM-DD-<slug>-spec.md
docs/specs/YYYY-MM-DD-<slug>-spec.ko.md
```

두 문서는 첫 질문 전부터 존재하며 영문을 먼저 갱신한 뒤 한국어를 맞춥니다. 영문 정본은 구현 작업자가 읽는 기준 문서입니다.

| 상태 | 읽는 방법 |
| --- | --- |
| `refining` | 결정과 구현 설계를 구체화하거나 최종 검토를 준비하고 있습니다. |
| `ready` | 현재 수정본의 검토가 끝났습니다. 구현 요청을 기다리거나 구현을 시작할 수 있습니다. |
| `implementing` | 검토된 수정본의 작업을 진행하고 있습니다. |
| `blocked` | 특정 계약, 범위나 환경 문제를 해결해야 합니다. |
| `complete` | 필요한 작업과 통합 검증을 마쳤습니다. |

`ready`는 코드 구현 완료를 뜻하지 않습니다. 중요한 설계 변경이 생기면 이전 검토 상태를 해제하고 수정본을 다시 확인해야 합니다.

## 문서에서 무엇을 검토하면 되나요?

- 사용자에게 보이는 동작과 인수 기준이 의도와 맞는지
- 에이전트가 선택한 전략과 그 근거를 수용할 수 있는지
- 변경할 파일과 심볼, 재사용할 기존 구현이 적절한지
- 새 파일, 의존성과 공유 추상화가 정말 필요한지
- 작업 단위와 의존성, 수정 범위와 변경 예산이 타당한지
- 위험과 미결정 사항, 검증 방법이 빠지지 않았는지

예산은 예상보다 작업이 커지는 상황을 확인하는 기준입니다. 줄 수를 맞추기 위해 코드를 압축하거나 검증을 줄이는 용도로 사용하지 않습니다.

## 선택 사항: 문서 상태 직접 검사하기

스킬이 작업 중 사용하는 도구를 직접 실행할 수도 있습니다. 대상 프로젝트를 기준으로 영문 정본 경로를 전달합니다.

```bash
python /path/to/feature-planner-old/scripts/specctl.py status docs/plans/order-cancel-spec.md
python /path/to/feature-planner-old/scripts/specctl.py validate docs/plans/order-cancel-spec.md
python /path/to/feature-planner-old/scripts/specctl.py review-ready docs/plans/order-cancel-spec.md
python /path/to/feature-planner-old/scripts/specctl.py ready docs/plans/order-cancel-spec.md
```

`/path/to/feature-planner-old`는 실제 스킬 폴더의 절대 경로로 바꿉니다. 이 명령들은 사용 예시이며 현재 실행 결과를 의미하지 않습니다.

| 명령 | 용도 |
| --- | --- |
| `status` | 현재 상태와 검토할 항목 요약 |
| `validate` | 문서 쌍과 제어 상태의 정합성 검사 |
| `review-ready` | 최종 검토를 요청할 만큼 설계가 준비됐는지 검사 |
| `ready` | 의존성을 충족한 작업과 독립적인 병렬 후보 확인 |

검사기는 이 스킬의 문서 계약을 따르는 실행 명세를 대상으로 합니다. 일반 Markdown이나 스킬 자체의 [SPEC.md](SPEC.md)에 그대로 적용하지 않습니다. 문서 검사가 통과해도 코드의 동작과 번역 의미를 모두 보증하는 것은 아닙니다.

## 자주 생기는 상황

| 상황 | 처리 방식 |
| --- | --- |
| 작업자가 완료를 보고함 | 실제 diff, 범위, 예산과 검증 결과를 확인한 뒤 수용합니다. |
| 같은 파일을 수정할 작업이 여러 개임 | 독립성이 입증되지 않으면 순차로 실행합니다. |
| 변경 예산을 초과함 | 원인과 전략을 확인하고 필요한 문서 수정 및 검토를 거칩니다. |
| 문서에 없는 동작이 필요함 | 해당 작업을 멈추고 영향받는 영역만 다시 구체화합니다. |
| 작업자 기능이 없음 | 차단 이유와 준비된 작업 요청을 제공합니다. |
| Python이나 검증 환경을 사용할 수 없음 | 검사를 통과했다고 보고하지 않고 필요한 환경과 남은 한계를 밝힙니다. |
