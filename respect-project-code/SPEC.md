# Respect Project Code 스킬 기획서

작성일: 2026-09-07 / 개정: 2

이 문서는 Respect Project Code의 단독 사용 조건부터 코드 변경, 검증과 완료 보고까지 정의합니다. 다른 스킬의 설치, 기획서 생성이나 작업자 실행을 전제로 하지 않습니다. 예시의 코드, 파일 경로와 결과는 설명용입니다.

근거: [스킬 정의](SKILL.md), 패키지 설명, [공통 행동 평가](tests/acceptance.md), [모델별 평가](tests/model-profiles.md).

## 1. 개요

### 1.1 제품명과 한 줄 정의

Respect Project Code는 기존 프로젝트의 코드 관례와 사용자 작업을 보존하면서 요청한 기능, 버그 수정과 범위가 정해진 리팩터링을 필요한 만큼 구현하는 독립적인 코딩 스킬입니다.

### 1.2 제공하는 결과

사용자는 요청한 동작을 반영한 변경과 검증 결과를 받습니다. 별도 기획 문서를 먼저 작성하거나 특정 실행 도구의 결과를 제출할 필요가 없습니다.

변경 결과는 주변 코드와 같은 위치, 이름, 제어 흐름과 오류 처리 방식으로 읽혀야 합니다. 필요한 호출부, 타입과 테스트는 포함하고 작업과 무관한 정리와 구조 변경은 제외합니다.

## 2. 배경과 문제 정의

### 2.1 작은 요청이 큰 수정으로 번지는 문제

경계 조건 하나를 수정하는 동안 파일 전체를 포맷팅하거나 이름을 바꾸면 실제 동작 변경을 찾기 어려워집니다. 새 공통 도우미와 설정을 만들면 검토 범위뿐 아니라 이후 유지보수 범위도 늘어납니다.

### 2.2 전역 스타일을 가까운 코드에 강요하는 문제

하나의 저장소 안에서도 패키지별 코드 관례와 설정이 다를 수 있습니다. 에이전트가 익숙한 스타일이나 다른 패키지의 구조를 적용하면 새 코드가 대상 모듈과 어긋납니다.

### 2.3 줄 수를 줄이려다 정확성을 잃는 문제

오류를 무시하면 한 줄로 끝날 수 있지만 원인은 해결되지 않습니다. 필요한 호출부나 테스트를 생략한 수정은 작아 보여도 완전한 구현이 아닙니다.

### 2.4 기존 작업을 자기 변경으로 취급하는 문제

사용자 수정, staged 상태와 실행 중 생긴 다른 변경을 구분하지 않으면 원하지 않은 내용을 되돌리거나 본인이 만들지 않은 변경까지 완료 보고에 포함할 수 있습니다.

### 2.5 근거 없는 검증과 끝없는 정리

검사를 실행하지 않고 통과를 보고하거나, 수정 후 실패를 근거 없이 기존 문제라고 단정할 수 있습니다. 반대로 필요한 검사가 끝나도 선택적인 정리와 최적화를 계속하면 요청 범위를 벗어납니다.

## 5. 호출 설계

### 5.1 적용할 요청

```text
$respect-project-code
검색어가 비어 있을 때 발생하는 오류를 고쳐 줘.
주변 컴포넌트와 오류 처리 방식은 유지해 줘.
```

다음과 같은 기존 프로젝트 작업에 적용합니다.

- 기능 추가와 기존 동작 확장
- 버그와 경계 조건 수정
- 명시적으로 범위가 정해진 리팩터링과 마이그레이션
- 기존 스타일 유지와 관련 없는 변경 최소화 요청

### 5.2 적용하지 않을 주 요청

읽기 전용 코드 리뷰, 원인 분석만 요구한 요청이나 초기 아키텍처 상담은 편집 권한을 만들지 않습니다. 명시적으로 스킬을 언급해도 사용자가 요청한 작업 종류와 범위를 따릅니다.

### 5.3 호출 메타데이터

[agents/openai.yaml](agents/openai.yaml)의 표시명은 `Respect Project Code`, 짧은 설명은 `Preserve project style with the smallest safe diff`입니다. `allow_implicit_invocation: true`가 정의돼 있습니다.

암묵적 호출을 허용하는 설정과 실제로 해당 요청에서 스킬이 선택됐다는 관찰은 구분합니다. 평가에서는 명시적 호출과 암묵적 선택을 따로 확인합니다.

## 6. 입력 계약

| 입력 | 확인할 내용 | 정보가 부족할 때 |
| --- | --- | --- |
| 사용자 요청 | 바꿀 동작, 보존할 동작과 완료 조건 | 관련 코드를 읽고 중요한 모호함만 질문합니다. |
| 기존 프로젝트 | 실제 구현, 호출부, 테스트와 구조 | 요청한 동작에 필요한 영역부터 조사합니다. |
| 적용 지침과 설정 | AGENTS.md, formatter, lint, 타입과 빌드 규칙 | 임의의 전역 관례를 만들어 적용하지 않습니다. |
| 시작 파일 상태 | staged, unstaged, untracked와 관련 내용 | Git이 없으면 파일 비교나 임시 스냅샷을 사용합니다. |
| 검증 환경 | 실행 가능한 기존 명령과 검사 범위 | 사용할 수 없는 검사를 명확하게 기록합니다. |

별도 계획 문서, 요구사항 ID나 다른 스킬이 만든 실행 기록은 필수 입력이 아닙니다. 있으면 요청을 이해하는 자료로 사용할 수 있습니다.

## 7. 출력 계약

### 7.1 필수 결과

필요한 파일 변경과 다음 내용을 담은 보고서를 제공합니다.

1. 무엇을 바꿨는지와 해당 로컬 접근을 택한 이유
2. 실제 실행한 검사와 결과
3. 필요한 범위 확대, 차단된 검사와 남은 한계

### 7.2 필수가 아닌 산출물

시작 상태, 관례 요약과 간단한 변경 지도는 작업 맥락이나 허용된 임시 저장소에 둘 수 있습니다. 이 스킬을 적용했다는 이유만으로 프로젝트에 설계 문서, 로그 파일이나 보고서 파일을 추가하지 않습니다.

별도 작업 흐름과 함께 쓰더라도 이 스킬 자체의 설치와 단독 사용 가능성은 유지합니다. 이 경우 해당 작업의 기존 보고 형식과 권한을 따릅니다.

## 9. 작업 시작 상태 확보

### 9.1 Git이 있는 경우

`git status --short`와 관련 파일의 unstaged, staged diff를 확인합니다. untracked 파일은 일반 diff에 나타나지 않으므로 내용을 별도로 읽습니다. 수정할 수 있는 파일의 시작 내용이나 패치를 작업 맥락 또는 허용된 임시 저장소에 유지합니다.

### 9.2 같은 파일에 기존 수정이 있는 경우

사용자가 오류 메시지를 이미 수정한 상태에서 에이전트가 조건문을 고쳐야 한다고 가정합니다. 시작 내용에서 사용자 메시지 변경을 확인한 뒤 해당 내용을 유지하는 부분 편집을 수행합니다.

파일 전체를 이전 버전으로 복원한 다음 자신의 변경만 다시 적용하는 방식은 사용하지 않습니다. 소유권이 불명확한 중첩 편집은 해당 부분을 멈추고 충돌을 해소합니다.

### 9.3 동시 수정과 Git이 없는 경우

동시 수정 가능성이 있으면 실제 편집 직전에 대상 파일을 다시 읽습니다. Git이 없으면 파일 내용 비교로 같은 보존 원칙을 적용하며, 저장소 초기화와 자동 정리를 추가하지 않습니다.

## 10. 로컬 관례 조사

### 10.1 조사 순서

1. 적용 지침과 설정을 확인합니다.
2. 대상 구현과 관련 호출부를 읽습니다.
3. 기존 테스트와 검증 명령을 확인합니다.
4. 실제로 비교 가능한 주변 구현 1~3개를 읽습니다.
5. 아직 동작이나 영향 범위가 불분명할 때만 조사를 넓힙니다.

### 10.2 관례 우선순위

명시적인 규칙과 적용 설정을 추론한 습관보다 우선합니다. 그 안에서 대상 파일, 같은 모듈이나 패키지, 비교 가능한 다른 코드 순으로 근거를 찾습니다. 똑같이 적용되는 명시 규칙이 충돌하면 중요한 충돌을 해소합니다.

### 10.3 확인할 스타일의 범위

| 영역 | 확인할 예 |
| --- | --- |
| 구조 | 파일 위치, 모듈 경계, 상태와 부수 효과의 소유 위치 |
| 선언 | 함수와 타입의 이름, export 방식, 제네릭 사용 |
| 의존성 | import 경로와 순서, 기존 유틸리티 사용 방식 |
| 제어 흐름 | 오류 반환과 예외 처리, async 처리와 취소 |
| 프레임워크 | 상태, 반응성, 생명주기와 컴포넌트 구성 |
| 검증 | 테스트 위치, fixture와 mocking, assertion 방식 |
| 텍스트 | 주석 언어, 인코딩, 줄바꿈과 포맷 |

## 11. 작은 변경의 판단 모델

### 11.1 비교 기준

정확한 여러 선택지가 있다면 관련 없는 동작 변화, 구조 변경, 공개 계약과 검토 부담을 먼저 줄입니다. 그다음 불필요한 파일과 줄 수를 줄입니다.

### 11.2 재사용 조건

기존 함수나 도우미가 필요한 의미, 오류와 생명주기를 충족하면 재사용합니다. 비슷한 이름이라도 다른 계층에 의존하거나 실패 동작이 다르면 재사용을 강제하지 않습니다.

### 11.3 필요한 추가 파일과 추출

현재 구조와 요청한 동작에 필요한 테스트, 호출부, 타입, export와 생성물은 포함합니다. 정확성이나 기존 구조 때문에 작은 로컬 함수 추출이 필요하면 허용합니다. 가상의 미래 호출자를 위한 범용 인터페이스와 설정은 만들지 않습니다.

## 12. 변경 지도 예제

다음 예제는 필수 산출물 형식이 아닌 작업 중 판단을 설명합니다.

```text
요청: 빈 검색어에서 발생하는 오류 수정
현재 동작: 빈 입력도 검색 파서에 전달됨
보존: 공백 정규화, 일반 검색 결과, 오류 메시지 형식
대상: 실제 검색 입력 처리 함수
기존 패턴: 같은 모듈의 빈 입력 처리 방식
필요 변경: 검색 실행 전 기존 빈 상태 분기 사용
필요 검증: 빈 입력, 공백 입력, 정상 검색 회귀 사례
제외: 컴포넌트 분리, 이름 변경, 검색 엔진 교체
```

대상 파일 경로나 현재 동작은 실제 조사로 채웁니다. 예제의 동작이 현재 프로젝트에도 존재한다고 가정하지 않습니다.

## 13. 편집 정책

### 13.1 필요한 지점만 수정

필요한 표현식, 함수와 통합 지점을 편집합니다. 관련 없는 import 순서, 주석, 이름, 죽은 코드와 중복을 함께 정리하지 않습니다. 편집하지 않은 부분의 인코딩과 줄바꿈도 보존합니다.

### 13.2 의존성과 설정

단순 편의를 위해 패키지, lockfile, 빌드 설정과 테스트 도구를 바꾸지 않습니다. 요청 범위에서 필요한 변경이면 기존 도구를 사용하고 파생 변경의 이유를 설명합니다.

### 13.3 생성물

원본 파일을 수정하고 저장소의 기존 명령으로 필요한 생성물을 갱신합니다. 필요한 산출물을 누락해 diff가 작아 보이게 하거나 생성 코드만 손으로 고치지 않습니다.

## 14. 도구가 만드는 변경 통제

formatter, autofix, 생성기, 테스트와 빌드가 파일을 쓸 수 있는지 확인합니다. 가능하면 검사 전용 모드나 도구가 실제 지원하는 대상 제한 기능을 사용합니다.

도구 실행 뒤 시작 상태와 비교하고 이번 실행이 만든 불필요한 변경만 제거합니다. 파일 전체를 다시 쓰는 도구라는 이유로 기존 사용자 변경을 덮어써도 되는 것은 아닙니다.

필수 생성물이나 저장소 규칙 때문에 넓은 변경이 불가피하면 이유를 보고합니다. 필요한 변경과 편의를 위한 정리를 구분합니다.

## 15. 동작 검증

### 15.1 검증 범위

요청 동작과 인접한 경계 조건을 기존 테스트 방식으로 확인합니다. 대상 영역에서 시작하되 공유 함수와 여러 호출부에 영향이 있으면 통합 검증을 넓힙니다. 저장소 필수 검사는 범위가 넓어도 수행 대상입니다.

### 15.2 검증 품질

assertion을 약화하거나 snapshot을 무분별하게 늘리지 않습니다. 테스트를 통과시키기 위해 오류를 무시하거나 새 테스트 프레임워크를 추가하지 않습니다. 필요한 회귀 검증은 최소 변경 원칙을 이유로 생략하지 않습니다.

### 15.3 실패 분류

| 관찰 | 올바른 보고 |
| --- | --- |
| 이번 변경 때문에 검사가 실패 | 새 회귀로 다루고 관련 수정을 해결하거나 미완료로 보고합니다. |
| 변경 전부터 같은 실패가 있었음이 확인됨 | 확인 근거와 함께 기존 실패로 구분합니다. |
| 변경 후 처음 실패를 관찰했고 기준 결과 없음 | 원인이 아직 확인되지 않았다고 보고합니다. |
| 검사 도구나 의존성을 사용할 수 없음 | 실행 불가 이유와 확인하지 못한 동작을 밝힙니다. |

검사를 실행할 수 없다는 이유만으로 허용되지 않은 환경 변경이나 설치를 하지 않습니다.

## 16. 최종 변경 검토

시작 상태를 기준으로 staged, unstaged, 새 파일, 삭제와 생성물을 함께 확인합니다. `git diff --check`는 공백 등 패치 형식 검사에 유용하지만 동작과 소유권의 증거는 아닙니다.

각 변경 구간에 대해 다음을 확인합니다.

- 요청 동작, 필수 통합 또는 의미 있는 검증에 필요한가?
- 실제로 적용되는 로컬 패턴을 따르는가?
- 요청 밖의 동작과 다른 사람의 작업을 보존하는가?
- 피할 수 있는 포맷과 구조 변경이 섞였는가?

불필요한 본인 변경을 제거한 결과가 검증에 영향을 주면 해당 검사를 다시 수행합니다. 이미 목적을 충족한 검사를 새로운 이유 없이 반복하지 않습니다.

## 17. 중요한 예외 처리

| 상황 | 처리 | 완료 판정에 미치는 영향 |
| --- | --- | --- |
| 한 파일만 수정하라는 명시 경계 | 완전한 수정에 다른 파일이 필요하면 구체적인 누락 결정을 요청합니다. | 허용 경계 안의 부분 수정만으로 완료를 주장하지 않습니다. |
| 가까운 코드에 안전하지 않은 패턴 존재 | 직접 관련된 안전 조건을 충족하는 로컬 수정으로 구현합니다. | 위험한 동작을 복제하면 실패입니다. |
| 비교할 코드가 없음 | 현재 스택과 설정에 맞는 단순한 방법을 선택하고 중요한 가정을 밝힙니다. | 추측을 확인된 관례로 보고하지 않습니다. |
| 사용자가 리팩터링을 명시 | 요청한 변환과 필요한 지원 변경을 수행합니다. | 부수적인 현대화는 제외합니다. |
| 필수 검사 실행 불가 | 실제 제한과 미검증 동작을 보고합니다. | 모든 완료 조건을 검증했다고 표현하지 않습니다. |
| 협업 도구 없음 | 주 에이전트가 요청 범위의 작업을 수행합니다. | 작업자 부재 자체가 차단 사유는 아닙니다. |

## 18. 권한 경계와 독립성

요청한 기존 프로젝트 수정은 그 범위의 조사, 구현과 필요한 검증으로 구체화합니다. 일상적인 이름 선택과 필요한 지원 편집을 매번 다시 승인받지 않습니다.

명시적 파일 경계, 공개 계약, 구조, 의존성이나 위험한 마이그레이션을 넘어야 정확성을 확보할 수 있다면 필요한 이유와 추가 결정을 설명합니다. 더 깔끔해 보인다는 이유만으로 방향 전환을 제안하며 작업을 멈추지 않습니다.

이 스킬만 설치된 환경에서도 요청 해석, 시작 상태 확보, 수정, 검증과 보고가 가능해야 합니다. 다른 스킬의 문서나 승인 상태를 필수 진입 조건으로 추가하지 않습니다.

## 19. 모델별 보정 설계

공통 계약은 모든 실행에 적용합니다. 추가 보정은 최대 하나만 선택하며 공통 계약의 목적, 여섯 단계와 산출물을 바꾸지 않습니다.

| 입력 조건 | 선택 |
| --- | --- |
| 명시적 `respect-project-code profile: common` | 보정 없이 공통 계약 |
| 신뢰할 수 있는 현재 `gpt-6-astra` | Astra |
| 현재 `gpt-5.6-sol` 또는 OpenAI `gpt-5.6` 별칭 | Sol |
| 모델 정보 없음 또는 미대응, 유효한 명시적 astra/sol 힌트 | 해당 보정 |
| 모델 정보와 유효한 힌트 없음 | 공통 계약 |

현재 ID는 주변 공백과 대소문자만 정규화하고 정확하게 일치하는지 확인합니다. 인식된 현재 모델은 다른 모델 힌트로 덮어쓰지 않습니다. 무효하거나 충돌하는 fallback 힌트는 공통 계약으로 처리합니다.

모델 추정을 위해 인증 정보, API와 호스트 설정을 조사하지 않습니다. 코드에서 사용하는 모델명과 현재 코딩 에이전트의 모델도 구분합니다.

## 20. 보정의 내용과 작업 재개

### 20.1 Astra

저장소에서 정할 수 있는 선택을 직접 해결하고, 필요한 지원 편집에 임의의 승인 절차를 추가하지 않도록 합니다. 의미 있는 검증이 끝나면 불필요한 추가 검사를 중단하며, 허용되고 이점이 있는 제한된 협업만 사용하도록 안내합니다.

### 20.2 Sol

보고를 줄이더라도 필요한 동작, 지원 변경과 검증 근거를 빠뜨리지 않도록 합니다. 기존 관례와 변경 지도를 재사용하고, 작업 범위 안에서 직접적인 도구 사용을 유지하도록 안내합니다.

### 20.3 지침 누락과 모델 변경

선택한 보정 파일이 없으면 공통 계약으로 진행하고 최종 보고에 누락을 한 번 알립니다. 외부에서 대체 파일을 가져오거나 보정을 임의로 만들어 내지 않습니다.

모델이 바뀌면 보정만 다시 선택합니다. 같은 시작 상태, 사용자 변경, 범위, 결정과 검증 결과를 유지하며 완료된 작업을 처음부터 다시 수행하지 않습니다.

## 21. 파일 구성

```text
respect-project-code/
├── SKILL.md
├── SPEC.md
├── README.md
├── agents/
│   └── openai.yaml
├── references/
│   ├── gpt-6-astra.md
│   ├── gpt-5.6-sol.md
│   └── model-profile-sources.md
└── tests/
    ├── acceptance.md
    └── model-profiles.md
```

`SKILL.md`는 실행 진입점이고 모델별 파일은 선택된 경우의 추가 지침입니다. 출처 매핑과 평가 문서는 유지보수 자료이며 일반 구현 때 모두 읽어야 하는 것은 아닙니다. 별도 스크립트나 외부 서비스 의존성은 없습니다.

현재 패키지 문서는 한국어 사본들을 참조하지만 실제 저장소에는 해당 파일이 없습니다. 이 차이는 문서 구성의 미해결 사항으로 기록하며 존재하지 않는 파일을 현재 구성도에 포함하지 않습니다.

| 다른 스킬이 없는 환경 | 추가 계획과 의무 작업자 없이 수행 | RPC-10 |
| 모델 미확인 또는 보정 파일 누락 | 공통 계약으로 진행하며 설정 탐색 없음 | RPC-13 |

평가는 폐기 가능한 프로젝트에서 수행합니다. 시작 파일, 기존 변경, 도구 기록과 최종 diff를 보존하고 각 결과를 PASS, FAIL 또는 NOT_RUN으로 기록합니다. 정적 문서 검사나 보정 선택 시뮬레이션을 실제 행동 통과로 계산하지 않습니다.

## 25. 완료와 최종 사용자 경험

요청한 동작, 적용 관례와 필요한 검증이 충족되면 작업을 끝냅니다. 관련 없는 최적화 기회가 보이더라도 추가 편집을 시작하지 않습니다.

최종 보고 예시는 다음과 같습니다. 괄호 안은 실제 실행 결과로 채워야 하는 항목입니다.

```text
빈 검색어를 기존 빈 상태 처리로 연결했습니다.
같은 모듈의 입력 정규화와 오류 형식을 유지했습니다.

검증: [실제 실행한 검사와 결과]
변경: [본인이 수정한 파일과 필요한 이유]
한계: [실행하지 못한 검사와 미검증 동작, 없으면 생략]
```

사용자는 무엇을 고쳤는지, 왜 그 위치와 방식을 선택했는지, 실제로 무엇을 검증했는지를 확인할 수 있어야 합니다. 검증하지 못한 완료 조건이 있으면 그 한계를 결과에 포함합니다.

## 26. 미결정 유지보수 사항

한국어 사본을 실제 배포 구성에 포함할지, 기존 패키지 설명을 영어 파일 구성에 맞출지는 결정되지 않았습니다. 이 문서 작성에서는 스킬 원본이나 패키지 파일을 추가로 수정하지 않습니다.

행동 평가의 첫 실행 환경과 대상 모델, 반복 횟수도 정해지지 않았습니다. 측정 자료가 없는 상태에서 보정 지침의 효과나 최소 변경 성공률을 주장하지 않습니다.
